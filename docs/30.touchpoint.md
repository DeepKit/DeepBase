# HB 触点观察契约与四自交付质量度量规范 v2.1
(HB Touchpoint Observation Contract & Four-Self Delivery Quality Specification)

> **文件编号**：30.touchpoint  
> **文档版本**：v2.1 (语义定位与人机适配统一校准版 · 2026-09-08)  
> **实现状态**：规范定稿，运行时未实施  
> **适用范围**：`DeepBase` 核心库及下游所有基于 HB 人机行为适配基础设施（HB — Human Behavior Adaptation Infrastructure）构建的桌面与跨平台软件（`DeepCommerce 唤金`、`AsWish`、`DeepDsh`、`Assayer`、`DeepRW` 等）  
> **统一定位与核心哲学**：**机器迁就人，不让人迁就机器**（**HB adapts machine behavior to humans; it does not adapt humans to machines**）。  
> **触点定位校准**：**Touchpoint 是机器行为与 Human Behavior 发生实际交互适配的观察点（Observation Point），而不是操纵 Human 状态或推动自营销的工具。**  
> **严格分层与职责定界**：  
> 1. **UI Element ≠ Interaction Unit ≠ Judgment Unit**：纯展示元素、布局容器与装饰性视觉组件不得为了度量指标而强制包装为独立触点；  
> 2. **Touchpoint / Telemetry 降级**：从 HB 本体定位降级为可观察交互（Observable Interaction）的下游测量、分析与验证消费者；  
> 3. **四自定位校准**：“四自”是跨产品的 **AI 交付质量检查规则**，不是 Core Runtime 业务对象，更不是 HB 本体的存在目的（HB 本体目的是让机器行为适配人类认知与权责现实）。

## 1. 触点核心架构与代码级契约（`IHbTouchpoint`）

**并非每一个界面元素都是触点**。HB 严格恪守 `UI Element ≠ Interaction Unit ≠ Judgment Unit`。只有承载实质人机交互适配、决策输入或状态分流的关键交互单元，才赋予确定性的触点契约；纯展示文本、装饰性排版与静态容器禁止注册为独立触点。

### 1.1 触点单元五问准入模型
对承载关键交互与决策流转的候选触点，在研发与评审中必须明确回答五个问题：

```
                    ┌──────────────────────────────────────────────┐
                    │       Touchpoint 触点单元五问准入模型        │
                    ├──────────────────────────────────────────────┤
                    │ 1. 它是否承载实质人机交互与适配需求？        │
                    │ 2. 机器行为是否清晰适配了人的认知与后续动作？│
                    │ 3. 它是否符合交付质量标准 (懂/判/行/纠错)？  │
                    │ 4. 用户不依赖客服能不能独立完成？            │
                    │ 5. 产生的交互证据是否足以验证适配有效性？    │
                    └──────────────────────────────────────────────┘
```

> [!IMPORTANT]
> **红线原则**：验收不只验“有没有挂指标”，更严禁将触点异化为“商业状态跃迁或自营销转化”的工具。核心在于**机器行为是否充分适配了人类的认知与工作流**，是否让用户自然理解、自主判断、顺畅完成并在遇到异常时能够自主恢复。

### 1.2 Touchpoint Unit 最低结构化契约
每个触点单元在契约定义中，至少必须具备以下结构化属性：

```yaml
# Touchpoint Unit 触点单元基础契约
touchpoint_id: "tp_waterfall_card_action_001"   # 全局唯一触点标识
surface_id: "surface_workspace_main"            # 所在界面/容器标识
component_type: "THbFacetWaterfall"             # 承载的 HB 控件类型

purpose: "引导用户推演多方案并进入下一步决策"    # 触点业务意图
trigger: "user_select_facet_or_expand"          # 触发条件

# 核心状态机 (没有状态变化定义，就不能算合格触点)
user_state_before: "UNCERTAIN_ABOUT_OPTIONS"    # 用户进入前状态
user_action: "EXPAND_DETAIL_AND_SELECT_CHOICE"  # 用户在触点上的行为
user_state_after: "DECISION_COMMITTED"          # 用户离开后状态

touchpoint_role: "DECISION_GUIDE"               # 触点角色

# 四自交付质量画像 (至少贡献一项交付质量保障)

self_growth: true                               # 是否沉淀用户知识与偏好

# 动作与退出流
next_action: "EXECUTE_PIPELINE_STEP"            # 正向下一步动作
exit_action: "COLLAPSE_OR_NAVIGATE_BACK"        # 主动退出动作
fallback_action: "SHOW_DIAGNOSE_WIZARD"         # 兜底恢复动作

# 事件埋点与数据回流
event_name: "tp_waterfall_choice_selected"      # 触点主事件
success_event: "tp_step_succeeded"              # 成功流转事件
failure_event: "tp_step_aborted"                # 失败/放弃事件
support_fallback: "IN_APP_SELF_RECOVERY"        # 遇阻时的自助服务路径
```

## 2. 触点分级与采样策略

为避免海量界面元素产生度量风暴与 UI 阻塞，HB 确立三级触点分级与采样标准：

```
+-----------------------------------------------------------------------------------------------+
|                                    HB 触点三级分级与采样矩阵                                  |
+-------------------+-----------------------------------+---------------------------------------+
| 触点级别          | 适用界面元素与场景                | 遥测与证据采集策略                    |
+-------------------+-----------------------------------+---------------------------------------+
| **1. tlCritical** | 关键决策点 (提交/支付/高危门禁/确认)| **全量度量 + 完整证据链** (100% 采集) |
| **2. tlStandard** | 常规交互控件 (普通按钮/输入/菜单项)| **轻量遥测** (仅记录 ID + 操作 + 时间)|
| **3. 非触点**     | 纯展示元素 (文本标签/装饰/网格单元格)| **禁止注册为独立触点**                |
+-------------------+-----------------------------------+---------------------------------------+
```

### 数据网格聚合采样规则
- `THbDataGrid` 整体注册为一个容器级触点（`tp_datagrid`）；
- 单个单元格或数据行不得注册为独立触点；
- 行级交互采用**聚合采样机制**（每 $N$ 次同类行交互合并为一条聚合证据），确保 10 万行大数据场景下零度量性能压力。

## 4. 四自维度详细验收标准与度量口径

### 4.0 跨产品 AI 交付质量检查规则（Human 裁定收口 2026-09-07）

> **最新架构裁定**：我们决定把“UI 四自”正式发展为一套跨产品的 **AI 交付质量检查规则**。  
> **适用层级**：`DeepBase └─ HB └─ AI Interaction / Design System` 规范层。本规范首先是一套**设计规则、审阅规则与验收规则**，暂时不是 Core 运行时业务对象。  
> **红线铁律**：严禁在第一阶段为了“四自”创建类似 `TFourSelf`、`TFourSelfMarketing`、`THbFourSelfPanel` 等业务味很重的强类型。HB 负责提供通用的支撑能力（价值显影、下一步动作、解释、反馈、学习入口、恢复入口），下游产品（AsWish、唤金等）负责填充其具体领域业务内容。

#### 1. 什么是“AI 交付”？
> **AI 交付**，不是 AI 返回了一段文字，而是 AI 把事情整理到：**用户看得懂、能判断、能继续行动、遇到问题知道怎么办，并且人的判断有机会让以后做得更好**。

#### 2. 四自大白话定义与好坏对照

* **自营销（价值显影 · Value Revelation）**：
  - *本体定位澄清*：自营销不是 HB 本体的存在目的，更不是商业操纵或广告诱导。HB 本体的目标是 Human-Compatible Machine Behavior（让机器行为对人可理解、可判断、可操作、可修正）。作为交付质量检查标准时，其本质是**价值显影**——让用户一眼看出机器当前交付对其现实有何用途，不搞宣传包装。
  - *大白话*：用户看到 AI 给出的东西后，能不能很快知道“这个东西对我有什么用”。不要依赖宣传语。
  - *坏例子*：“AI 分析完成”、“处理成功”、“生成成功”。
  - *好例子*：“今天有 3 个人值得你重新联系”、“发现 2 处会影响最终界面的差异”、“这个方案能减少 4 个重复步骤”。
* **自承接**：
  - *大白话*：用户看懂结果以后，能不能自然知道下一步做什么。严禁把结果扔给用户就撒手结束。
  - *好例子*：发现 3 个值得联系的人 $\rightarrow$ 看推荐话术 $\rightarrow$ 选择 / 修改 $\rightarrow$ 确认下一步。
* **自成长**：
  - *大白话*：用户这一次说“这个好”、“这个不好”、“我为什么这样选”，能不能让软件以后更懂他。
  - *注意*：自成长第一阶段不是偷偷训练大模型，重点是：记录用户为什么这样判断 $\rightarrow$ 形成以后可以使用的偏好 $\rightarrow$ 下一次 AI 工作时参考。
* **低客服**：
  - *大白话*：用户遇到疑问、失败、限制或者不理解时，界面自己能不能把事情说明白。
  - *必须回答*：发生了什么？为什么？现在怎么办？还能不能继续？怎样恢复？

#### 3. 铁律：四自不是四块 UI

```text
四自 ≠ 四个面板
四自 ≠ 四个按钮
四自 ≠ 四个业务模块
```

四自是一套**检查一次 AI 交付是否完整的标准**。同一个界面可以同时完成四件事，例如：

```text
今天有 3 人值得重新联系                  <--- [自营销] 价值显影
       │
[看看怎么联系]                           <--- [自承接] 下一步动作
       │
[让我学习]                               <--- [自成长] 偏好学习入口
       │
[为什么推荐这 3 人？]                     <--- [低客服] 自主解释与释疑
```

#### 4. 检查办法与打分表

对每一次重要 AI 交付，均执行四项打分：
* **0 分**：没做到；
* **1 分**：做到了，但用户还需要明显费脑子；
* **2 分**：用户基本一看就懂。

| 项目 | 核心检查问题 | 0 分表现 (不可接受) | 1 分表现 (需优化) | 2 分表现 (标杆体验) |
| :--- | :--- | :--- | :--- | :--- |
| **自营销** | 用户很快知道“这有什么用”吗？ | “处理成功”、“生成完毕”无价值感文字 | 给出数据但需要用户自己心算推断用途 | 直白点出对用户的现实价值或收益 |
| **自承接** | 用户知道接下来最值得做什么吗？ | 结果展示完即终结，无明确正向动作 | 有按钮但选项过多、层级混乱 | 单一清晰的主推荐动作，辅助轻量分支 |
| **自成长** | 用户的判断能帮助以后做得更好吗？ | 无反馈入口，选完即丢弃 | 仅有大段空白让用户手写反馈小作文 | AI 猜理由，用户勾选，沉淀明确偏好 |
| **低客服** | 用户现场能知道为什么、怎么办吗？ | 弹系统级 Error 码或提示“请联系客服” | 有报错说明但未指引可行的恢复路径 | 现场说清发生了什么、为什么、怎么恢复 |

> [!IMPORTANT]
> **一票说明硬约束**：
> 1. 严禁简单规定“总分达到 X 就算通过”；
> 2. **任意一项为 0 分，都必须明确书面说明为什么这一次允许为 0**；
> 3. 重要 AI 交付原则上：**自营销不能缺，自承接不能缺**！

### 4.1 A. 自营销验收（Self-Marketing）
- **验收核心**：用户是否能在产品内部自然发现下一个业务价值。
- **必须满足**：
  - [ ] 每个核心功能至少存在一个自然的价值发现触点；
  - [ ] 触点与当前用户的上下文行为强相关；
  - [ ] 严格禁止全屏阻断式弹窗轰炸；
  - [ ] 用户拥有完全的主动权进入或拒绝下一功能；
  - [ ] 触点提供明确的“下一步”；
  - [ ] 用户拒绝后能自然平滑退出，不反复骚扰；
  - [ ] 无需销售或人工解说，界面自身即能自明其价值。
- **数据指标**：`discovery_rate`, `self_initiated_transition_rate`, `cross_feature_transition_rate`, `touchpoint_exit_rate`。

### 4.2 B. 自承接验收（Self-Onboarding · 四自核心）
- **验收核心**：用户遇到困难或复杂任务时，界面必须具备**自解释与自引导**分流能力。
- **必须满足**：
  - 路径严格符合：`问题 → 显影 → 选择/判断 → 分流 → 下一步`；
  - 严禁出现“如果不知道怎么办，请联系客服”的甩锅式提示，优先采用“你现在可能属于 A/B/C，请选择最接近的情况”；
  - [ ] 用户在任意时刻均清晰知道“自己当前在哪里”；
  - [ ] 用户明确了解“当前正在解决什么”；
  - [ ] 用户明确知晓“下一步是什么”；
  - [ ] 复杂任务支持通过多层瀑布向导逐层显影；
  - [ ] `UNKNOWN` 状态允许停下来补充材料或暂存草稿；
  - [ ] `REFER` / `FREEZE` / `ESCALATE` 异常状态严格阻断强推；
  - [ ] 用户可随时主动退出，且核心主干流程无需人工客服介入。
- **数据指标**：`self_onboarding_rate`, `self_resolution_rate`, `completion_rate`, `drop_off_rate`, `support_required_rate`。

### 4.3 C. 自成长验收（Self-Growth）
- **验收核心**：必须证明**系统因为用户的持续使用而产生了新的可用价值**。
- **必须满足**：
  - [ ] 系统能够安全、合规地记录用户操作反馈与有效结果；
  - [ ] 具备完备的回看机制（History / Snapshot / Diff）；
  - [ ] 第二次使用时可自动引用或复用第一次沉淀的有效模板或配置；
  - [ ] 产品能够根据历史结果自适应优化后续推荐路径；
  - [ ] 过去的错误路径与纠错记录可被系统学习并自动提示避坑；
  - [ ] 历史数据具备生命周期管理与数据治理边界，禁止无限制无限期盲目膨胀。
- **学习增益公式（Learning Gain, LG）**：
  $$\text{Learning Gain (LG)} = \text{第一次完成所需人工/解释成本} - \text{第二次完成同类任务所需人工/解释成本}$$
  - **合格硬指标**：任何主干业务功能追踪必须长期保持 $\text{LG} > 0$。

### 4.4 D. 低客服验收（Low-Service）
- **验收核心**：必须采用**“少客服 + 高成功率”的双向约束**，严禁追求虚假的客服量下降。
- **精确度量口径 —— 自助化解率（Support Deflection Rate, SDR）**：
  $$\text{SDR} = \frac{\text{产品内自助向导完整闭环解决的异常次数}}{\text{异常触发总次数}} \times 100\%$$
  - *注：自助失败后转人工的计入分母、不计入分子。*
  - **合格标准**：高频常见问题 $\text{SDR} \ge 80\%$。
- **红线警示**：
  > [!CAUTION]
  > **“客服咨询量下降，但未完成任务流失率（`unresolved_without_support_rate`）上升”直接判定为验收不合格！**

## 6. 本地优先遥测与数据隐私保护（Local-First Telemetry）

桌面端（VCL/FMX）面向企业与私域高隐私要求场景，HB 触点引擎严格遵守 **Local-First 原则**：
1. **零明文 / 零 PII 泄露**：遥测仅记录触点 ID、状态机跃迁与耗时毫秒，严禁采集明文文本、密码或交易数据；
2. **尽力而为持久化承诺（Best-Effort Persistence）**：
   - 退出与应用崩溃时 **best-effort 持久化** 至本地 SQLite（WAL 模式）；
   - 异常断电时最近写入窗口（最后一条事务提交之后）的缓冲数据可能丢失；
   - **持久化承诺等级为尽力而为（best-effort），非零丢失**。

## 7. 会话快照恢复机制（Session Snapshot Recovery）

为支撑“低客服 + 高完成率”，向导类容器（`THbFacetWaterfall`、`THbDialog`、`THbVoiceDialog`）支持 **会话快照恢复（Session Snapshot Recovery）**：
- **覆盖场景**：覆盖用户误关窗、切出查阅、应用崩溃场景（不含操作系统级断电未落盘窗口）；
- 再次激活触点时，界面平滑恢复并温和提示：*“已为您恢复上次推演进度”*，消灭因中断丢进度导致的客服求助。

## 8. 黑盒盲测打分模型（Four-Self Black Box Scoring Model）

盲测根据用户无协助独立完成情况，按四大维度综合评分：
- $\text{SM Score}$（自发现能力得分）：是否自发探索并理解价值；
- $\text{SO Score}$（自承接能力得分）：是否在 0 解释下完成任务；
- $\text{SG Score}$（自成长能力得分）：二次使用是否效率倍增；
- $\text{LS Score}$（自助服务得分）：遇到歧义或错误时是否自助化解。

*(注：详细盲测执行规程、G0–G4 五级门禁、性能门禁与反暗黑否决表详见 [31.hb-test.md](file:///d:/_Progs/02Business/DeepBase/docs/31.hb-test.md))*
