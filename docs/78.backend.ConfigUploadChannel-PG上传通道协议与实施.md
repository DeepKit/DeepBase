## 1. 背景

DeepDomIn 产出的站点适配配置需要一个权威上行通道写入 PG（deepkit.top 后端）。经查证 DeepBase 全部后端契约文档（65.Commerce / 66.DB4 / 67.DeepKitTop），现有端点仅覆盖 auth/commerce/license 与读端点（`GET /dk/updates/manifest`），**无现成上传协议**，本文档定义并冻结该协议。

链路全景：

```
DeepDomIn（适配工厂）
   │ POST /dk/providers/configs  (本文档协议)
   ▼
deepkit.top 后端 ──▶ provider_configs 表（权威原始成果）
   │ 可选 publish=true
   ▼
update_manifests（app_id=deepcompare-gateway-config）+ 静态 zip 包
   │ GET /dk/updates/manifest（既有端点）
   ▼
DeepCompare Gateway（用户端，轮询 → 下载 → 验签 → 热重载）
```

## 2. 协议冻结

### 2.1 数据表 provider_configs（PG）

```sql
CREATE TABLE IF NOT EXISTS provider_configs (
  id            BIGSERIAL PRIMARY KEY,
  provider_key  TEXT NOT NULL CHECK (provider_key ~ '^[a-z0-9_][a-z0-9_-]*$'),
  version       TEXT NOT NULL CHECK (version ~ '^[0-9]{4}\.[0-9]{2}\.[0-9]{2}(\.[0-9]+)?$'),
  config_json   JSONB NOT NULL,
  config_json_canonical_bytes BYTEA NOT NULL,
  sha256        TEXT NOT NULL CHECK (sha256 ~ '^[0-9a-f]{64}$'),
  status        TEXT NOT NULL DEFAULT 'draft'
                CHECK (status IN ('draft','building','published','failed','deprecated')),
  zip_pending   BOOLEAN NOT NULL DEFAULT FALSE,
  note          TEXT,
  created_at    TIMESTAMPTZ NOT NULL DEFAULT now(),
  UNIQUE (provider_key, version)
);
CREATE INDEX idx_provider_configs_key_status ON provider_configs (provider_key, status, id DESC);

-- 唯一发布头；同一 provider 只有这里决定当前版本，历史行不再同时标多个 active。
CREATE TABLE IF NOT EXISTS provider_release_heads (
  provider_key TEXT PRIMARY KEY,
  config_id BIGINT NOT NULL REFERENCES provider_configs(id),
  generation BIGINT NOT NULL,
  updated_at TIMESTAMPTZ NOT NULL DEFAULT now()
);

-- 幂等表；api_key_id 的 FK 由王维侧迁移绑定到真实服务间密钥表。
CREATE TABLE IF NOT EXISTS api_idempotency (
  api_key_id       BIGINT NOT NULL,
  idempotency_key  UUID NOT NULL,
  request_sha256   TEXT NOT NULL CHECK (request_sha256 ~ '^[0-9a-f]{64}$'),
  response_status  INTEGER NOT NULL,
  response_body    JSONB NOT NULL,
  created_at       TIMESTAMPTZ NOT NULL DEFAULT now(),
  PRIMARY KEY (api_key_id, idempotency_key)
);

-- 正式 migration 必须另含：真实 FK、审计表、配置制品作业表、update_manifests 的
-- app_id 唯一约束或等价行锁条件，以及 downgrade/rollback 脚本。
```

> PostgreSQL 使用 `~` 正则运算符，不使用 MySQL 风格 `REGEXP`。`id` 已是单调 revision，不再声明 `GENERATED ALWAYS AS (id)`；该写法在 PostgreSQL 中既冗余又存在生成列合法性风险。


### 2.2 上传端点 POST /dk/providers/configs

| 项 | 规格 |
|----|------|
| 鉴权 | `Authorization: Bearer <服务间 API key>`（复用 65.Commerce 契约的服务端到服务端 API key 机制；key 由后端签发，**不进任何用户端二进制**） |
| 幂等 | 请求头 `Idempotency-Key`（UUID）；同 key 重放返回首次结果（Commerce 契约既有模式）；Key 有效期 72 小时、与调用方 API Key 绑定（不同 API Key 使用同一 Key 视为无效）；响应体增加 `"idempotent": bool` 字段，重放命中时返回 true；**幂等表唯一约束为 `(api_key_id, idempotency_key)` 并记录 `request_sha256` 与原始响应，相同 key+ 相同 request 则返回首次结果，相同 key+ 不同 request 则返回 409 IDEMPOTENCY_KEY_REUSED；request_sha256 由服务端对收到的规范化请求体计算（客户端不参与，防篡改）；幂等表建表 SQL 见 §2.1，72h 过期行由每日核对任务统一清理** |
| Content-Type | `application/json` |
| 请求体 | `{ "provider_key": "...", "version": "...", "config_json": {...}, "sha256": "...", "note": "...", "publish": true|false }` |
| 201 | 创建成功；响应 `{ "id": N, "provider_key": "...", "version": "...", "accepted": bool, "publish_state": "draft|building|published|failed", "idempotent": false }` |
| 200 | Idempotency-Key 重放命中，响应体与 201 一致但 `"idempotent": true` |
| 400 | schema 校验失败（字段缺失/类型错误/sha256 与 config_json 不符） |
| 401 / 403 | 鉴权失败 / key 无上传权限 |
| 409 | (provider_key, version) 已存在且内容不同；相同内容视为幂等成功；响应附 `{"existing_sha256": "..."}` 供客户端展示差异提示 |
| 413 | config_json 超过 512KB 上限 |
| 429 | 限流：单 API Key 全局每分钟 ≤10 次上传；后续迭代可扩展单 provider_key 维度限流 |

服务端行为：
1. 校验 config_json 符合 DeepCompare provider 配置 schema（必需字段：url / selectors / actions / engine）；服务端校验失败返回 400 并附字段级错误（**不入库**）；
2. 服务端自行重算 sha256 与客户端声明值比对，不一致 400；
3. 发布状态机：
   - `publish=false`：同步事务只写 `status='draft'`，`zip_pending=false`，不得进入打包队列；
   - `publish=true`：事务 A 写 `status='building'`、`zip_pending=true`、审计和唯一制品作业；若幂等键或 `(provider_key, version)` 冲突，必须锁定既有行并按 request_sha256 判定重��/冲突；
   - Worker 构建制品后先完成签名、哈希和对象存储可读性验证；
   - **发布事务 B**：对 `provider_release_heads(provider_key)` 与 `update_manifests(app_id)` 取行锁（首发时使用 advisory lock 或等价唯一串行化机制），校验 expected generation/version，按整数段版本比较拒绝并发降级，然后在同一事务内切换 release head、manifest generation、目标行 `status='published'` 并清除 `zip_pending`；
   - 旧历史行保留为 published 历史，但“当前版本”只由 release_heads 决定；
   - 打包失败写 `failed` 并告警，事务 B 不执行；
   - Worker 必须使用唯一 job/lease、`FOR UPDATE SKIP LOCKED` 或等价机制避免同一配置重复并发发布。
4. 全部操作写审计日志（谁、何时、哪站点、哪版本）；
5. 每日定时核对任务：扫描已入库但 manifest 缺失/zip_pending 超过 30 分钟的记录，自动重试打包或告警人工介入。

### 2.3 直读端点 GET /dk/providers/config

| 项 | 规格 |
|----|------|
| 参数 | `?provider_key=<key>`（必填）、`&version=<v>`（缺省按 `provider_release_heads` 返回当前已发布版本） |
| 鉴权 | 与服务端调试一致即可；**客户端主链路不使用本端点**（主链路走 zip 包，见设计文档 §6） |
| 200 | `{ "provider_key", "version", "config_json", "sha256", "created_at" }` |
| 404 | 无该 provider_key 或版本不存在 |

权威源优先级：**zip 配置包为权威，本端点只读、仅供单站点增量查询与调试**。

### 2.4 版本与回滚规则

- version 单调递增（日期版本号）；禁止覆盖已发布版本；
- 回滚 = 以新 version 重新上传旧 config_json 内容（与 Gateway 侧 manifest_generation 单调规则呼应，见设计文档 §7.5）；
- `status=deprecated` 仅做历史下线标记；生产 zip 必须从 `provider_release_heads` 解析当前集合，禁止用多行 `status='published'` 扫描替代唯一发布头。


### 2.5 Manifest 签名、信任根与防回滚

> 签名算法以 78a ADR r1 §2.7 为法源：**RSA-SHA256（PKCS#1 v1.5, 2048-bit, Windows CNG 原生）**；算法门禁当前仅接受 `rsa-sha256`。Ed25519 为可选演进，当前禁用。

- Manifest 使用 RFC 8785 JCS 规范化后签名；客户端必须验证规范化字节、**RSA-SHA256 签名**、`key_id`、目标产品/架构、`issued_at`、`expires_at` 和 generation。
- 信任根公钥必须随客户端可信安装或通过已信任旧密钥签署的 keyset 更新；禁止由同一个尚未验证的 Manifest 自证公钥。
- 私钥不得进入客户端、数据库或普通配置；由受控 KMS/HSM/签名服务保管，具备双人审批、轮换、吊销与审计。
- 客户端持久化最高已接受 generation；除带有独立授权、审计的 rollback token 外，拒绝 generation 降低。
- 签名失败、过期、目标不符或 generation 回退时继续使用 LKG，并上报可诊断错误。

## 3. 客户端实施规格（DeepDomIn / 发布工具侧）

### 3.1 Delphi 组件 TConfigUploader

新增单元（建议放 DeepCompare 侧 `DeepCompare.Publish.Uploader.pas`，DeepDomIn 通过它导出上传；也可直接集成进发布 CLI）：

```pascal
TConfigUploader = class
public
  constructor Create(const ABaseUrl, AApiKey: string);
  // 上传单站点配置；APublish=true 时触发服务端更新 manifest
  function Upload(const AProviderKey, AVersion: string;
    AConfigJson: TJSONObject; const ANote: string;
    APublish: Boolean; out AResponse: string): Boolean;
end;
```

实现要点：
- HTTP 客户端用 `System.Net.HttpClient`（TLS ≥1.2，禁止明文）；
- config_json 发送前做**规范化序列化**（严格采用 **RFC 8785 JCS** 标准）：键按 Unicode 码点升序排列、无空白字符、布尔值用 `true/false`、数字不补前导零、空值转为 `null`、字符串统一 UTF-8 转义规则；服务端（王维侧）采用同款 JCS 库，双端单测对齐哈希值——**同一条 config 双端哈希必须相等**（验收硬条件）；**双方必须使用通过 RFC 8785 测试向量的库，并处理属性排序规则、ECMAScript 数字序列化、`-0`、非法 Unicode、重复 JSON Key、超出 IEEE-754 安全范围的数字**；建议 provider schema 对高精度数字采用字符串表达，服务端在转成 JSONB 前先对收到的原始 JSON/JCS 结果验签并保存 `config_json_canonical_bytes`；
- `Idempotency-Key` 每次上传生成 UUID，重试复用同一 key（网络超时重试 ≤3 次，间隔 2/4/8 秒指数退避）；
- API key 来源：发布机环境变量 `DK_PUBLISH_KEY`，**不落盘、不进 git、不进配置包**；密钥默认 90 天轮换，支持实时撤销（撤销后旧 Key 立即失效）；
- 409 → 明确报错提示版本冲突，附服务端返回的 existing_sha256 供人工比对差异，不允许静默覆盖。

### 3.2 发布流程两种形态

- **Phase 1（脚本版，不依赖本协议）**：导出 providers/*.json → 打包 zip + sha256 → RSA-SHA256 签名 → 上传静态区 → UPDATE update_manifests（经 SSH/脚本）；
- **Phase 2（API 版，本协议）**：DeepDomIn 适配完成 → TConfigUploader.Upload(publish=true) → 服务端自动落库 + 更新 manifest → 用户端 ≤10 分钟生效。

两形态可并存；zip 包链路始终是客户端主链路，API 上传只是权威成果入库 + 触发器。

### 3.3 与 DLL 插件热重载的衔接契约（关联 77.extend.PluginHotReload）

当 provider 配置的 `engine` 字段为 `dll:<plugin_name>` 时，该站点的运行依赖对应的 DLL 插件文件。衔接规则：

1. **打包方式**：zip 包**不内嵌 DLL 实体**；zip 内 `plugin_manifest.json` 引用制品仓库中 DLL 的 URL + sha256 + RSA-SHA256 签名（`plugins/<plugin_name>` 条目），config zip 保持轻量、只含 config JSON + plugin_manifest.json；DLL 的独立生命周期（单独更新/回滚/删除）由制品仓库保证；
2. **Gateway 校验顺序**：下载 zip → 校验整体 RSA-SHA256 签名 → 解压 → 逐个校验 config 的 sha256（与 provider_configs 表比对） → 按 plugin_manifest.json 的 URL 从制品仓库下载 DLL → 校验 DLL 的 sha256 与签名 → 触发插件热重载；**制品仓库不可用时降级策略**：保留本地旧版 DLL 继续运行 + 告警（禁止回退到无签名 DLL，禁止跳过校验）；
3. **版本匹配**：zip 包内附 `plugin_manifest.json`，记录每个 DLL 的 `plugin_name`、`dll_version`、`compatible_config_version_range`；Gateway 加载 DLL 前校验当前配置版本在兼容范围内，不匹配则拒绝加载并告警；
4. **单独更新 DLL**：先向制品仓库上传新 DLL（新 sha256/签名）→ 再以新 config version 重新上传 config（config_json 内容不变，plugin_manifest.json 的 DLL 引用更新为新 URL/hash，`dll_version` 字段递增）→ 触发重新打包；
5. **DLL 制品来源（严重补充）**：本端点只上传 config JSON，**不支持直接上传 DLL 制品**；DLL 制品须通过独立的制品仓库（如 Nexus/Artifactory 或对象存储桶）提供：
   - 客户端另有一个端点 `POST /dk/plugins/upload`（待设计），负责 DLL 文件的二进制上传 + RSA-SHA256 签名验证；
   - Config upload 的 zip 包中，DLL 的下载路径指向制品仓库的 URL；
   - Gateway 下载 config zip 时，先校验 config zip 整体签名，再按 zip 内的 URL 从制品仓库下载 DLL，校验 DLL 签名和 hash；
   - 制品仓库须独立于 config storage，保证 DLL 的生命周期管理独立（可单独回滚/删除）。
