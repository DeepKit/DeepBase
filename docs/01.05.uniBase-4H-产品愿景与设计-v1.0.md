# 01. 产品愿景与整体设计（软件工程导演台 / DevDirector / DevDirector）

> 目标：明确 **软件工程导演台（DevDirector，内部工程代号：DevDirector，内部简称：DevD）** 想成为一个什么样的工具（最理想状态），面对哪些用户，解决什么问题，并给出高层能力地图，指导后续 MVP 和实现决策。

---

## 0. 文档定位

- 本文回答的问题：
  - DevDirector 在整个 AipexBase 生态中的定位是什么？
  - 最理想情况下，DevDirector 能力边界到哪里？
  - 它为人类开发者与多 AI/MCP 带来什么独特价值？
- 本文 **不讨论** 细节实现、技术栈和具体数据表设计，这些分别在 03/04/05 中展开。

---

## 1. 产品一句话愿景

> **DevDirector = 面向 AipexBase 项目的工程质量中枢，是一个用 AI 驱动的“工程操作系统 + 协作驾驶舱 + 决策黑匣子”。**
>
> 它用“编排 + 模型 + 多 AI 协作”统筹从需求挖掘到实现与回顾的全过程：
> - 把项目拆成清晰的功能卡片（Feature）和可执行的 00-xx 步骤计划（StepPlan）；
> - 规范人类与 MCP/IDE 之间的输入/输出契约，并通过 Prompt 编译器注入给 AI；
> - 在执行过程中记录所有关键决策（Decision）、执行（Execution）和经验（Guideline/Pattern/BugCase/WorkLog）；
> - 让工程既能在 AI 的帮助下跑得更快，又不容易失控，并且可追溯、可复用。

理想状态下：

- 新项目接入 AipexBase 时，人类打开 DevDirector：
  - 先在“功能板”中列出要做的功能；
  - 为每个功能一键套用“步骤模板”；
  - 人类按步骤配合 AI/MCP 执行，大部分建模与后端工作在几小时内收敛；
- 复杂变更（如字段调整、索引优化）在 DevDirector 中可视化对比、审批和回滚；
- 整个项目的知识沉淀在 DevDirector 的“档案视图”中，而不是散落在群聊和零散文档里。

## 1.5 关键价值主张（对个人高阶全栈开发者）

站在“像你这样的单人全栈、预算有限但怕翻车”的角度，DevDirector 最核心的两点价值是：

1. **工程黑匣子：出了事能查清楚**  
   - 对所有高风险改动（表结构、大逻辑、大功能）自动沉淀：需求、预案、决策、执行摘要和关键 AI 输出；
   - 发生问题时，可以快速重放“当时是怎么想的、谁拍的板、AI 建议了什么”，避免推倒重来或陷入无头苍蝇式排查。

2. **AI 安全阀：AI 乱来之前能被发现**  
   - 对标记为高风险的 Step，通过规约/知识库/BugCase 自动强化 Prompt，并在接收 AI 输出后做一次“自动体检”：
     - 检查是否引用不存在的表/字段/接口；
     - 检查是否违反 Must 级规约；
     - 检查是否复现已知 Bug 模式；
   - 给出清晰的安全信号（通过/可疑/危险），让你既敢大量使用 AI，又不会被它拖累工程质量。

这两点构成了 DevDirector 对个人开发者愿意付费的直接理由：
- 只要少翻一两次大的车，就足以覆盖工具成本；
- 同时把长期方法论沉淀下来，为未来的团队化和分享打下基础。

## 1.6 人–AI–系统三方分工：手+眼 / 算力+智力 / 记忆+规范

在整体愿景层面，我们约定一条长期有效的分工原则：

- **人类（产品/工程/测试）= 手 + 眼**  
  - 主要职责：在导演工作台中直接操作和审视可见的界面与场景流，判断“好不好用、顺不顺、说得过去”；
  - 交互原则：
    - 优先提供可视化直接操作（拖拽、拉伸、属性面板），自然语言交互是可选捷径，而不是唯一入口；
    - 典型高频任务的操作路径应尽量压缩到最短（就地完成，而不是在多个子系统之间来回切换）。

- **多 AI 角色 = 算力 + 智力**  
  - 主要职责：基于当前工程模型和历史记忆，负责“想”和“算”的部分：
    - 挖需求、补边界和异常场景；
    - 生成和对比不同实现预案，提示风险与依赖；
    - 利用历史项目经验发现潜在遗漏和反模式，提出替代方案；
  - 约束：不抢夺人类的决策权和直接操作权，不强行覆盖人通过手+眼已经确认的结果。

- **系统（DevDirector / DevDirector）= 记忆 + 规范**  
  - 主要职责：作为工程“黑匣子”和“质量地基”，长期沉淀工程事实，并在此基础上形成可执行的规范：
    - 记忆至少覆盖三层：
      - 原始语义层：需求原文、关键对话和会议纪要；
      - 模型演化层：角色/道具/界面/场景等结构性变更及其原因；
      - 运行与质量层：测试结果、线上真实路径、Bug 与事故的落点。
    - 在这些记忆之上，抽象出可复用的经验模式（最佳实践与反模式）。
  - 规范分级：
    - 红线：少量必须阻断的规则（例如：没有任何界面/场景分镜就将 UI 需求标记为“完成”），在关键动作发生时明确拦截并给出替代方案；
    - 黄线：持续提醒但不挡路的规则（例如：只有主路径、长期没有任何异常/边界场景的 Feature），以局部黄点和一句话提示形式存在，必要时可一键让 AI 给出改进建议；
    - 蓝线：从历史项目中沉淀的经验与推荐（例如典型异常处理模式、常见易错布局），以轻量卡片的形式在合适时机出现，完全不强制。
  - 交互原则：
    - 记忆要“贴近当前焦点”呈现，例如对象局部时间线、场景热力图和历史快照，而不是藏在独立系统里；
    - 规范大部分时间静默存在，只在真正高风险的关键节点介入，既保护工程质量，也不过多打断人用手+眼走最短路径。

## 2. 目标用户与使用场景

### 2.1 目标用户

> 当前产品范围**限定在以 AipexBase 为后端的平台型项目**，不考虑纯前端或与 AipexBase 无关的系统。

1. **项目 Owner / 架构负责人**  
   - 需要一个地方：统一看到多个 AipexBase 项目有哪些功能、处于什么阶段、有哪些关键决策和风险。

2. **后端 / 全栈工程师（偏 AipexBase）**  
   - 需要系统化地：
     - 规划表结构和数据模型；
     - 通过 MCP 驱动 AipexBase 完成建表/改表；
     - 记录每次 DDL 与变更背后的原因。

3. **前端 / 客户端工程师**  
   - 希望有清晰的接口契约、Mock 数据来源和变更记录。

4. **测试 / 质量负责人**  
   - 需要基于“功能 + 流程步骤”来设计测试计划与回归用例。

5. **团队协作成员（多用户场景）**  
   - 多人共同在 DevDirector 中查看/维护同一组 Project/Feature/Step；
   - 需要按用户记录执行历史和工作日志，支持简单的责任归属与协作。

### 2.2 典型使用场景（理想状态）

- 新建 AipexBase 项目前，架构师在 DevDirector 中：
  - 建立项目 → 列出功能 → 为每个功能套用模板生成一套 00-xx 步骤。
- 之后几天内，开发团队围绕这些步骤推进：
  - MCP 相关的步骤由 AI + 人类在 IDE 中协同执行；
  - 前端步骤产出接口契约与页面雏形；
  - 测试步骤产生测试计划与初始用例。
- 所有执行（尤其是 DDL）前，都在 DevDirector 中经过仿真和审批；
- 上线后，任何故障/疑问都可以通过 DevDirector 的档案查到“是谁在什么时候、基于什么理由做了什么更改”。

## 3. 不做什么（产品边界）

为避免 DevDirector 变成“什么都做一点的万能工具”，需要在愿景层面明确“不做的事”：

1. **不做通用 AI 聊天 IDE**  
   - 代码补全、重构、调试等交给 Cursor / VSCode / 其它 IDE；
   - DevDirector 只关心：项目/功能/步骤/协议/决策层面的“编排”和“记录”。

2. **不直接承担执行引擎职责**  
   - AipexBase + MCP 仍是后端执行的真正引擎；
   - DevDirector 的职责是：制定计划、生成提示词与参数、记录执行与审批结果。

3. **不替代详细技术规范文档**  
   - 全局的编码规范、安全规范、测试规范仍在统一文档仓库维护；
   - DevDirector 文档只描述自身产品与实现，不复制粘贴那部分内容。

4. **不做复杂监控/运维平台**  
   - 监控和运维只在需要时挂接链接或简单字段；
   - 真正的性能监控和告警继续由专门的运维系统承担。

## 4. 高层能力地图

从“理想终态”出发，DevDirector 主要包含以下能力域：

1. **项目与功能管理（Project & Feature Management）**  
   - 项目列表与元数据；
   - 功能卡片（Feature）的创建、分类、优先级管理；
   - 功能状态流转（规划中 → 进行中 → 已归档）。

2. **流程编排（Flow / Step Orchestration）**  
   - 基于 00-xx 编号的步骤列表；
   - 步骤模板与流程模板（可复用）；
   - 步骤间依赖关系（先后、循环、分支）。

3. **协议归约（Input/Output Contract）**  
   - 为每个步骤定义输入/输出契约；
   - 建立“产物类型”（如 TableSchemaJSON、APIDoc、TestPlan 等）的统一抽象；
   - 支持步骤之间的产物引用与追踪（谁产生，谁消费）。

4. **执行与决策管理（Execution & Decision Management）**  
   - 记录针对 MCP/IDE/Console 的执行；
   - 对高风险操作进行审批与仿真；
   - 为每一次重要变更记录理由与结论。

5. **档案与版本管理（Archive & Versioning）**  
   - 按“项目/功能/步骤”维度记录历史；
   - 支持不同时间点/版本间的差异对比；
   - 支持从历史中提炼模板（通用流程和最佳实践）。

6. **多角色协作支持（Human + Multi-AI + MCP）**  
   - 显示不同角色的关注点视图（产品、后端、前端、测试）；
   - 为四个 AI 角色提供“可引用的上下文结构”（功能、步骤、协议、历史）。

7. **自然语言到界面视图的导演工作台**  
   - 针对“界面相关”的需求，提供一套“自然语言 → 角色+道具 → 分镜（帧）→ 场景流”的导演式工作台；
   - 支持从会议记录/说明文本中抽取场景、角色和业务对象，生成初始界面分镜（UIViewState 序列），
     并通过多轮问答和鼠标微调完善界面结构与状态；
   - 为后续的实现步骤和测试步骤提供“以视图和状态为中心”的统一参照系（详见 11/12/13/14/15 章）。

## 5. 版本演进路线（概览）

> 细节将在《02-MVP范围与约束_DevDirector.md》中展开，这里只给出方向性路线。

1. **v0.x（MVP）**  
   - 目的：
     - 先把“项目/功能/步骤”这三层结构固化下来；
     - 让你可以在一个界面里：列出功能 → 为每个功能维护 00-xx 步骤 → 记录简单的执行结果。
   - 特点：
     - 以“界面可用”为优先；
     - MCP 集成先以“生成提示词 + 人工复制执行”为主，暂不做直连执行。

2. **v1.x（增强期）**  
   - 加入：
     - 步骤模板与流程模板；
     - 初级的协议归约（输入/输出字段描述）；
     - 简单的审批标记与风险提示。

3. **v2.x（自动化与团队协作）**  
   - 加入：
     - 与 MCP 的安全直连执行（在明确安全边界后）；
     - 更细致的角色视图（产品/后端/前端/测试切换）；
     - 多人协作与评论机制。

4. **v3.x（知识化与推荐）**  
   - 能力：
     - 基于历史项目自动推荐流程模板和步骤；
     - 为新项目生成“起步方案”，人类只需调整少量部分。

## 6. 与其它系统的关系

1. **与 AipexBase + MCP**  
   - DevDirector 不直接是 MCP 自身的一部分，而是 MCP 上层的“协作与决策 UI”；
   - MCP 的工具调用（`list_tables` / `execute_sql` 等）在 DevDirector 中表现为：
     - 某些步骤的“执行渠道”和“产物类型”。

2. **与 IDE / 编辑器（Cursor / VSCode / Windsurf 等）**  
   - IDE 负责代码级工作（编辑、重构、调试）；
   - DevDirector 负责项目级工作（需求、步骤、协议、决策）；
   - 交集：
     - 从 DevDirector 复制提示词/参数到 IDE；
     - 未来可能通过简单集成自动把“执行结果摘要”写回 DevDirector。

3. **与现有文档仓库（规范与说明）**  
   - 统一的规范文档仍然放在专门仓库中；
   - DevDirector 文档在引用时只做链接和简要说明，不重复维护细节。

## 8. 产品功能与交互设计补充原则

本节补充若干跨章节的设计约束，用于指导后续功能细化与 UI 设计评审，确保前述“手+眼 / 算力+智力 / 记忆+规范”的分工在产品形态上真正落地。

### 8.1 从“工位”而不是“功能列表”出发

- 设计任何主界面时，优先以“一个人一天坐在导演工作台前”的使用故事为出发点，而不是单纯罗列可用能力：
  - 关注视线与手势的主路径：一个产品/工程/测试角色在 3 小时内最常做的几件事，应当在同一视野内顺畅完成；
  - 对高频任务宁可牺牲部分低频功能的露出，也要保证主路径极简、极顺。
- 评审 UI 时优先问：
  - “一个人连续用一整天，会不会累、会不会乱、会不会经常被打断？”
  而不只是“功能齐不齐”。

### 8.2 为跨项目的知识复用预留挂钩

- 任何值得复用的设计成果，都要能在系统中“提炼成模板”或“标记为经验”：
  - 不仅包含流程模板、Step 模板，也包括典型异常处理模式、场景配置模式、测试覆盖策略等；
  - 产品上需显式提供“提炼为模板/经验卡片”的动作，而不是完全依赖隐式推断。
- 在模型上预留跨项目维度：
  - 关键场景、模式、决策需带有来源项目/版本信息，便于后续按项目族群进行统计和类比；
  - 支持在新项目中浏览和引用历史项目的决策链与经验，而不是简单复制粘贴流程。

### 8.3 提供安全的练习场与试玩模式

- 为降低上手成本，系统应内置一到多个“沙盒项目/样板戏”：
  - 自带 Demo 需求、Demo 场景和 Demo 界面，允许用户在无风险环境中随意尝试：拖拽、删除、一键用脑等操作；
  - 用以直观展示记忆如何呈现、规范如何介入、AI 如何给建议。
- 对真实项目提供“试玩/试改模式”：
  - 支持对某个 Feature/场景建立临时分支，在不影响主工程模型的前提下，大胆试验新的设计或让 AI 大幅改写；
  - 试验完成后可以一键合入或一键丢弃，减少因“怕动真数据”而压抑探索的情况。
- 渐进式暴露复杂度：
  - 初次使用时仅展示最核心的 20% 能力，其余高级功能通过引导或设置逐步解锁，避免新用户被信息量淹没。

### 8.4 让质量改进“看得见”

- 在导演工作台中，按 Feature/场景提供轻量的质量仪表：
  - 需求覆盖度（主路径 + 异常 + 边界）；
  - 测试覆盖度（按场景/接口维度）；
  - 历史 Bug/线上事故的分布与演化；
  - 设计变更频次和返工情况。
- 按版本/迭代支持一键回顾：
  - 展示本迭代新增或显著调整的场景与异常处理；
  - 对比前后 Bug/线上问题数量与严重度，让团队看到工具与流程的真实收益。
- 对 AI 贡献提供可感知的“战报”：
  - 统计在某个时间段内，AI 协助识别/补充了多少异常场景、提出了多少被采纳的预案或测试思路；
  - 不是作为 KPI，而是帮助团队建立对“在设计期多按几次一键用脑”的信心。

以上补充原则不新增新的强制流程，但应作为后续产品设计与评审时的“风格约束”，持续校正界面与功能实现是否真正服务于：
- 人的手+眼（顺手、路径短、不怕试错）；
- AI 的算力+智力（有足够结构化上下文和合理的用脑入口）；
- 系统的记忆+规范（长期可追溯、可学习、可见质量收益）。
