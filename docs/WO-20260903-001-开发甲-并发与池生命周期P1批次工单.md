## 一、修复项明细（7 项，主控已复核）

### FIX-1 · ObjectPool 锁内回调外移（C-CON-05 · Deadlock）

- **文件**：`D:\_Progs\02Business\DeepBase\Core\DeepBase.ObjectPool.pas`

- **现状**（主控复核）：Acquire 的两条命中路径都在 `FLock` 持有期间触发 `FOnObjectAcquired(Self, AObject)`——L689-690（取现成对象）与 L718-719（新建对象）。回调若重入 Acquire/Release 或自旋等待，直接死锁。

- **要求**：回调移到锁外：锁内只完成取对象 + 状态/统计变更，锁释放后统一触发 `FOnObjectAcquired`。注意 Exit 前的早退路径都要覆盖；等待超时路径不触发。同类回调（若有 OnObjectCreated 等）一并排查锁内调用。

### FIX-2 · EventBus edmMainThread 未计入异步跟踪（C-CON-06 · UAF）

- **文件**：`D:\_Progs\02Business\DeepBase\Core\DeepBase.EventBus.pas`

- **现状**（主控复核）：L952-963 `edmMainThread` 分支的 `TThread.Queue` 没有 `TrackAsyncBegin/TrackAsyncEnd` 包装（对比线程路径 L945-947 有 TrackAsyncEnd）。Destroy 的 drain 等待 `FAsyncCount=0` 时不知道 main-thread 队列还有未执行回调——`TThread.Queue` 的匿名闭包捕获 `LHandler/LEvent`，订阅者已销毁时回调体 UAF。

- **要求**：

  1. edmMainThread 入队前 TrackAsyncBegin，QueueProc 内 finally TrackAsyncEnd。
  2. Destroy drain 覆盖 main-thread 消息：drain 后调用 `TThread.Synchronize(nil, procedure begin end)` 风格的 barrier，或 `Application.ProcessMessages` 语义等价物（依本项目消息泵实际情况选型，方案进 brief）。
  3. 回调捕获改弱引用或与订阅生命周期绑定（按项目现有 EDM 其他分支的范本统一）。

### FIX-3 · Scheduler Start/Stop 无锁双 Timer 竞态（C-CON-07 · Race）

- **文件**：`D:\_Progs\02Business\DeepBase\Core\DeepBase.Scheduler.pas`

- **现状**（主控复核）：`Start`（L837-850）检查 `FRunning`、置 `FTimerThread` 全程无锁；`Stop`（L852-880）同样。并发 Start+Start 会双 Timer 线程 + 旧线程句柄覆盖泄漏；Start/Stop 交错可致 Stop WaitFor 一个已换人的线程。

- **要求**：引入 Start/Stop 互斥（专用 lifecycle 锁，勿与 job 执行锁复用防死锁），`FRunning`/`FTimerThread` 的读写全部进锁；Stop 的 drain 循环（L876-880）留锁外。补并发回归测试（双线程同时 Start 断言单 Timer；Stop 期间 Start 断言排队或拒绝，语义二选一进 brief）。

### FIX-4 · WorkerQueue Timeout 语义：超时后仍无限 WaitFor（C-CON-08 · Semantics）

- **文件**：`D:\_Progs\02Business\DeepBase\Core\DeepBase.WorkerQueue.pas`

- **现状**（主控复核）：L1934-1939 `LWaitResult := LDoneEvt.WaitFor(LTimeoutMs)` 超时后 L1939 仍无条件 `LHandlerThread.WaitFor`——注释自认「If we timed out, the handler may still be running — wait for it」。结果：标记失败（timeout）后 worker 槽仍被卡死的 handler 占用，timeout 只是 detect 不是 abort（与 BUG325 结论一致）。

- **要求**：

  1. 超时路径不再无限等待 handler：`TerminateThread` 禁止；正确做法是 handler 线程 `FreeOnTerminate := True` + 超时后放弃 join（记录泄漏告警 + DoPoolEvent 级别日志），或依赖 handler 内部协作取消（若项目已有取消令牌机制则接入）。方案与取舍（泄漏线程 vs 卡死 worker）进 brief，默认取向：**释放 worker 槽，泄漏告警**。
  2. `LHandlerErr` 在放弃 join 路径的归属要明确，不得 double-free。
  3. 扩展 BUG325 回归测试：超时后断言 worker 立即可接新任务。

### FIX-5 · DB.Pool Release 状态校验：复活 Invalidate + 双 Release（P-DB-P1）

- **文件**：`D:\_Progs\02Business\DeepBase\Persistence\DeepBase.DB.Pool.pas`

- **现状**（主控复核）：`TPooledConnection.Release`（L753-790）在锁内无条件 `FState := csIdle`（L766）：

  1. **复活问题**：连接已被 `Invalidate`（csInvalid，L791-796）后调用方又 Release，csInvalid 被覆盖成 csIdle——坏连接回池。
  2. **双 Release**：无 `FState = csInUse` 前置校验，重复 Release 会重复 SetEvent + 重复 TotalReleases 统计。

- **要求**：Release 进锁后先校验状态：仅 `csInUse` 才允许置 csIdle；`csInvalid` 保持不变（记事件「release after invalidate, discarded」）；非 csInUse 的重复 Release 记告警事件后直接返回，不动状态不发信号。注意 BUG334 的 Shutdown 路径依赖 Release 语义——shutdown 与 release 的交互（Shutdown 期间归还的连接状态）一并考虑，勿破坏 WO-001 FIX-1 行为（csInUse 连接 Shutdown 不释放）。回归测试挂 BUG334 同文件或新建编号。

### FIX-6 · JobQueue SQLite 事务模式不一致 → BUSY 死锁（P-DB-P1）

- **文件**：`D:\_Progs\02Business\DeepBase\Persistence\DeepBase.DB.JobQueue.pas` + `DeepBase.DB.Migrations.pas`

- **现状**（主控复核）：`DequeueSQLite`（L693-695）用 FireDAC `StartTransaction`（SQLite 默认 `BEGIN DEFERRED`——SELECT 不持写锁，UPDATE 升级写锁时才冲突）；而 Migrations（L148）显式 `BEGIN IMMEDIATE`。并发 dequeue + busy\_timeout 边界下，DEFERRED 升锁失败返回 SQLITE\_BUSY，且 SELECT-then-UPDATE 模式存在两消费者同时选中同一行的窗口。

- **要求**：SQLite 写事务统一 `BEGIN IMMEDIATE`（FireDAC：`Connection.TxOptions` 或 ExecSQL 前置设置——用项目现有机制，Migrations 的做法可参考）；`OwnTransaction` 各路径（enqueue L843/L1036/L1285 等所有 `StartTransaction` 调用点）统一处理，勿只修 Dequeue 一处。PG 路径不受影响。补并发 dequeue 回归测试（双线程并发 dequeue 断言无 BUSY 异常且行不重复消费——复用 CR-608 测试的并发模式）。
