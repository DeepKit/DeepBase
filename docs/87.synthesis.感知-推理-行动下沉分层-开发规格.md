## 0. 背景与动机

DeepAxis 是基于 DeepBase 的应用层包，目前把"感知(截图/OCR/视觉) →
推理(LLM 理解对话+决策) → 行动(系统级自动化操作界面)"三模块放在应用层。
这三项能力并非 DeepAxis 专属——任何基于 DeepBase 的桌面智能体程序
（桌面数据采集、UI 合规审计、操作录屏、其它自动化工具）都可能复用。

把它们困在 DeepAxis 里会产生两类问题：

- **复用壁垒**：下一个桌面程序要重写一遍截图/OCR/执行原语，且格式、
  准确率、问题排查方式各不相同。
- **底座退化**：通用机制沉在应用层，意味着每次应用迭代都可能动到本应
  稳定的执行器与感知器，违反底座"稳定、通用、少变"的设计原则。

本文档定义三模块**下沉为 DeepBase 基础设施**的分层机制、边界契约与落地路线。
注意：这不是把三模块从应用层"平移"到底座——真相源盘点（第 2 节）显示
三模块现状是"感知缺、推理已全、行动半套"，下沉是一个**分层剥离**动作，
不同模块的下沉深度不同。

> 本文档是综合规格，对应 docs/32-36 的整合结论，不是替代它们。

## 1. 下沉判据

单一判据，适用于全部三模块：

```
机制沉底，策略留上。
判据是"是否含业务语义"，不是"是否可能被复用"。
```

- **机制**：与具体应用无关的通用能力（截图、OCR、点击、键盘输入、
  LLM 调用、Provider 路由、Token 计量）→ 下沉到 DeepBase。
- **策略**：含业务语义的决策（"这个按钮该不该点""下一步做什么""
  "用哪条 Prompt""失败后怎么补"）→ 留在 DeepAxis 或具体应用层。

衍生规则：

1. **零业务语义红线**：下沉到 DeepBase 的单元/类/方法，不得出现
   "微信/购买/对话/任务/按钮名"等业务词。命中即驳回，保持基础设施纯度。
2. **三次法则**：先以内部模块形式下沉，接口保持可改；出现第 2 个
   真实消费者再冻结稳定 API。**不为想象中的复用者过早设计。**
3. **不假设必须使用 LLM**：下沉能力但不强制启用——规则引擎、离线、
   合规审计场景可能完全不需要 LLM 推理。底座提供能力，不替应用做决定。

## 2. 现状盘点（真相源核对）

下沉前必须先看清三模块在底座里**已经有什么**，避免重复造轮子。

### 2.1 推理层 —— 已是完整底座，无需下沉

DeepBase 已有成体系的 LLM/推理基础设施，分布在三个包：

| 包 | 内容 |
|---|---|
| `DeepBaseCore.dpk` | `DeepBase.LLM.Manager`（管理器，Core 层） |
| `DeepBaseLLM.dpk` | `DeepBase.LLM`、`DeepBase.LLM.BillingClient`、`DeepBase.LLM.PromptTemplateManager`、`DeepBase.AIErrorHandler.LLMBridge`、`DeepBase.LLM.ImportExport` |
| `DeepBaseFeatures.dpk` | `DeepBase.LLM.Service`、`DeepBase.LLM.Client`、`DeepBase.LLM.HTTP`、`DeepBase.LLM.Providers`、`DeepBase.LLM.Config`、`DeepBase.LLM.Proxy`、`DeepBase.LLM.Types` |
| `DeepBaseInference.dpk` | `DeepBase.Inference.Types / Runtime / Session / Service / IoC`（推理编排会话） |

关键公开 API（`Features/DeepBase.LLM.Service.pas`）：

```delphi

// 文本对话
```

**结论**：会议原设想的"瘦 LLM 网关等 ≥2 场景再抽"已被真相推翻——
它不是待抽的瘦网关，而是远超网关的完整系统（含 `TierVision` 视觉模型分层、
`PromptTemplateManager` 模板管理、`BillingClient` 计量、Provider 路由与降级）。
**推理层的"下沉"动作 = 零**。应用层只需声明依赖、调用 `LLM()` 全局入口。

### 2.2 行动层 —— 半套（UIA 引擎已存在，视觉兜底与统一执行器缺）

| 已有 | 位置 | 状态 |
|---|---|---|
| Win32 UIA COM 引擎 | `Features/DeepBase.UIA.Engine.pas`（docs/34） | 实现就绪，含 `TUIAElementLocator` + `FallbackChain` + `TFallbackPolicy` |
| Schema adapter（数据侧） | `Core/DeepBase.SchemaAdapter.WeChat39x.pas` / `WeChat4x.pas`（docs/32-33） | 数据持久化职责，与本轮正交 |

**缺**：

- UIA 找不到控件时的**视觉坐标兜底执行**（点击/输入仍靠 selector，无视觉降级）。
- 统一执行器抽象：把"UIA 操作"和"视觉坐标操作"收敛到同一执行原语接口，
  让应用层不感知底层走的是哪条通道。

**结论**：行动层的"下沉"动作 = **升级 UIA 引擎为双通道统一执行器**，
补视觉兜底，不是新建平行系统。

### 2.3 感知层 —— 缺（桌面侧无截图/OCR 单元）

| 已有 | 位置 | 说明 |
|---|---|---|
| 浏览器视觉 | `Features/DeepBase.Browser.Vision.pas` | 仅浏览器域，不覆盖桌面 |
| 启动闪屏 | `Core/DeepBase.SplashScreen.pas` | 非感知能力 |
| 桌面截图 / OCR / 元素视觉识别 | — | **不存在，需新建** |

**结论**：感知层是本轮唯一真正"新建下沉"的模块，复用价值最高、
策略污染最低、可逆——是 P0。

## 3. 各模块下沉决策

| 模块 | 决策 | 动作量级 | 去向 |
|---|---|---|---|
| 感知（截图/OCR/视觉） | **下沉（新建）** | 新建单元 + 新建包或并入 Platform | DeepBase，与 UIA 并列为"桌面感知双通道" |
| 行动（系统级操作） | **部分下沉（升级）** | 升级 UIA 引擎为统一执行器 + 补视觉兜底 | DeepBase（扩 `DeepBase.UIA.*` 或新建 `DeepBase.Actuation.*`） |
| 推理（LLM 决策） | **不下沉（复用）** | 零代码，仅声明依赖 | 已在 `DeepBaseLLM` + `DeepBaseInference` |
| 决策模板/Prompt 管理 | **不下沉** | — | 已有 `PromptTemplateManager`；业务 Prompt 永远留应用层 |
| schema adapter | **不纳入本轮** | — | 数据持久化职责，正交，单独演进 |

## 4. 分层架构与边界契约

### 4.1 依赖方向

```
                     DeepAxis 应用层
                  （策略：决策/编排/Prompt/业务规则）
                          │ 依赖
                          ▼
        ┌─────────────────────────────────────┐
        │  DeepBase 行动层（统一执行器）        │  ← 可选依赖感知层
        │  UIA selector 操作 + 视觉坐标兜底     │
        └─────────────────────────────────────┘
                  ▲                    ▲
                  │可选依赖            │依赖
        ┌─────────┴──────┐   ┌────────┴────────┐
        │ DeepBase 感知层 │   │ DeepBase 推理层  │
        │ 截图/OCR/视觉   │   │ LLM+Inference   │
        │ (纯机制,可独立) │   │ (已存在,复用)    │
        └────────────────┘   └─────────────────┘
                  │                            │
                  └──────── 调用 LLM().ChatVision ─┘
```

### 4.2 模块间边界契约

| 契约 | 规则 |
|---|---|
| **感知⇢行动** | 行动层**可选**依赖感知层（UIA 失败时请求视觉坐标）。感知层**不得**依赖行动层，可独立用于纯采集/审计场景。 |
| **感知⇢推理** | 感知层产出"图像+结构化描述"，调用 `LLM().ChatVision` 做语义理解。感知层不写业务 Prompt，只传图与中性描述指令。 |
| **推理⇢行动** | 推理层产出"意图/决策"，由应用层翻译为执行原语调用。**推理层不直接调用行动层**——中间必须经应用层编排，保持"底座无脑"。 |
| **schema adapter** | 与三模块正交。行动层操作 GUI，schema adapter 读写 DB，两者不互相调用。 |
| **LLM 防穿透** | DeepBase 只暴露 `LLM()` / `LLMAdmin()` 入口与 `ILLMClient`。业务 Prompt、决策编排、上下文管理一律留应用层。底座禁止"顺手把决策逻辑写进来"。 |

### 4.3 感知层接口草案（待 P0 实现时定稿）

```delphi
// DeepBase.Desktop.Perception.Types.pas（新建，零业务语义）
type
  TDesktopScreenshot = record
    ImageBase64: string;   // 直接喂 LLM().ChatVision
    MimeType: string;      // 'image/png'
    CaptureRect: TRect;    // 全屏或区域

  end;

  TPerceivedElement = record

    Confidence: Double;

  end;

  IDesktopPerception = interface
    function CaptureScreen(const ARect: TRect): TDesktopScreenshot;
    function CaptureWindow(const AWindowLocator): TDesktopScreenshot;
    function Recognize(const AShot: TDesktopScreenshot): TArray<TPerceivedElement>;
  end;
```

### 4.4 行动层升级：统一执行器

```delphi
// 扩展 docs/34 的 TUIAElementLocator / TFallbackPolicy
type
  TActuationChannel = (acUIA, acVisual);  // 结构化通道 / 视觉坐标通道

  // 统一执行原语：应用层不感知底层走 UIA 还是视觉坐标
  IUnifiedActuator = interface
    function Click(const ATarget: TActuationTarget): TActuationResult;
    function InputText(const ATarget: TActuationTarget; const AText: string): TActuationResult;
    // TActuationTarget 可由 UIA locator 或感知层 BoundingBox 构造
  end;
```

`TFallbackPolicy.fpBestEffort` 的语义升级：UIA selector 失败 →
请求感知层对该区域截图识别 → 用 `TPerceivedElement.BoundingBox` 走
`acVisual` 通道兜底。`fpStrict` 仍只走 UIA，失败即抛（保持现有行为）。

## 5. 落地路线

| 优先级 | 模块 | 动作 | 信心 | 风险 |
|---|---|---|---|---|
| **P0** ✅ | 感知层 | 新建 `DeepBase.Desktop.Perception.*`（截图+OCR+视觉识别），输出直接喂 `LLM().ChatVision`。先内部模块、不冻结 API。 | 高 | OCR 模型体积大，须懒加载，不拖累不需要它的应用 |
| **P1** ✅ | 行动层 | 升级 UIA 引擎为 `TUnifiedActuator`，补视觉坐标兜底；UIA 原语行为回归测试。 | 高 | 回归测试须覆盖原 selector 行为不被破坏 |
| **P2** | 推理层 | **无动作**。仅在应用层文档中声明依赖 `DeepBaseLLM` + `DeepBaseInference`，示例调用 `LLM().ChatVision`。 | 高 | — |
| **P3** | 决策/Prompt | **不下沉**。应用层自有编排，复用 `PromptTemplateManager` 存业务 Prompt。 | 高 | 防止"框架暴政"——底座不替应用做决定 |

P0 完成即验证"感知→推理"半环可跑通（截图喂 ChatVision 返回结构化描述）；
P1 完成即闭环"感知→推理→行动"。P0/P1 之间无强耦合，可并行起步。

## 6. 纯度红线与门禁

1. **零业务语义**：下沉单元禁止出现微信/购买/对话/任务等业务词。PR 审查硬门。
2. **不强制启用 LLM**：行动层 `fpStrict` 路径与感知层纯采集路径不得强制要求 LLM 配置。
3. **懒加载**：OCR/视觉模型按需加载，`IsConfigured=false` 时感知层降级为"仅截图不识别"。
4. **API 稳定承诺**：P0/P1 阶段标注 `// Unstable API`，第 2 个真实消费者出现后冻结。
5. **Fire Worker 边界**：感知/行动层的机械迁移候选（如 UIA→统一执行器的方法搬运）
   可交 Flash Worker 写 staging，但接口契约与回归测试由主模型整合与验证。
6. **SPW 门禁**：涉及 `DeepBase.UIA.*` / 新建感知单元的改动，按 CLAUDE.md 要求
   补 DUnitX 回归测试；Delphi GUI 生产代码禁止裸 `Write`/`WriteLn`，走标准 Logger。
