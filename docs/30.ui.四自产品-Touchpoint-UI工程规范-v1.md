# 四自产品 × Touchpoint UI 工程规范 v1.0

> **文件编号**：30.ui (Four-Self Product & Touchpoint UI Engineering Specification)  
> **文档版本**：v1.0（2026-09-01 正式工程基线版）  
> **适用范围**：`DeepBase` 核心库及下游所有基于 HB 视觉基础设施构建的桌面与跨平台软件（`DeepDsh`、`Assayer`、`DeepRW`、`DeepCommerce 唤金`、`DeepSync` 等）  
> **设计哲学**：**理论 → 触点 → 状态转换 → 四自指标 → 数据回流 → 验收**  
> **核心定义**：**每一个界面元素都是潜在触点；每一个触点都必须有状态转换目标；每一次状态转换都必须可测量；每组测量都必须能够推动产品下一轮成长。软件不是承载营销的容器，软件本身就是营销发生的地方。**

---

## 一、四自验收总原则

传统 UI 规范往往只关注视觉样式（颜色、间距、字体）或页面级布局，容易导致“四自”（自营销、自承接、自成长、低客服）退化为宣传标签。

本规范确立的核心原则是：**验收标准是整套规范的核心组成部分，验收对象不是抽象的“页面”，而是具体可测量的“触点单元”（Touchpoint Unit）**。

任何新增功能、页面、菜单、按钮、卡片、向导节点，在研发与评审中都必须明确回答五个问题：

```
                    ┌──────────────────────────────────────────────┐
                    │       Touchpoint 触点单元五问准入模型        │
                    ├──────────────────────────────────────────────┤
                    │ 1. 它是不是触点？                            │
                    │ 2. 它触发用户什么状态变化 (Before → After)？ │
                    │ 3. 它服务四自中的哪一项？                    │
                    │ 4. 用户不依赖客服能不能独立完成？            │
                    │ 5. 数据能不能证明它真的有效？                │
                    └──────────────────────────────────────────────┘
```

> [!IMPORTANT]
> **红线原则**：验收不只验“有没有挂指标”，而要验**这个触点是否真的让用户更容易发现、理解、进入、完成和继续使用产品**。没有状态变化定义与零客服闭环路径的界面元素，不得宣告完成。

## 二、Touchpoint Unit 触点单元最低验收结构

每个触点单元在契约定义与工程实现中，至少必须具备以下结构化属性：

```yaml
# Touchpoint Unit 触点单元基础契约
touchpoint_id: "tp_waterfall_card_action_001"   # 全局唯一触点标识
surface_id: "surface_workspace_main"            # 所在界面/容器标识
component_type: "THbFacetWaterfall"             # 承载的 HB 控件类型

purpose: "引导用户推演多方案并进入下一步决策"    # 触点业务意图
trigger: "user_select_facet_or_expand"          # 触发条件

# 核心状态机 (没有状态变化定义，就不能算合格触点)
user_state_before: "UNCERTAIN_ABOUT_OPTIONS"    # 用户进入前状态
user_action: "EXPAND_DETAIL_AND_SELECT_CHOICE"  # 用户在触点上的行为
user_state_after: "DECISION_COMMITTED"          # 用户离开后状态

touchpoint_role: "DECISION_GUIDE"               # 触点角色

# 四自属性画像 (至少贡献一项)
self_marketing: true                            # 是否承担自营销价值发现
self_onboarding: true                           # 是否承担自承接向导分流
self_growth: true                               # 是否沉淀用户知识与偏好
low_service: true                               # 是否提供零客服自助恢复路径

# 动作与退出流
next_action: "EXECUTE_PIPELINE_STEP"            # 正向下一步动作
exit_action: "COLLAPSE_OR_NAVIGATE_BACK"        # 主动退出动作
fallback_action: "SHOW_DIAGNOSE_WIZARD"         # 兜底恢复动作

# 业务生命周期对齐
pfm_stage: "DELIBERATION"                       # PFM 阶段
cop_status: "ACTIVE"                            # COP 状态
rt6_stage: "STAGE_3_BRANCHING"                  # 运行态阶段

# 事件埋点与数据回流
event_name: "tp_waterfall_choice_selected"      # 触点主事件
success_event: "tp_step_succeeded"              # 成功流转事件
failure_event: "tp_step_aborted"                # 失败/放弃事件

support_fallback: "IN_APP_SELF_RECOVERY"        # 遇阻时的自助服务路径
```

## 三、四自维度详细验收标准

```
+---------------------------------------------------------------------------------------------------+
|                                      四自验收指标与闭环体系                                       |
+---------------------------------+---------------------------------+-------------------------------+
|         【A. 自营销验收】       |         【B. 自承接验收】       |       【C. 自成长验收】       |
| • 内部自然发现下一个价值        | • 显影/分流/无障碍推进          | • 持续使用沉淀可用价值        |
| • 拒绝弹窗轰炸，上下文相关      | • 拒绝“遇事找客服”              | • Learning Gain: LG > 0       |
| • 指标: discovery_rate          | • 指标: self_onboarding_rate    | • 指标: return_rate           |
|         self_transition_rate    |         self_resolution_rate    |         personalization_gain  |
+---------------------------------+---------------------------------+-------------------------------+
                                  |         【D. 低客服验收】       |
                                  | • 少客服 + 高成功率 (双向约束)  |
                                  | • 进度不丢失、历史可回溯        |
                                  | • 指标: support_deflection_rate |
                                  |         human_intervention_rate |
                                  +---------------------------------+
```

### 1. A. 自营销验收（Self-Marketing）
- **验收核心**：不是验“有没有挂推广内容”，而是验**用户是否能在产品内部自然发现下一个价值**。
- **必须满足**：
  - [ ] 每个核心功能至少存在一个自然的价值发现触点；
  - [ ] 触点与当前用户的上下文行为强相关（按需出现，非全局打扰）；
  - [ ] 严格禁止全屏阻断式弹窗轰炸；
  - [ ] 用户拥有完全的主动权进入或拒绝下一功能；
  - [ ] 触点提供明确的“下一步”；
  - [ ] 用户拒绝后能自然平滑退出，不反复骚扰；
  - [ ] 无需销售或人工客服解说，界面自身即能自明其价值。
- **数据验收指标**：
  - `discovery_rate`（价值发现率）
  - `self_initiated_transition_rate`（自发流转率）
  - `cross_feature_transition_rate`（跨功能流转率）
  - `touchpoint_exit_rate`（优雅退出率）
- **合格定义**：目标用户在没有客服、销售或外部广告介入的情况下，从当前功能自然发现并主动进入另一个具有明确业务价值的功能。

---

### 2. B. 自承接验收（Self-Onboarding · 四自最核心）
- **验收核心**：用户遇到困难或复杂任务时，界面必须具备**自解释与自引导**分流能力。
- **必须满足**：
  - 路径严格符合：`问题 → 显影 → 选择/判断 → 分流 → 下一步`；
  - 严禁出现“如果不知道怎么办，请联系客服”的甩锅式提示，优先采用“你现在可能属于 A/B/C，请选择最接近的情况”；
  - [ ] 用户在任意时刻均清晰知道“自己当前在哪里”；
  - [ ] 用户明确了解“当前正在解决什么”；
  - [ ] 用户明确知晓“下一步是什么”；
  - [ ] 复杂任务支持通过多层瀑布向导逐层显影；
  - [ ] `UNKNOWN`（不确定）状态允许停下来补充材料或暂存草稿；
  - [ ] `REFER` / `FREEZE` / `ESCALATE` 异常状态严格阻断强推，保护数据安全；
  - [ ] 用户可随时主动退出，且核心主干流程无需人工客服介入。
- **数据验收指标**：
  - `self_onboarding_rate`（自主上手率）
  - `self_resolution_rate`（自主解决问题率）
  - `completion_rate`（核心任务完成率）
  - `drop_off_rate`（中断跳出率）
  - `support_required_rate`（客服依赖率，越低越好）
- **合格定义**：初次使用该功能的目标用户，在没有任何人工解释指导的前提下，能够独立完成核心任务或获得清晰明确的下一步行动指引。

---

### 3. C. 自成长验收（Self-Growth）
- **验收核心**：不能以“单纯使用次数增加”充数，必须证明**系统因为用户的持续使用而产生了新的可用价值**。
- **必须满足**：
  - [ ] 系统能够安全、合规地记录用户操作反馈与有效结果；
  - [ ] 具备完备的回看机制（History / Snapshot / Diff）；
  - [ ] 第二次使用时可自动引用或复用第一次沉淀的有效模板或配置；
  - [ ] 产品能够根据历史结果自适应优化后续推荐路径；
  - [ ] 用户能够直观感知到自身的资产沉淀与效率提升；
  - [ ] 过去的错误路径与纠错记录可被系统学习并自动提示避坑；
  - [ ] 历史数据具备生命周期管理与数据治理边界，禁止无限制无限期盲目膨胀。
- **数据验收指标**：
  - `review_rate`（历史回看率）
  - `return_rate`（主动复用率）
  - `adaptation_rate`（自适应契合率）
  - `repeat_completion_improvement`（重复任务提效率）
  - `personalization_gain`（个性化增益）
- **关键计算模型 —— 学习增益（Learning Gain）**：
  $$\text{Learning Gain (LG)} = \text{第一次完成所需人工/解释成本} - \text{第二次完成同类任务所需人工/解释成本}$$
  - **合格标准**：长期追踪保持 $\text{LG} > 0$。

---

### 4. D. 低客服验收（Low-Service）
- **验收核心**：必须采用**“少客服 + 高成功率”的双向约束**，严禁追求虚假的客服量下降。
- **必须满足**：
  - [ ] 80% 以上高频常见问题在产品内具备全自动自助排障路径；
  - [ ] UI 能够精准识别并标记用户当前所处的具体步骤与上下文；
  - [ ] 发生错误时，不仅提示 Error 文本，更给出具体的恢复建议与下一步动作；
  - [ ] 用户退出向导后不会丢失已填写的内容（具备本地草稿暂存能力）；
  - [ ] 当确需客服介入时，客服端能直接看到用户前置完成的全部证据链，用户无需重复描述基础信息；
  - [ ] 客服处理的问题能够形成工单反哺回流至产品迭代。
- **数据验收指标**：
  - `self_service_resolution_rate`（自助排障成功率）
  - `human_intervention_rate`（人工介入率）
  - `repeat_question_rate`（同类问题重复咨询率）
  - `support_deflection_rate`（客服拦截化解率）
  - `unresolved_without_support_rate`（未解决且未联系客服的流失率，红线指标）
- **红线警示**：
  > [!CAUTION]
  > **“客服咨询量下降，但未完成任务流失率上升”直接判定为验收不合格！**

## 五、产品级五级工程准入门禁（G0 ~ G4）

任何功能或模块不得在完成编码后立即宣称“已实现四自闭环”，必须按顺序逐级爬坡验证：

```
     [G4：可改善] ──── 指标驱动迭代 (指标异常 → 分析根因 → UI微调 → 指标转好)
          ▲
     [G3：可验证] ──── 数据真实回流 (全量埋点入库、四自指标看板可信度量)
          ▲
     [G2：可承接] ──── 黑盒用户走通 (初次使用目标用户 0 解释独立跑通核心流)
          ▲
     [G1：可运行] ──── 事件闭环触发 (触点激活、流转、退出、失败事件正常发出)
          ▲
     [G0：存在]   ──── 静态契约冻结 (组件声明 FourSelfProfile 与状态转换)
```

| 门禁级别 | 门禁名称 | 准入硬性证据要求 | 授权状态 |
|---|---|---|---|
| **G0** | **契约存在 (Existence)** | 源码中完成触点结构化契约定义（含 `user_state_before/after`） | 🟡 允许合并至功能开发分支 |
| **G1** | **事件可运行 (Runnable)** | 自动化单元测试通过，触点事件能够正确触发与捕获 | 🔵 允许进入集成测试环境 |
| **G2** | **流程可承接 (Onboardable)** | 盲测目标用户在 0 客服指导下成功完成核心任务流程 | 🟣 允许进入灰度发布 |
| **G3** | **指标可验证 (Verifiable)** | 生产/灰度环境下真实采集到四自指标并完成基线测量 | 🟢 允许面向全部用户发布 |
| **G4** | **产品可改善 (Improvable)** | 形成“指标度量 → 发现断点 → 优化触点 → 指标提升”闭环 | 🏆 **正式获评“四自标杆功能”** |

## 六、终极黑盒盲测验收法（Four-Self Black Box Acceptance）

在代码走查与自动化测试通过后，产品最终验收必须进行**黑盒盲测（Black Box Usability Test）**：

### 1. 盲测执行规程
1. **测试对象**：邀请 3~5 位从未接触过该功能的新目标用户；
2. **隐藏实现**：不提供操作手册，不讲解背景理论，界面不显示内部状态码；
3. **下达任务**：仅给出业务目标（例如：“请在系统中完成一份供应商评估推演并导出确认卡”）；
4. **全程静默**：观察员在旁记录，**全程严格禁止进行任何口头提示或操作干预**。

### 2. 盲测记录与打分模型
```
首次进入 ──→ 是否知道当前位置 ──→ 是否识别出核心问题 ──→ 是否顺利找到下一步
   │                                                             │
   └── 是否需要人工求助 (是则扣分)                                └── 是否达成最终结果
                                                                 │
次度复用 ──→ 第二次完成同类任务 ──→ 时间与摩擦是否显著降低 (LG > 0) ──┘
```

- **四大评分维度**：
  - $\text{SM Score}$（自发现能力得分）：是否自发探索并理解价值；
  - $\text{SO Score}$（自承接能力得分）：是否在 0 解释下完成任务；
  - $\text{SG Score}$（自成长能力得分）：二次使用是否效率倍增；
  - $\text{LS Score}$（自助服务得分）：遇到歧义或错误时是否自助化解。

## 七、反四自 / 滥用防范验收（Anti-Growth Abuse Check）

严防为了迎合指标而采取短视的黑帽设计（Dark Patterns）。出现以下任意一种情况，**一票否决，直接判定验收失败**：

| 违规类型 | 违规表现与红线定义 | 判定结果 |
|---|---|:---:|
| ❌ **诱导型触点** | 用户未主动触发即反复弹窗、倒计时强推、强行阻断当前工作流 | **FAIL 🔴** |
| ❌ **假自营销** | 将普通商业广告伪装成系统关键通知或必备功能推荐 | **FAIL 🔴** |
| ❌ **假自承接** | 堆砌大量无实质内容的向导步骤，用户走完全程仍未解决核心问题 | **FAIL 🔴** |
| ❌ **假自成长** | 仅做表面的用户名替换，未实质沉淀用户知识、偏好与纠错模型 | **FAIL 🔴** |
| ❌ **假低客服** | 故意隐藏客服入口或提高联系门槛，导致客服量下降但用户流失 | **FAIL 🔴** |
| ❌ **指标游戏** | 诱导误触（如把拒绝按钮做成极小浅色、主按钮默认捆绑其他操作） | **FAIL 🔴** |
