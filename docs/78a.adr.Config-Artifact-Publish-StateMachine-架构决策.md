# ADR — 配置制品发布状态机与原子切换（Config-Artifact-Publish-StateMachine）

> 编号：78a.adr.Config-Artifact-Publish-StateMachine
> 日期：2026-08-10
> 状态：**开发已授权；受控实施基线 r1，服务端首版待差异复验**
> 关联设计：`78.backend.ConfigUploadChannel-PG上传通道协议与实施.md` §2/§3.3
> 冻结范围：发布状态机 / 幂等表 / release_heads+manifest 原子性 / DLL 制品 URL 引用 / 版本规则

---

## 1. 背景

DeepDomIn→PG 配置上传通道需要权威的发布链路（config 入库 → 打包 → manifest 原子切换 → Gateway 生效）。第二轮评审暴露：幂等表无建表定义、release_heads 与 manifest 更新原子性缺失、DLL 打包方式（实体 vs URL）互斥矛盾。本 ADR 统一收口。

## 2. 决策

### 2.1 发布状态机（provider_configs.status）

| 状态 | 含义 | 进入条件 | 迁出条件 |
|---|---|---|---|
| `draft` | 仅入库，不请求发布 | `publish=false` | 后续显式发布 → `building` |
| `building` | 唯一作业正在构建和验证制品 | `publish=true` 或显式发布 draft | 成功 → `published`；失败 → `failed` |
| `published` | 已完成制品验证；是否为当前版本由 release_heads 唯一决定 | 发布事务 B 提交 | 可标记 deprecated；历史行保留 |
| `failed` | 构建/签名/发布失败 | Worker 失败 | 修复后以受控重试进入 building |
| `deprecated` | 历史下线标记 | 人工或策略操作 | — |

`publish=false` 时 `zip_pending=false`，不得自动打包。`publish=true` 时为 `building/true`。

### 2.2 publish 两步事务与并发串行化

- 事务 A：校验幂等键和 `(provider_key, version)`；写 config、审计及唯一 artifact job。
- Worker 使用唯一 job lease、`FOR UPDATE SKIP LOCKED` 或等价机制，确保同一 config 不被重复并发构建。
- 制品完成后先验证对象可读、JCS、哈希、签名和目标元数据。
- 事务 B 必须锁定 provider 发布头及 manifest 行；首发使用 advisory lock 或等价唯一串行化；校验 expected generation/version，禁止并发降级；同一事务内切换 release head、manifest generation、目标状态和 zip_pending。
- 当前版本只能由 `provider_release_heads` 决定；禁止通过多行 `status='published'` 推断当前版本。
- 构建失败不改变 release head/manifest，Gateway 继续使用 LKG。

### 2.3 幂等表 api_idempotency

```sql
CREATE TABLE IF NOT EXISTS api_idempotency (
  api_key_id      BIGINT NOT NULL,          -- 引用服务间 API key 表（65.Commerce 契约）
  idempotency_key UUID NOT NULL,
  request_sha256  TEXT NOT NULL,            -- 服务端对收到的规范化请求体计算（客户端不参与，防篡改）
  response_status INTEGER NOT NULL,
  response_body   JSONB NOT NULL,           -- 原始响应，重放原样返回
  created_at      TIMESTAMPTZ NOT NULL DEFAULT now(),
  PRIMARY KEY (api_key_id, idempotency_key)
);
```

- 相同 key + 相同 request_sha256 → 返回首次响应（HTTP 200 + `"idempotent": true`）；
- 相同 key + 不同 request_sha256 → 409 `IDEMPOTENCY_KEY_REUSED`；
- 72h 过期行由每日核对任务统一清理（与 §2.5 同一任务）；
- `request_sha256` **由服务端计算**（对收到的规范化请求体），客户端不参与——防客户端篡改。

### 2.4 DLL 制品：URL 引用方案（不内嵌实体）

- config zip **不包含 DLL 实体**；zip 内 `plugin_manifest.json` 记录每个 DLL 的 `plugin_name`、制品仓库 **URL**、sha256、Ed25519 签名、`dll_version`、`compatible_config_version_range`；
- 决策依据：DLL 生命周期独立（单独更新/回滚/删除）优先于"一步下载"的便捷；zip 保持轻量，config 与 DLL 解耦；
- **Gateway 校验顺序**：下载 zip → 校验整体 Ed25519 签名 → 解压 → 校验 config sha256（与 provider_configs 表比对）→ 按 URL 从制品仓库下载 DLL → 校验 DLL sha256 与签名 → 触发热重载；
- **制品仓库不可用降级**：保留本地旧版 DLL 继续运行 + 告警；禁止回退到无签名 DLL、禁止跳过校验；
- 单独更新 DLL：先传制品仓库（新 sha256/签名）→ 以新 config version 重新上传 config（config_json 不变，plugin_manifest.json 引用更新，`dll_version` 递增）→ 触发重新打包；
- DLL 上传端点 `POST /dk/plugins/upload`（二进制 + Ed25519 签名验证）与 config 端点隔离；制品仓库独立于 config storage。

### 2.5 版本与一致性规则

- `version` 为日期版本号 `YYYY.MM.DD(.N)`，**服务端按整数段比较**（2026.08.10.9 < 2026.08.10.10），禁止字符串比较；
- 禁止覆盖已发布版本；回滚 = 以新 version 重新上传旧 config_json 内容；
- `id BIGSERIAL` 已作为单调 revision；不再建立引用 id 的生成列；业务版本仍按整数段比较；
- 每日核对任务（与幂等清理同任务）：扫描 manifest 缺失 / zip_pending 超 30 分钟 / 幂等表超 72h 行，自动重试或告警。

### 2.6 包格式归口

zip 包格式（目录结构、签名规则、plugin_manifest.json schema）**归口 77 号文档 S0 定义**，本协议（78）严格按其规范打包与校验——两文档的 S4/C4 依赖以"77 S0 包格式规范 + 78 制品仓库就绪"为共同前置，不再互相引用形成循环。


### 2.7 签名信任根与防回滚

- Manifest 和 plugin_manifest 使用 RFC 8785 JCS 后 Ed25519 签名。
- 公钥信任根随可信安装交付，或由已信任旧密钥签署 keyset 更新；禁止未验证 Manifest 自带公钥完成自证。
- 私钥托管于 KMS/HSM/受控签名服务，具备审批、审计、轮换和吊销。
- 客户端持久化最高 generation；除独立签名且有审计的 rollback token 外，拒绝 generation 降低。
- 下载 URL 必须 HTTPS；正式部署应支持域名白名单和短期签名 URL。签名失败或制品缺失时使用 LKG。

## 3. 被拒绝的备选方案

| 方案 | 拒绝理由 |
|------|---------|
| publish 单事务内同步打包 | 打包耗时长（zip 生成 + 签名），同步事务锁行时间不可接受；状态机才能支持异步化与失败重试 |
| 打包失败自动回滚 provider_configs | 已入库成果是审计事实，回滚会丢失失败现场；状态机 FAILED + 告警更可观测 |
| DLL 实体打进 zip | 与制品仓库独立生命周期目标冲突：DLL 更新被迫重新发布 config；zip 体积膨胀 |
| 幂等 key 单独唯一（不绑 API key） | 不同租户可互相重放/冲突；(api_key_id, key) 复合唯一是标准做法 |
| request_sha256 由客户端计算上报 | 客户端可伪造/篡改，服务端重算比对才可信 |

## 4. 实施与验收要点

- 服务端（王维）：§2.1/§2.2/§2.3 建表 + 状态机 + 每日核对任务；客户端（本仓库）：TConfigUploader + JCS 对齐 + 幂等重放测试；
- 验收硬条件：正式 migration 可 apply/rollback；同一 config 双端 JCS 哈希相等；同 key 重放不重复；不同请求复用 key 返回 409；两个并发发布只有一个 generation 成功；publish=false 不产生打包任务；签名失败、generation 降低和构建失败均保持 LKG。
