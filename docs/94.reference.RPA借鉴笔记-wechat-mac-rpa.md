## 0. 定位

本笔记记录对 macOS 微信客户端外部 UI 自动化参考项目 `wechat-mac-rpa` 的
技术调研结论，对照 deepaxis（基于 DeepBase 的微信 RPA 应用）已落地的
"感知层(截图+视觉识别+LLM provider) + UIA 统一行动器(strict/best-effort 双通道)"，
提炼可借鉴与应规避项，作为后续迭代选型依据。**非生产代码规格**，不直接驱动实现。

---

## 1. 参考项目本质

它是**视觉坐标流 RPA 的完整参考实现**：截图 → macOS Vision OCR → numpy 布局分析
（绿色气泡/红色未读角标颜色匹配 + 连通区域标记）→ LLM 语义理解 → AppleScript/cliclick
坐标点击。**全程不用 macOS Accessibility API 做元素定位**（仅取窗口几何）。

五层认知循环架构：
```
L1 Capture → L2 OCR → L3 Layout/Extract → L3.5 Pipeline → L4 Action → L5 Bot
```

感知管道三模可切：`VisionPipeline`(纯OCR) / `SmartPerceptionPipeline`(智能路由) /
`WeFlowPipeline`(数据库增量)。

## 2. 值得借鉴（按 ROI 排序）

### P0｜帧间变化检测（MD5 + ROI 像素 diff）

`SmartPerceptionPipeline` 两级跳过：
1. 全图 MD5 相同 → 直接复用上次结果，跳过一切后续。
2. MD5 不同 → 对消息区 ROI / 聊天列表区 ROI 做像素 diff
   (`np.abs(curr-prev)`，阈值>10 视为有变化)，差异<0.1% → 跳过 LLM 只做本地 OCR。
3. 稳定模式：连续 3 帧低差异 → 阈值再降 50%。

**价值**：直接砍 60-90% LLM API 成本。

**deepaxis 落点**：`TVisualRecognitionEngine` 当前是线性"每次截图→识别→LLM"，
缺这一层心跳优化。Delphi 实现用 `TBitmap.ScanLine` 做 ROI 像素 diff 很轻，
配合 `TPerceptionCache`（已有 label→element 缓存）做"帧未变即复用"。

> **落地状态（2026-07-22）**：已实现双 L0 闸门。`TFrameDiffer`（像素级，
> encode 前，`feat/wyjx-colormatch-canary` `a8c2ada`）+ `TPerceptionCache`
> （MD5 级，provider 前，`3915ce1`）。阈值标定协议见 §7；`0.4%` 为占位默认值，
> 待 §7.3 真机扫描后回填实测值。

### P1｜纯像素检测补 UIA 盲区

它用颜色匹配+连通区域标记识别"哪些气泡是我发的"和"未读角标数"。
这是 **Accessibility 给不了的信息**——气泡归属/未读数不在 UIA 树里。

**deepaxis 落点**：`TUnifiedActuator` 的 `acVisual` 通道目前是 UIA 失败的坐标兜底，
可扩展为"UIA 拿不到的视觉语义"补充信号源（气泡归属、未读计数、状态指示色）。
对应 `TPerceptionSource.psVision`（已定义但未充分使用）。

### P1｜登录恢复状态机

四状态：SUCCESS / NEEDS_PHONE_CONFIRM / NEEDS_QRCODE / NO_LOGIN_BUTTON，
自动检测+尝试恢复。7×24 无人值守必备。

**deepaxis 落点**：应用层（DeepAxis）职责，不属底座。但底座感知层可暴露
"登录态特征检测"原语供应用层编排。

### P2｜截图内容验证

截图后先 OCR/特征校验"确实是目标窗口"，防被覆盖窗口截错。

**deepaxis 落点**：`TDesktopScreenshot` 采集后加一步特征验证
（UIA 树校验或 OCR 关键词），防感知层看错窗口。

### P2｜WeFlow 双模渐进增强

默认零侵入（纯截图 OCR），可选数据库增量同步，切换通过环境变量，hybrid 失败自动降级。

**deepaxis 落点**：可设计类似双模——默认纯视觉感知，可选 hook 本地数据库
做增量同步，失败自动降级。属应用层策略，底座只提供原语。

## 4. 反面教材（明确规避）

| 项 | 它的做法 | deepaxis 规避 |
|---|---|---|
| 硬编码坐标 | 输入框 X/Y 写死 | UIA 行动器语义定位，不依赖坐标 |

| 超时策略不统一 | AppleScript 5s / cliclick 5s / API 30s 各异 | 统一 `IActionExecutor` 超时+重试配置 |
| 颜色值硬编码 | `self_green` RGB 写死 | 运行时采样或 UIA 取控件样式属性 |

## 5. 一句话结论

它是视觉坐标流 RPA 的完整参考实现，工程成熟度低于 deepaxis（无 UIA、无反检测、
硬编码遍野），但 **P0 帧间变化检测** 和 **P1 纯像素补 UIA 盲区** 两点有真实价值——
前者直接降 LLM 成本，后者补 Accessibility 盲区。P0 变化检测已落地为双 L0 闸门
（`TFrameDiffer` 像素级 + `TPerceptionCache` MD5 级，见 §7 标定协议与 `feat/wyjx-colormatch-canary` 的 `3915ce1`/`a8c2ada`）。

### 6.1 LayoutParser 算法 —— 可直接移植的「OCR→语义结构」管线

这是 deepaxis 感知层缺的 L1「布局解析」层，算法清晰、平台无关、可移植：

```
OCR 元素列表 [(text, bbox)]
    │
    ├─ 按 left_boundary 分左右两区（左=聊天列表, 右=消息区）
    ├─ title 区 (y<title_y_max) → 聊天名
    ├─ input 区 (y>input_y_min) → 输入框内容（须排除，防草稿污染）
    ├─ timestamp 元素（正则匹配 HH:MM/昨天/星期X/YYYY/MM/DD）→ 时间分隔
    └─ 消息区剩余元素 → 按绿色像素聚类成气泡（self_bubbles）
            → 每个气泡按 y 排序、x 对齐一致性校验 → ChatMessage
```

**关键设计**：
1. **LayoutParser 只分组不过滤**——语义过滤交给下游 MessageExtractor。
   分层单一职责（对应 docs/87 §1.1 单一职责原则）。
2. **LayoutProfile 是配置真相源**：`left_boundary` / `title_y_max` /
   `input_y_min` / `self_green` / `message_cluster_threshold` 全在 Profile，
   代码零硬编码（对应 §6.4 红线1）。
3. **窗口尺寸动态 scale**：`title_y_max` 等不随窗口高度线性缩放（经验值），
   但 `left_boundary` 类按比例。Profile 用绝对值 + ratio 混合。

**deepaxis 落点** → P2-004 canary `TLayoutParser`：
- 输入 `TArray<TOcrElement>`（text+bbox），输出 `TUILayout`（分区+气泡）
- 零业务语义：分区用中性名 `left_region/right_region`，不出现"微信/聊天列表"
- `left_boundary` 等从 `TPerceptionProfile` 读，不硬编码

### 6.2 绿色气泡判 sender —— ColorMatch 的生产用法范例（已验证可落地）

`MessageExtractor` 判 SELF 消息的核心：
```python
self_green = (176, 240, 167)      # 微信自己发的气泡绿
self_green_tolerance = 35         # 容差
min_bubble_pixels = 1000          # 绿色连通区域最小像素数，防噪声误判
```
判定：在气泡 bbox 内做颜色匹配（RGB 分量差 ≤ tolerance），
连通区域像素数 ≥ min_bubble_pixels → 认定为 SELF 气泡。

**这正是 deepaxis ColorMatch canary 落地的能力**：
`TColorMatcher.FindColorTol` + `MatchPointsTol` 已实现「容差颜色匹配」，
17 测试通过。wechat-rpa 的用法证明这套原语的**生产形态**是
「颜色匹配 + 连通区域像素计数」——后者（连通区域）deepaxis 尚未实现。

**deepaxis 落点** → P2-006 增强方向：`TColorMatcher` 补
`CountConnectedPixels(ARect, AColor, ATol): Integer`，支持「最小像素数」判据，
从单点/多点匹配升级到「区域级颜色块识别」。这是 ColorMatch canary 的直接下一步。

### 6.3 MessageExtractor 的 sender 防错 —— 启发验证层

四条防错规则值得移植为 deepaxis 的「验证探针」：

| 规则 | wechat-rpa 做法 | deepaxis 对应 |
|---|---|---|
| 群聊判定单一来源 | `is_group` 只在 chat_utils 算一次，下游不重判 | 感知结果携带权威 flag，下游不得覆盖 |
| 私聊 sender=chat_name | 非 OTHER 类才用昵称 | 感知层归一化职责边界 |
| 群聊 sender 防误聚 | `sender==text and len>3` → 用上条左对齐 sender | 多模态提取的二次校验 |
| 输入框内容排除 | prompt 明确排除底部输入框 | 截图 ROI 裁剪（配合 P0 帧间检测的 ROI） |

### 6.4 Memory 归一化哲学 —— 「判断用归一化，显示用原名」

`memory/engine.py` 的 `normalize_chat_name`：
- 去 emoji + 折叠空白，但**只用于判断重复和路径计算，不改显示名**。

**deepaxis 落点**：感知层若做多来源元素去重（UIA + 视觉 + OCR 同一控件），
应遵循同哲学——`NormalizeForDedup()` 仅用于 key，`DisplayName` 保留原值。
比 wechat-rpa 的硬编码昵称词典（§4 反面教材）更通用。

### 6.5 CODING_PRINCIPLES 三红线 —— 直接强化 docs/87 §6 门禁

wechat-rpa 自述的三条开发红线，与 SPW 纪律高度共鸣，应纳入 deepaxis 感知层门禁：

**红线1：阈值必须有出处**
- 禁魔法数字。`red_pixels >= 50` ❌ → `>= profile.badge_min_pixels` ✅
- 硬编码须注释数据来源 + 校准 TODO
- **改 Profile 阈值须同步 grep docs/ 旧值**（防归档变考古层）

→ deepaxis 落点：`TPerceptionProfile`（P2-003 canary）的所有阈值须有出处注释，
SPW H4 扫描器可加「无注释魔法数字」检查。

**红线2：拒绝列表式补丁**
- `THINKING_PREFIXES = ["等等，","让我想想",...]` ❌（会无限增长）
- 向上游走一步：用 API 参数让模型不输出，而非事后过滤

→ deepaxis 落点：感知层若发现要维护「OCR 噪声词典」，停下来问是治本还是治标。
对应 docs/87 §4.2「感知层不写业务 Prompt」——把噪声治理放在上游（ROI 掩码）而非下游（正则清洗）。

**红线3：测试是探针不是遮瑕膏**
- 严禁在测试里 mock 修正掩盖产品缺陷

→ deepaxis 落点：ColorMatch canary 的 17 测试须保持「探针」性质，
发现的产品缺陷要修产品而非改测试预期值。

### 6.6 ACTION_SPEC 验证闭环 —— 强化 docs/34 UIA 规格的回读

wechat-rpa 发消息的 verify 闭环（§3）暴露一个 deepaxis `TUnifiedActuator` 的缺口：
- 现状 `InputText` 仅 SendInput 逐字符，**无回读验证**
- wechat-rpa: 粘贴后 `Cmd+A+C + pbpaste` 读回比对，不匹配重试 5 次（3 常规 + 2 fallback）
- 关键修复：**verify 前必须清空剪贴板**，否则读到旧残留 → 假成功

→ deepaxis 落点 → P2-006 canary `VerifyInput` 回读：
- 作为 `fpBestEffort` 通道的可选加强（fpStrict 不加，保持 fail-fast）
- Windows 回读：UIA 取控件 Text 属性 / `GetGUITextInfo`，非剪贴板
- fail-closed 重试，符合 docs/87 §4.4 双通道语义

### 6.7 REACT_SELF_REFINE —— reasoning_content 透传陷阱

## 7. 阈值标定协议（TFrameDiffer）

`TFrameDiffer.ChangeRatio` 的默认阈值 `0.4%` 是**占位默认值**，仅作为标定起点，
在 §7 协议产出实测数之前不得视为最终值。本节定义标定方法，实测数填入后回填。

**落地状态（`feat/wyjx-colormatch-canary`）**：B 步真机执行端已就绪——
`Tools/Calibration/Calib.Record.dpr`（录制三类样本到 `<root>/{static,changed,boundary}/<seq>/*.png`）
与 `Calib.Sweep.dpr`/`Calib.SweepLib.pas`（sweep 候选阈值 → 选定 → 印 §6.3 markdown 表，可用 `--md <f>` 落盘 UTF-8）
已通过 Win64 路径编译并经**合成位图**端到端验证（static 100% skip / changed 0% 误静默 / 选阈链路通）。
合成图**仅证明 harness 通道正确，非真机标定**（§6.2 明令不使用合成位图）；下表仍为 TBD，
待真机按 §6.3 录 ≥30 段序列后 `Calib.Sweep.exe <root> --md <f>` 产出 UTF-8 表回填。

### 7.1 指标

主指标：**LLM 调用削减率** = `1 - (有闸门时 vision provider 调用次数 / 无闸门时调用次数)`。
目标带：≥ 90%（与 §2 P0 的 "60-90% LLM API 成本削减" 上限对齐，deepaxis 目标取上限）。
次指标：**误静默率** = 静止判定但实际有内容变化的比例（= 漏检 / 总静止判定），
目标 ≤ 1%（漏检一次会丢消息，代价高于多调一次 LLM，故容忍带宽于主指标）。

### 7.2 样本集

- **静态样本**：DeepAxis 待机场景连续 N 帧屏幕（≥3 帧低差异序列，覆盖光标闪烁/时钟刷新/
  输入框光标闪烁等亚像素抖动）。用于测主指标——这些帧应被判静止、跳过 encode+provider。
- **变化样本**：真实消息收发场景连续���（新消息气泡出现/未读角标变化/滚动），用于测
  次指标——这些帧必须被判变化、触发 encode+provider。
- **边界样本**：渐变色/半透明气泡淡入/动画过渡帧，用于扫描阈值灵敏度曲线。
- 样本须来自真实 DeepAxis 运行，不使用合成位图（合成图无法反映亚像素抖动）。

### 7.4 设计约束（非标定可改）

- 阈值是**每帧每通道归一化平均绝对差**（`Σ|Δ|/(cells×3×255)`），不是像素级硬阈值；
  块均值采样（stride=4）已平滑亚像素抖动，故阈值数值偏小（千分位）。
