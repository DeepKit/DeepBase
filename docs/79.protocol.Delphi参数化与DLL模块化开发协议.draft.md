## 1. 目标与总体结论

本协议建立一套可远程参数化、可模块扩展、可恢复、可审计、可渐进交付的 Delphi 软件平台规范。

当前推荐方案不声称“绝对最优”，而定义为：

> **在现有 Delphi/Windows 技术栈、既有 DeepBase/DeepCompare 资产、团队交付速度和安全约束下的 Pareto 推荐基线。**

该基线选择：

- **组合 α（稳健增量）作为近期强制基线**；
- **组合 β（能力协商、双实例）作为实验性能力包**；
- **组合 γ（服务化更新、进程隔离）按长期后台进程场景启用**。

出现以下情况时必须复评：

1. 新增第三方或不可信插件；
2. Delphi/RTL/编译器大版本变化；
3. 产品由桌面交互进程转为长期后台服务；
4. 单次故障影响超过一个发布环；
5. 兼容关系或插件数量增长到人工维护不可控；
6. 安全、恢复、交付速度或维护成本任一维显著恶化。

## 2. 规范词

- **必须**：违反即不得进入对应交付等级。
- **应当**：默认执行；偏离须记录理由、责任人和替代控制。
- **可以**：按产品需求启用。
- **禁止**：任何交付等级均不得采用。

## 3. 变更承载层级

产品必须按以下顺序选择最低充分能力层：

1. 类型化参数与 Feature Flag；
2. 声明式规则；
3. 受限 DSL；
4. 签名、沙箱化的 JavaScript 适配器；
5. 可信任的进程内 Delphi DLL；
6. 高风险、不可信或无法证明可卸载模块的进程外 PluginHost；
7. 主 EXE 或安装包更新。

能由低层完整且安全表达的变更，禁止无理由升级到高层。升级层级时必须提供：

- 机器可读的 `escalation_reason`；
- 一句人类可读的“低层为何无法满足”；
- 新增权限、风险等级、验证与回滚证据。

## 4. 稳定主 EXE 的最低责任

“薄壳”只表示业务能力可扩展，不表示移除生存、安全与监督内核。主 EXE 必须保留：

- 身份认证与授权；
- 制品签名、哈希、版本、目标与防回滚验证；
- Last Known Good（LKG）缓存；
- 日志、审计和必要遥测；
- 插件生命周期监督；
- 故障恢复、安全模式��Kill Switch 与 Circuit Breaker；
- 更新条幅、用户选择和状态展示；
- 核心数据完整性；
- UpdateAgent 的可信启动与结果复核。

## 5. FastAPI / PostgreSQL 参数控制面

- 客户端必须通过 FastAPI 获取参数与 Feature Flag，**禁止客户端直连 PostgreSQL**。
- 服务端 PostgreSQL 是权威持久层；FastAPI 是唯一受控业务接口。
- 参数必须类型化，并包含 schema/version、默认值、作用域、发布时间、过期时间、兼容范围及回滚目标。
- 客户端必须维护 LKG；服务不可用、超时或响应无效时继续使用已验证本地版本。
- 客户端状态至少区分 `READY`、`STALE`、`ERROR`、`PENDING_RESTART`。
- 网络失败不得被解释为参数关闭。
- 敏感值不得作为普通参数明文分发；密钥必须使用受控凭据通道。
- FastAPI 控制面必须支持 ETag/版本条件、幂等发布、审计和限流。

## 6. 浏览器规则、DSL 与受控 JavaScript

优先使用声明式规则和受限 DSL。JavaScript 仅在前两者无法表达时使用，并作为独立代码制品治理。

`browser_adapter_js` 必须包含：

- 独立签名、哈希、版本、过期时间；
- 固定入口与能力声明；
- 允许域名和显式权限；
- CPU、内存、执行时间和调用次数限制；
- 静态扫描和适配测试证据；
- 本地及远程 Kill Switch、Circuit Breaker；
- LKG 回滚与实际执行版本审计。

默认禁止访问文件、注册表、进程、COM、Delphi RTTI；默认禁止网络，确需网络时使用最小白名单。

**禁止下载任意文本后直接执行。**

## 7. 插件能力级与风险级

插件采用两个独立维度：

### 7.1 Capability Level

| 等级 | 能力 |
|---|---|
| C0 | 仅参数/只读查询 |
| C1 | 声明式动作或受限 DSL |
| C2 | 受控 JS 或无状态 DLL 调用 |
| C3 | 有状态 DLL、回调、线程或窗口 |
| C4 | 进程外服务、系统级或高权限能力 |

### 7.2 Risk Level

风险根据权限、数据敏感度、调用频率、失败影响、可恢复性和第三方来源评估为 R0-R4。

- C0-C2 且 R0-R1：可在主进程内运行；
- C2-C3 且 R2：必须通过热重载认证与灰度；
- C3-C4 或 R3-R4：应当进入 PluginHost；
- 不可信第三方代码默认不得进入主进程。

风险等级决定审批、隔离、测试、发布环和遥测强度；高频不自动等于低风险，低频不自动等于高风险。

## 8. Delphi DLL ABI 与所有权

- 产品线稳定插件 ABI 必须使用纯 C 数据面；经批准的 Delphi 同编译器接口只能作为实验适配层，不得作为 Preview/GA 冻结 ABI。
- Manifest 必须声明 ABI MAJOR/MINOR、宿主最低版本、CPU 架构、编译器/RTL 约束和 capability 集合。
- 跨边界禁止 Delphi interface、string、TBytes、动态数组、对象、Variant 和异常；使用不透明句柄、固定宽度整数、PByte+Length+Capacity、显式错误码，或由同一 DLL 导出的 FreeBuffer。
- 禁止跨 DLL 边界传递所有权不明的 Delphi 管理类型。
- 插件必须声明线程、窗口、回调、数据库连接、COM 对象及外部句柄生命周期。
- 依赖必须显式声明；禁止循环依赖和隐式加载未声明模块。
- MAJOR 不兼容必须拒绝加载；MINOR/capability 不满足时必须选择兼容版本、LKG 或安全模式，不得带病运行。

## 9. 热重载资格与 Lease

热重载不是默认权利，而是经认证后授予的能力。插件须通过卸载、资源清理、并发、崩溃隔离和循环重载测试，方可声明：

```json
{
  "hot_reload": "verified",
  "restart_fallback": true,
  "unload_timeout_ms": 10000
}
```

如果线程、窗口、回调、对象、内存、连接或句柄仍未释放：

- 禁止强制 `FreeLibrary`；
- 必须保留 DLL 并记录原因；
- 新请求停止进入旧实例；
- 更新进入 `PENDING_RESTART`；
- 下次真实退出后由 UpdateAgent 完成替换。

双实例 active/staged 与 capability 协商可先以实验性能力提供，不作为近期 Preview 的强制门槛；通过真实产品实验后再升级为基线。

## 10. 运行模式感知

Manifest 必须声明运行模式：

- `desktop_interactive`：可等待用户退出或由用户选择“退出并更新”；
- `background_long_running`：必须定义维护窗口或最大 pending 时长；
- `server_process`：必须使用计划重启、双实例切换或进程外承载，不得无限等待“下次用户重启”。

## 11. 进程外 PluginHost

高风险、第三方、不稳定、需要强权限隔离或无法证明可卸载的模块应当放入 PluginHost。PluginHost 必须具备：

- 超时与调用取消；
- 崩溃隔离与自动拉起上限；
- CPU、内存、句柄和并发配额；
- 权限 profile 与最小权限；
- 健康检查、Circuit Breaker、Kill Switch；
- 版本、请求和结果审计。

PluginHost 可采用按风险/权限 profile 分池，不要求每个插件永久独占一个进程。

## 12. 独立 UpdateAgent

文件替换必须由主进程之外的独立更新器执行：

1. 下载到 staging；
2. 校验签名、哈希、版本、目标和防回滚元数据；
3. 写入 pending-update；
4. 用可关闭条幅告知用户；
5. 用户选择立即更新时，主界面可以隐藏，但主进程必须释放资源并真实退出；
6. UpdateAgent 等待目标进程完全退出；
7. 原子切换双槽版本目录或替换文件；
8. 使用 `--after-update` 启动新版本；
9. 执行健康检查；
10. 失败时回滚 LKG 并启动旧版本。

软件可以在用户退出时自动重启一次完成更新，但禁止假退出、隐藏后继续秘密正常运行。

## 13. 统一 Artifact Manifest

参数、规则、DSL、JS、DLL、PluginHost 和 EXE 应使用统一 Manifest，至少包含：

- artifact_id、artifact_type、version；
- schema_version、ABI 及 capability；
- target_product、target_arch、运行模式；
- 依赖和有界兼容范围；
- 权限及风险等级；
- sha256、signature、signing_key_id；
- issued_at、expires_at；
- rollout_ring、rollback_target、LKG；
- hot_reload、restart_fallback；
- delivery_tier、tier_evidence_url；
- escalation_reason；
- 构建来源、commit/hash 和审计引用。
- JCS 规范化方式、签名算法、key_id 与信任链；
- generation、防回滚状态与独立 rollback token 约束。

Manifest 的信任根必须来自可信安装或已信任旧密钥签署的 keyset，禁止由同一未验证 Manifest 自证；私钥必须在 KMS/HSM/受控签名服务中管理，不得进入客户端或普通数据库。

兼容规则的维护责任归制品发布者；宿主维护支持能力集合。过期制品必须在保留期后清理，但至少保留当前版本与一个 LKG。无法满足兼容约束时按以下顺序降级：兼容候选版本 → LKG → 安全模式 → 禁用模块并告警。

## 14. 发布环和故障控制

发布必须支持：

```text
Shadow → Internal Canary → Pilot Ring → Expanded Ring → GA
```

- 新制品禁止一次性推送全部终端；
- 每环必须具备错误率、崩溃率、回滚率、pending 时长和版本分布观测；
- 越过阈值必须自动停止扩圈，并允许一键 Kill Switch；
- 桌面提示必须同时提供用户文案和开发者诊断信息。

## 15. 交付等级与量化门槛

### 15.1 Preview

必须满足：

- 契约和核心单元可编译；
- 单元/动态测试全部通过；
- 已知限制和兼容范围书面化；
- 有示例、接入说明和本地回滚方法；
- 不承诺生产稳定性，允许兼容性调整。

### 15.2 Pilot

在 Preview 基础上必须满足：

- 至少一个真实下游完成接入；
- 真实或等价测试环境完成签名、下载、安装/加载、故障恢复和 LKG 演练；
- Canary 可停止、可回滚；
- 关键遥测和审计可查；
- 连续运行窗口内无未解释的严重故障。

### 15.3 GA

在 Pilot 基础上必须满足：

- 服务端、客户端、制品、更新器、安全与运维全链路闭环；
- 生产 FastAPI commit/hash、PG migration、部署记录和 API 契约可核验；
- 生产凭据通过受控渠道交接并完成轮换演练；
- E2E 覆盖幂等、并发发布冲突、publish=false、签名失败、信任根轮换、过期、断网、防回滚、Kill Switch、pending/restart；
- CI/CD 构建完整性、签名密钥托管和轮换有审计证据；
- 兼容策略冻结并有弃用窗口；
- 至少一次灾难恢复和 LKG 回滚演练通过。

任何单元测试、mock E2E 或动态测试均不得单独被表述为 GA。
