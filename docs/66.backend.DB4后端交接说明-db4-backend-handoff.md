## 1. 目标

这份文档定义 deepBase 桌面软件上线后的服务器端实现边界。

你负责的不是桌面端代码，而是 `DB4 生产后端`。该后端要解决以下问题：

1. 用户认证
2. 设备会话管理
3. 商品/订单/支付
4. 权益发放与校验
5. 桌面端离线授权快照签发
6. 按权益控制更新通道

现有 deepBase 客户端已经有后端对接抽象，服务器端必须按既定契约实现，不能让桌面端直连生产数据库。

---

## 2. 总体架构

```text
deepBase 桌面端
    |
    | HTTPS JSON API
    v
DB4 业务后端服务
    |
    +-- PostgreSQL: deepKit
    +-- 微信支付 / 支付宝 / Stripe / PayPal
    +-- COS: 安装包 / 更新清单 / 补丁包
```

原则：

- 桌面端不直连 `DB4`
- `DB4` 是后端真相源
- 本地 `License` 只是缓存，不是收费真相源
- 支付结果以服务端验签回调为准
- 权益 `entitlement` 是最终可用性依据

服务端生产数据库使用 PostgreSQL，数据库名要求为：


注意：

建议执行：

```sql

  WITH
  ENCODING = 'UTF8'
  TEMPLATE template0;
```

## 6. 服务端必须提供的 API

> 2026-05-08 确认：当前服务器实际挂载前缀为 `/dk`。本节标题中未写前缀的路径均为逻辑路径，生产调用时统一加 `/dk`，例如 `/auth/login` 的实际路径是 `/dk/auth/login`。

## 6.1 认证 API

### `POST /auth/login`

用途：

- 登录
- 首次创建设备会话
- 返回 access token / refresh token

支持的登录方式建议至少有：

- 邮箱 + 密码
- 手机号 + 验证码
- 微信身份登录
- 设备匿名登录后再升级绑定账号

响应至少包含：

```json
{
  "user_id": "usr_xxx",
  "access_token": "jwt_or_other_token",
  "refresh_token": "refresh_token_xxx",
  "expires_in": 7200
}
```

### `POST /auth/refresh`

用途：

- 刷新 access token

### `POST /auth/logout`

用途：

- 注销当前 refresh token 或设备会话

### `GET /auth/me`

用途：

- 返回当前用户信息
- 返回当前有效权益摘要

---

## 6.2 收费 API

### `POST /commerce/users/ensure`

用途：

- 按第三方身份查找或创建平台用户

### `POST /commerce/orders`

用途：

- 创建订单
- 价格以服务端 `products` 表为准

### `POST /commerce/payments/intents`

用途：

- 生成支付意图
- 返回客户端支付参数

### `POST /commerce/payments/wechat_pay/notify`

用途：

- 微信支付回调
- 必须服务端验签
- 验签成功后再更新订单/支付/权益

### `POST /commerce/payments/alipay/notify`

用途：

- 支付宝回调

### `GET /commerce/entitlements`

用途：

- 返回用户在指定 `app_id` 下的权益

---

## 6.3 授权 API

### `POST /license/snapshot/issue`

用途：

- 根据当前用户权益签发桌面端可缓存的授权快照

要求：

- 快照必须有签名
- 快照必须带过期时间
- 快照必须带设备信息

建议响应：

```json
{
  "snapshot_id": "licsnap_xxx",
  "issued_at": "2026-05-07T12:00:00Z",
  "expires_at": "2026-05-14T12:00:00Z",
  "payload": "base64_or_json",
  "signature": "signature_xxx"
}
```

### `POST /license/snapshot/refresh`

用途：

- 已登录用户续发新的快照

### `POST /license/snapshot/revoke`

用途：

- 风控、退款、封号、纠纷后撤销离线授权

---

## 6.4 更新 API

### `GET /updates/manifest`

> **精确实现契约见 §16.5（请求/权益门控/三态响应/字段）+ §16.10（签名 payload 构造）+ §16.11（王维 checklist）+ §16.12（公钥）**。本节为简述，以 §16.5 为准。

用途：

- 根据用户权限、版本、渠道返回**带签名与 hash 的完整 manifest**（不是裸 URL）

规则：

- 匿名（无 token）只可拿 `stable-free`
- `pro_full` 可拿 `stable-pro`
- `enterprise_full` 可拿企业通道
- 付费通道 `package_url` 必须短期签名 URL（TTL ≤ 1h）
- 客户端 fail-closed 校验 `package_hash` + `signature` + `manifest_hash` + `manifest_signature`

请求参数：`app_id`、`current_version`、`channel`（可选，默认 stable）、`platform`、`device_id`，可选 `Authorization: Bearer` / `X-API-Key`。

## 7. 收费与授权的核心规则

这部分必须按服务端统一，不允许桌面端自己判定收费状态。

### 7.1 真相源

收费状态真相源是 `entitlements`，不是本地 license。

### 7.2 商品类型

服务端必须支持以下商品模型：

| 类型 | 说明 |
|---|---|
| 买断版 | 一次购买，永久权益 |
| 订阅版 | 月费/年费，到期失效 |
| 次数包 | 比如 AI 调用次数 |
| 升级包 | Free 升级到 Pro |

### 7.3 标准流程

标准业务流程如下：

1. 用户登录
2. 服务端识别用户身份
3. 客户端请求创建订单
4. 服务端创建支付意图
5. 用户完成支付
6. 支付渠道回调服务端
7. 服务端验签
8. 服务端更新订单/支付状态
9. 服务端幂等发放 entitlement
10. 客户端重新拉取 entitlement
11. 客户端请求新的 license snapshot

### 7.4 退款与撤权

退款后，服务端必须能执行以下动作：

1. 标记订单退款
2. 回收或失效相关 entitlement
3. 作废相关 license snapshot
4. 记录 audit log

## 11. 第一阶段验收标准

第一阶段上线前，至少满足：

- 可以创建 `"deepKit"` 数据库并初始化 schema
- 桌面端可以登录并拿到 token
- 桌面端可以创建订单
- 微信支付回调能正确验签并改订单状态
- 支付成功后能发放 entitlement
- 桌面端能拉到 entitlement
- 桌面端能拿到 license snapshot
- 免费版和 Pro 版能返回不同更新通道

---

## 12. 不要这样做

以下做法禁止：

- 让桌面端直连 PostgreSQL
- 在桌面端保存支付私钥
- 在客户端本地直接把订单改成 `paid`
- 用本地 license 作为收费唯一真相源
- 支付回调不验签直接发权益
- 把免费版/收费版判断逻辑分散到多个地方

## 15. PostgreSQL 建表 SQL 草案

下面这份 SQL 是第一版可执行草案，目标是让王维先把 `deepKit` 跑起来，支撑：

- 登录
- 订单
- 支付
- 权益
- 离线授权快照
- 更新通道

如果后续业务增加字段，可以在此基础上继续迁移。

### 15.1 创建数据库

```sql
CREATE DATABASE "deepKit"
  WITH
  ENCODING = 'UTF8'
  TEMPLATE template0;
```

连接到 `"deepKit"` 后执行：

```sql
CREATE EXTENSION IF NOT EXISTS pgcrypto;
```

### 15.2 核心表

```sql
CREATE TABLE IF NOT EXISTS users (
  user_id              TEXT PRIMARY KEY,
  display_name         TEXT,
  email                TEXT,
  phone                TEXT,
  password_hash        TEXT,
  is_active            BOOLEAN NOT NULL DEFAULT TRUE,
  created_at           TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  updated_at           TIMESTAMPTZ NOT NULL DEFAULT NOW()
);

CREATE TABLE IF NOT EXISTS identities (
  identity_id          TEXT PRIMARY KEY,
  user_id              TEXT NOT NULL REFERENCES users(user_id) ON DELETE CASCADE,
  provider             TEXT NOT NULL,
  provider_user_id     TEXT NOT NULL,
  app_id               TEXT NOT NULL,
  union_id             TEXT,
  created_at           TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  CONSTRAINT uq_identities_provider UNIQUE (provider, provider_user_id, app_id)
);

CREATE INDEX IF NOT EXISTS idx_identities_user_id
  ON identities(user_id);

CREATE INDEX IF NOT EXISTS idx_identities_union_id
  ON identities(union_id);

CREATE TABLE IF NOT EXISTS products (
  app_id                        TEXT NOT NULL,
  product_id                    TEXT NOT NULL,
  name                          TEXT NOT NULL,
  description                   TEXT,
  amount_minor                  BIGINT NOT NULL,
  currency                      TEXT NOT NULL,
  entitlement_code              TEXT NOT NULL,
  entitlement_duration_days     INTEGER NOT NULL DEFAULT 0,
  initial_quota                 INTEGER NOT NULL DEFAULT -1,
  is_active                     BOOLEAN NOT NULL DEFAULT TRUE,
  product_type                  TEXT NOT NULL DEFAULT 'subscription',
  created_at                    TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  updated_at                    TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  PRIMARY KEY (app_id, product_id)
);

CREATE INDEX IF NOT EXISTS idx_products_entitlement_code
  ON products(entitlement_code);

CREATE TABLE IF NOT EXISTS orders (
  order_id              TEXT PRIMARY KEY,
  user_id               TEXT NOT NULL REFERENCES users(user_id) ON DELETE RESTRICT,
  app_id                TEXT NOT NULL,
  product_id            TEXT NOT NULL,
  out_trade_no          TEXT NOT NULL UNIQUE,
  title                 TEXT NOT NULL,
  amount_minor          BIGINT NOT NULL,
  currency              TEXT NOT NULL,
  status                TEXT NOT NULL,
  created_at            TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  paid_at               TIMESTAMPTZ,
  closed_at             TIMESTAMPTZ,
  failed_at             TIMESTAMPTZ,
  refunded_at           TIMESTAMPTZ
);

CREATE INDEX IF NOT EXISTS idx_orders_user_id
  ON orders(user_id);

CREATE INDEX IF NOT EXISTS idx_orders_app_product
  ON orders(app_id, product_id);

CREATE INDEX IF NOT EXISTS idx_orders_status
  ON orders(status);

CREATE TABLE IF NOT EXISTS payments (
  payment_id            TEXT PRIMARY KEY,
  order_id              TEXT NOT NULL UNIQUE REFERENCES orders(order_id) ON DELETE CASCADE,
  provider              TEXT NOT NULL,
  channel               TEXT NOT NULL,
  provider_trade_no     TEXT,
  prepay_id             TEXT,
  status                TEXT NOT NULL,
  raw_payload           JSONB,
  created_at            TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  paid_at               TIMESTAMPTZ,
  refunded_at           TIMESTAMPTZ,
  CONSTRAINT uq_payments_provider_trade_no UNIQUE (provider, provider_trade_no)
);

CREATE INDEX IF NOT EXISTS idx_payments_status
  ON payments(status);

CREATE TABLE IF NOT EXISTS payment_notifications (
  notification_id       TEXT PRIMARY KEY,
  provider              TEXT NOT NULL,
  notification_key      TEXT NOT NULL UNIQUE,
  out_trade_no          TEXT NOT NULL,
  provider_trade_no     TEXT,
  amount_minor          BIGINT NOT NULL,
  currency              TEXT NOT NULL,
  verified              BOOLEAN NOT NULL DEFAULT FALSE,
  processed             BOOLEAN NOT NULL DEFAULT FALSE,
  raw_payload           JSONB NOT NULL,
  received_at           TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  processed_at          TIMESTAMPTZ
);

CREATE INDEX IF NOT EXISTS idx_payment_notifications_out_trade_no
  ON payment_notifications(out_trade_no);

CREATE INDEX IF NOT EXISTS idx_payment_notifications_provider_trade_no
  ON payment_notifications(provider_trade_no);

CREATE TABLE IF NOT EXISTS entitlements (
  entitlement_id        TEXT PRIMARY KEY,
  user_id               TEXT NOT NULL REFERENCES users(user_id) ON DELETE CASCADE,
  app_id                TEXT NOT NULL,
  product_id            TEXT NOT NULL,
  code                  TEXT NOT NULL,
  status                TEXT NOT NULL,
  valid_from            TIMESTAMPTZ NOT NULL,
  valid_until           TIMESTAMPTZ,
  remaining_quota       INTEGER NOT NULL DEFAULT -1,
  source_order_id       TEXT NOT NULL UNIQUE REFERENCES orders(order_id) ON DELETE RESTRICT,
  created_at            TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  updated_at            TIMESTAMPTZ NOT NULL DEFAULT NOW()
);

CREATE INDEX IF NOT EXISTS idx_entitlements_user_app
  ON entitlements(user_id, app_id);

CREATE INDEX IF NOT EXISTS idx_entitlements_user_app_code
  ON entitlements(user_id, app_id, code);

CREATE INDEX IF NOT EXISTS idx_entitlements_status
  ON entitlements(status);

CREATE TABLE IF NOT EXISTS refresh_tokens (
  refresh_token_id      TEXT PRIMARY KEY,
  user_id               TEXT NOT NULL REFERENCES users(user_id) ON DELETE CASCADE,
  device_id             TEXT,
  token_hash            TEXT NOT NULL UNIQUE,
  expires_at            TIMESTAMPTZ NOT NULL,
  revoked_at            TIMESTAMPTZ,
  created_at            TIMESTAMPTZ NOT NULL DEFAULT NOW()
);

CREATE INDEX IF NOT EXISTS idx_refresh_tokens_user_id
  ON refresh_tokens(user_id);

CREATE TABLE IF NOT EXISTS device_sessions (
  session_id            TEXT PRIMARY KEY,
  user_id               TEXT NOT NULL REFERENCES users(user_id) ON DELETE CASCADE,
  device_id             TEXT NOT NULL,
  device_name           TEXT,
  device_fingerprint    TEXT,
  app_id                TEXT NOT NULL,
  platform              TEXT,
  app_version           TEXT,
  last_seen_at          TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  created_at            TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  revoked_at            TIMESTAMPTZ,
  CONSTRAINT uq_device_sessions_user_device UNIQUE (user_id, device_id, app_id)
);

CREATE INDEX IF NOT EXISTS idx_device_sessions_user_id
  ON device_sessions(user_id);

CREATE TABLE IF NOT EXISTS license_snapshots (
  snapshot_id           TEXT PRIMARY KEY,
  user_id               TEXT NOT NULL REFERENCES users(user_id) ON DELETE CASCADE,
  app_id                TEXT NOT NULL,
  device_id             TEXT NOT NULL,
  entitlement_summary   JSONB NOT NULL,
  payload               JSONB NOT NULL,
  signature             TEXT NOT NULL,
  issued_at             TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  expires_at            TIMESTAMPTZ NOT NULL,
  revoked_at            TIMESTAMPTZ
);

CREATE INDEX IF NOT EXISTS idx_license_snapshots_user_device
  ON license_snapshots(user_id, device_id, app_id);

CREATE TABLE IF NOT EXISTS update_manifests (
  app_id                TEXT NOT NULL,
  channel               TEXT NOT NULL DEFAULT 'stable',
  platform              TEXT NOT NULL DEFAULT 'win64',
  latest_version        TEXT NOT NULL,
  min_version           TEXT NOT NULL DEFAULT '0.0.0',
  min_entitlement_code  TEXT,
  manifest_url          TEXT NOT NULL DEFAULT '',
  package_url           TEXT NOT NULL DEFAULT '',
  package_hash          TEXT NOT NULL DEFAULT '',
  signature             TEXT NOT NULL DEFAULT '',
  signature_algorithm   TEXT NOT NULL DEFAULT 'rsa-sha256',
  signature_required    BOOLEAN NOT NULL DEFAULT TRUE,
  manifest_hash        TEXT NOT NULL DEFAULT '',
  manifest_signature    TEXT NOT NULL DEFAULT '',
  force_update          BOOLEAN NOT NULL DEFAULT FALSE,
  release_notes         TEXT NOT NULL DEFAULT '',
  is_active             BOOLEAN NOT NULL DEFAULT TRUE,
  created_at            TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  updated_at            TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  CONSTRAINT uq_update_manifests UNIQUE (app_id, channel, platform)
);

CREATE INDEX IF NOT EXISTS idx_update_manifests_app_channel
```

### 16.5 更新 manifest 接口契约（`GET /dk/updates/manifest`）

本节是 `/dk/updates/manifest` 的**精确实现契约**，王维照此实现 Python 路由。算法统一为 **RSA-SHA256（PKCS#1 v1.5）**，与 license snapshot 的 Ed25519 密钥隔离（见 §16.12 公钥、§16.11 王维 checklist）。

> 客户端 `Features/DeepBase.Updater.pas` 的 `TUpdateManager` 已实现本契约的全部客户端侧逻辑（双层验签 / manifest 路由模式 / transport 注入 / 安装 / 回滚），本节只规定服务端必须返回什么、客户端如何校验。客户端生产代码改动仅一处：默认加载 §16.12 公钥（见 `Initialize` / `SetPublicKey`）。

#### 请求

| 参数 | 位置 | 必填 | 说明 |
|---|---|---|---|
| `app_id` | query | 是 | 如 `deepbase_desktop` / `deepsync_desktop` |
| `current_version` | query | 是 | 客户端当前版本，语义化版本字符串 |
| `channel` | query | 否 | 默认 `stable`；客户端可请求 `stable`/`beta` 等，但最终返回哪个通道由权益决定（见下） |
| `platform` | query | 否 | `win64`/`macos`/`linux`，服务端按平台返回对应 `package_url` |
| `device_id` | query | 否 | 风控/审计用 |
| `Authorization` | header | 否 | `Bearer <access_token>`；**无 token 视为匿名（免费用户）**，只可拿 `stable-free` |
| `X-API-Key` | header | 否 | 设备级 API Key，与 Bearer 二选一或并用 |

#### 权益门控（服务端职责）

服务端先解析 token 拿用户身份 → 查 `entitlements` → 按 `update_manifests.min_entitlement_code` 选可见的最高通道：

| 用户权益 | 可见 channel | 超出请求 channel |
|---|---|---|
| 无 token / 无 entitlement | `stable-free` | 返回 403 `FORBIDDEN` |
| `pro_full` | `stable-free` / `stable-pro` | 返回 403 |
| `enterprise_full` | 全部含企业通道 | — |

> 客户端**不做**权益门控校验（§16.5 要求 1-3 全在服务端）。客户端收到 403 不自动降级（调用方决定是否重请求 `stable-free`）。

#### 响应

**200（有更新）** — 返回完整签名 manifest：

```json
{
  "app_id": "deepsync_desktop",
  "current_version": "1.2.0",
  "channel": "stable-pro",
  "latest_version": "1.3.0",
  "min_version": "1.0.0",
  "manifest_url": "",
  "package_url": "https://download.deepkit.top/ds/1.3.0/deepsync-1.3.0-win64.zip?sign=...&expires=...",
  "package_hash": "sha256:a1b2c3...",
  "signature": "<base64 RSA-SHA256 签名，见 §16.10>",
  "signature_algorithm": "rsa-sha256",
  "signature_required": true,
  "manifest_hash": "sha256:<hex>",
  "manifest_signature": "<base64 RSA-SHA256 签名，见 §16.10>",
  "force_update": false,
  "release_notes": "...",
  "min_entitlement_code": "pro_full"
}
```

字段说明：

- `package_url`：**最终下载 URL**。付费通道必须是短期签名 URL（COS presigned，TTL ≤ 1 小时，§16.5 要求 4），避免裸链长期传播。`stable-free` 可用 CDN 裸链。
- `package_hash`：`sha256:` 前缀 + zip 原始字节的 SHA256 hex。客户端下载后用此校验包完整性。
- `signature`：**对 zip 原始字节的 RSA-SHA256 签名**，base64。客户端用 §16.12 公钥验。
- `manifest_hash` / `manifest_signature`：对 manifest payload 的双层保护（§16.10），防 manifest 在传输中被篡改。
- `signature_required`：`true` 时客户端 fail-closed——缺签名直接判失败，不装。
- `min_entitlement_code`：该通道所需权益，透传给客户端审计展示（客户端不据此拦截）。
- `manifest_url`：保留字段，本契约不使用（`package_url` 即下载源），留空。

**200（无更新 / 已是最新）** — 同结构，`latest_version == current_version`，`package_url`/`signature` 可空，`force_update: false`。客户端据此显示「已是最新」。

**403 `FORBIDDEN`** — 用户权益不足以访问请求 channel，body 含 `{"error":"forbidden","detail":"entitlement insufficient"}`。客户端不自动降级。

**404** — `app_id` 或 `platform` 无对应通道配置。

#### 客户端校验顺序（§16.5 要求 5）

`TUpdateManager` 下载后依次：① `VerifyFileHash`（package_hash）→ ② `VerifySignature(package_hash, signature)` 验包签名 → ③ `BuildManifestSignaturePayload` 重算 manifest payload → ④ 比对 `manifest_hash` → ⑤ `VerifySignature(payload, manifest_signature)` 验 manifest 签名。任一失败且 `signature_required=true` → `usFailed`，不安装。`signature_required=false` 时仅记日志放行（仅 `stable-free` 允许）。

#### COS / 域名解耦

客户端只认 `package_url` 字符串，不感知 COS。付毅侧建腾讯云 COS bucket + 备案 `download.deepkit.top`（或 CDN 域名）后，王维在 `update_manifests.package_url` 填真 URL + 生成短期签名 URL。域名/CDN 切换对客户端零改动。

### 16.10 签名 payload 构造（王维照此实现，最易错处）

manifest 的 `signature` / `manifest_hash` / `manifest_signature` 三个字段必须按本节顺序构造，否则客户端 `BuildManifestSignaturePayload`（`Features/DeepBase.Updater.pas`，7 字段管道分隔）验签失败。

#### 算法

- 签名算法：**RSA-SHA256（PKCS#1 v1.5）**，base64 编码输出（标准 base64，非 base64url）。
- 签名密钥：单一 RSA-2048 私钥（env `UPDATE_SIGN_RSA_PRIVATE_KEY_PEM`），**与 license 的 Ed25519 密钥隔离**。包签名与 manifest 签名用**同一私钥**。

#### 步骤

```
Step 1: package_bytes = zip 安装包原始字节
Step 2: package_hash  = "sha256:" + hex(sha256(package_bytes))
Step 3: signature     = base64( RSA_SHA256_Sign(private_key, utf8(pkg_hash_hex)) )
                                  # §16.10 关键点 2：签的是 pkg_hash_hex（去掉 "sha256:" 前缀、
                                  # 小写）的 UTF-8 字节，不是 zip 字节、不是含前缀串

Step 4: payload = app_id + "|" + latest_version + "|" + channel + "|"
              + package_url + "|" + download_size + "|" + package_hash + "|"
              + signature
        # 7 字段，'|' 分隔，顺序固定，与客户端 BuildManifestSignaturePayload 一致
        # 第 7 位 signature = Step 3 算出的包签名 base64（自引用：先有 package signature 才能拼 payload）

Step 5: manifest_hash      = "sha256:" + hex(sha256(utf8(payload)))
Step 6: manifest_signature = base64( RSA_SHA256_Sign(private_key, utf8(payload)) )
                                  # 签的是 payload 的 UTF-8 字节

返回体填入 package_hash / signature / manifest_hash / manifest_signature
```

#### 关键点（必读）

1. **第 7 位是 `signature` 自身**——这是自引用结构：必须先算出 package signature（Step 3），才能拼出完整 payload（Step 4），再对完整 payload 算 manifest_signature（Step 6）。**顺序不能颠倒，payload 字段顺序不能变**。
2. `signature` 签的是 **去掉 `sha256:` 前缀后的纯 hex 小写字符串**（如 `"a1b2c3..."`），**不是** zip 原始字节，也**不是**含前缀的完整字符串。客户端 `Updater.pas` ParseUpdateManifest（L835-837）会先 `Delete('sha256:', 1..7)` 去前缀 + `LowerCase`，存入 `Info.PackageHash`；随后 L1710 `VerifySignature(Info.PackageHash, Info.Signature, ...)` 的第一个参数 `Data` 就是这个**纯 hex 小写串**；`TRSAVerifier.VerifySignature(AData: string)` 内部对 `AData` 做 `UTF8.GetBytes` 后 RSA-SHA256 验签。所以**服务端 Step 3 必须对「`package_hash` 去掉 `sha256:` 前缀、转小写」后的纯 hex 字符串的 UTF-8 字节做 RSA-SHA256 签名**，即 `signature = base64(RSA_SHA256_Sign(sk, hex(sha256(package_bytes)).lower().encode("utf-8")))`。两边 data 来源、编码、大小写完全一致——这是联调最易炸点，先对齐这个再验签名。
3. `manifest_signature` 签的是 **payload 的 UTF-8 字节**（不是 payload 的 hash）。客户端 `BuildManifestSignaturePayload` 重算 payload → `VerifySignature(payload_string, manifest_signature)`。
4. 空字段用空字符串 `''`，不用 `null`，确保 `|` 分隔后字段数恒为 7。
5. `download_size` 是 package 字节数的十进制整数字符串（如 `"12345678"`），不带单位。

#### Python 参考片段（cryptography 库）

```python
from cryptography.hazmat.primitives import hashes, serialization
from cryptography.hazmat.primitives.asymmetric import padding
import base64, hashlib

def _sign(sk, data: bytes) -> str:
    return base64.b64encode(sk.sign(data, padding.PKCS1v15(), hashes.SHA256())).decode()

def build_signed_manifest(sk, app_id, latest_version, channel,
                          package_url, package_bytes) -> dict:
    pkg_hash_hex = hashlib.sha256(package_bytes).hexdigest()  # 已是小写
    package_hash = "sha256:" + pkg_hash_hex                     # 写库 / 下发带前缀
    # §16.10 关键点 2：客户端 ParseUpdateManifest 会去 "sha256:" 前缀 + 小写后传入验签，
    # 故服务端签名 data 必须与之对齐——签去前缀的纯 hex 小写串的 UTF-8 字节：
    signature = _sign(sk, pkg_hash_hex.encode("ascii"))
    download_size = str(len(package_bytes))
    payload = "|".join([app_id, latest_version, channel, package_url,
                        download_size, package_hash, signature])
    manifest_hash = "sha256:" + hashlib.sha256(payload.encode("utf-8")).hexdigest()
    manifest_signature = _sign(sk, payload.encode("utf-8"))  # §16.10 关键点 3：签 payload
    return {
        "package_hash": package_hash,
        "signature": signature,
        "manifest_hash": manifest_hash,
        "manifest_signature": manifest_signature,
        "signature_algorithm": "rsa-sha256",
        "signature_required": True,
    }
```
