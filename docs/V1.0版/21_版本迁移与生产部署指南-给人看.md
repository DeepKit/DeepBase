# 21. 版本迁移与生产部署指南（给人看）

> 本文是面向架构师 / 维护者的 **V1.0 规划文档**，用于指导未来 UniBase 框架及使用 UniBase 的应用在版本升级与生产部署时遵循统一流程。当前代码仍以 v0.3 规范为准，本文件不改变现有行为。

---

## 1. 适用范围与目标

- 适用对象：
  - 维护 UniBase 框架本身的核心开发者；
  - 使用 UniBase 的应用的架构师 / 运维。
- 目标：
  - 为 UniBase 自身定义清晰的版本语义与迁移路径；
  - 为使用 UniBase 的应用提供 **可预测** 的升级策略；
  - 给出 **生产部署前** 的统一检查清单。

---

## 2. UniBase 版本语义（预期 V1.0 规则）

未来 UniBase 版本号采用 `Major.Minor.Patch` 语义：

- `Major`（主版本）：可能存在破坏性变更，通常伴随数据结构或 API 重大调整。例如：`0.3 → 1.0`。
- `Minor`（次版本）：向后兼容的功能增强，不破坏既有 API 使用方式。例如：`1.0 → 1.1`。
- `Patch`（补丁版本）：Bug 修复和小型优化，不新增重要特性。例如：`1.0.0 → 1.0.1`。

**对应用的承诺（规划）：**

- 在同一 Major 版本内（如 `1.x.y`）：
  - config.db 的表结构变更通过 **自动迁移脚本** 完成，避免手工干预；
  - 公开 API（`docs/13.api.md`, `docs/14.api-reference.md` 中标记为 `@stable` 的部分）保持兼容；
  - 仅允许新增字段 / 新表，不随意删除字段。
- 升级到新的 Major 版本（如 `0.3 → 1.0`）：
  - 需要显式执行迁移脚本或使用 Studio/CLI 的升级命令；
  - 可能需要人工调整应用代码或配置（会在迁移说明中给出清单）。

> 说明：当前 v0.3 仍处于“演进期”，上述规则主要约束未来的 `1.x` 系列。对于 v0.x → v1.0 的迁移，可以将其视为“一次性的结构化重构”。

## 3. config.db 迁移基础（复用现有机制）

`docs/12.unibase-spec-v0.3.md` 已经定义了：

- `SchemaInfo` / `SchemaMigrations` 等元数据表；
- 迁移脚本命名规范 `V001__Add_Hotkeys_Table.sql` 等；
- `ApplyMigrations` 的典型执行流程。

在 V1.0 中建议：

1. **所有 Schema 变更必须以迁移脚本形式存在**：
   - 禁止在运行时直接执行 `ALTER TABLE ...` 等裸 SQL 修改结构；
   - 所有结构变更集中放入 `migrations/` 目录，由 SchemaManager 统一执行。
2. **迁移脚本必须是幂等 / 可检测的**：
   - 使用 `IF NOT EXISTS` 检查表/列是否存在；
   - 在 `SchemaMigrations` 中记录 `version`、`script_name`、`checksum`、`applied_at` 等信息。
3. **应用初始化时默认执行迁移**（可配置）：
   - 开发环境：自动迁移以降低门槛；
   - 生产环境：建议在部署脚本中显式执行 `unibase db upgrade`，应用启动时只做版本号检查。

## 4. 应用升级推荐流程（从 v0.x 到 V1.0）

> 本节为未来 V1.0 推出时的规划建议，当前可以作为思想准备，不影响现有 0.3 使用方式。

### 4.1 升级前

1. **备份 config.db 与业务数据库**：
   - 对于每个应用：
     - 备份 `{ProjectRoot}/config.db`；
     - 备份所有业务库（PostgreSQL/SQLite）。
2. **冻结当前版本**：
   - 在应用中记录当前 UniBase 版本号（例如在 `ProjectInfo` 中增加 `UniBaseVersion` 字段）；
   - 确保所有环境（开发/测试/生产）使用相同 UniBase 版本。
3. **阅读迁移说明**：
   - 查阅未来的 `21_版本迁移与生产部署指南` 中的“从 v0.3 到 v1.0 迁移说明”章节；
   - 明确需要人工参与的步骤（如配置重命名、废弃字段处理等）。

### 4.2 执行迁移

1. **在测试环境先跑迁移脚本**：
   - 使用 CLI：
     ```bash
     unibase db backup --db config.db --output backup_before_v1.db
     unibase db upgrade --db config.db --to-version 1.0
     ```
2. **运行应用自测与回归测试**：
   - 编译并运行 `Tests/UniBaseTests.dproj`；
   - 启动应用自带的 `*.TestGUI.dpr`，人工点击主要用例；
   - 修复发现的问题，并记录在迁移说明中。

### 4.3 正式环境切换

1. 在维护窗口内：
   - 停止旧版本应用；
   - 备份生产环境 config.db；
   - 执行迁移脚本；
   - 部署新版本应用 EXE/依赖；
2. 启动应用并进行一次“冒烟测试”（Smoke Test）：
   - 打开主界面；
   - 完成一笔典型业务流程；
   - 检查日志中是否有新的严重错误。

## 5. 生产部署 Checklist（V1.0 规划版）

> 作为未来 V1.0 的推荐实践，当前可作为参考。真正执行时，请结合实际项目调整。

### 5.1 配置与安全

- [ ] **config.db**：
  - [ ] 位于预期目录（`{ProjectRoot}/config.db`），且访问权限正确（应用可读写）。
  - [ ] Schema 版本与期望的 UniBase 版本相符（`SchemaInfo.SchemaVersion`）。
- [ ] **敏感配置**：
  - [ ] 所有带 `IsEncrypted = 1` 的 `Settings` 项已通过 `SetConfigSecure` 加密；
  - [ ] 未在代码中硬编码 API Key / 密码。
- [ ] **日志与脱敏**：
  - [ ] `Log.Level` 为 `INFO` 或 `WARN`，生产环境禁用 DEBUG（除非临时排障）；
  - [ ] 日志脱敏关键字配置合理（参考 `05_安全与防护指南.md`）。
- [ ] **EXE 与完整性**：
  - [ ] EXE 已完成代码签名；
  - [ ] 若启用了运行时完整性校验（HMAC/SHA256），已在目标环境验证通过。

### 5.2 性能与容量

- [ ] `config.db` 已在上线前执行 `VACUUM`，并删除不必要的历史日志：
  - [ ] `Logs` 表保留最近 N 天（例如 30 天）。
  - [ ] `ExceptionReports` 中旧数据视情况归档或清理。
- [ ] 在预生产环境完成了压测或高并发测试：
  - [ ] 典型操作的响应时间在可接受范围内；
  - [ ] 日志写入、Config 读取等没有明显瓶颈。

### 5.3 备份与回滚

- [ ] 已配置：
  - [ ] config.db 的定期备份任务；
  - [ ] 业务数据库的备份与恢复脚本；
- [ ] 明确回滚路径：
  - [ ] 若 V1.0 部署失败，可以在有限时间内回退到上一个稳定版本（EXE + config.db 备份）。

### 5.4 监控与告警（可选，推荐）

- [ ] 对关键日志事件（FATAL/ERROR）建立监控与告警通道；
- [ ] 对 ExceptionReports 表的新增速率进行监控；
- [ ] 对 LLM 调用的失败率和成本进行定期审查。
