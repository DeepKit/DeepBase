# 22. 多项目协作与公共库规范（给人看）

> 本文是面向 **多项目 / 多团队协作** 的 V1.0 规划文档，指导如何在多个 UniBase 应用之间共享公共库、控制版本和避免冲突。当前代码仍以 v0.3 文档为准，本文件用于规划未来演进方向。

---

## 1. 目标与适用场景

- 目标：
  - 指导多个基于 UniBase 的应用如何安全地共享公共代码（UT/BT/DB/PG 等单元）。
  - 明确 UniBase 框架 / 公共库 / 业务仓库的职责边界与版本关系。
- 适用场景：
  - 同一公司内有多个业务系统共同使用 UniBase；
  - 存在一个或多个“公共工具仓库”（例如 UTxxx_*, BTxxx_*）；
  - 多个团队分别维护不同业务应用，但共享一套基础设施。

---

## 2. 仓库与模块划分建议

### 2.1 仓库角色

建议划分三类仓库：

1. **框架仓库（UniBase）**：
   - 当前这个仓库；
   - 提供 `Core/`、`VCL/`、`FMX/`、`Tools/` 等基础设施；
   - 版本号独立维护（遵循 21 号文档中的版本语义）。

2. **公共库仓库（CommonLibs）**：
   - 存放 `UTxxx_*`, `BTxxx_*`, `DBxxx_*`, `PGxxx_*` 等可跨项目复用的单元；
   - 只依赖 **Delphi RTL** 和 **极少量第三方库**，不直接依赖业务仓库；
   - 与 UniBase 框架的依赖关系应是 **单向的**（UniBase 中可以使用 UT/BT，但公共库不依赖 UniBase）。

3. **业务应用仓库（AppA / AppB / ...）**：
   - 每个业务应用一个独立仓库；
   - 依赖：UniBase + CommonLibs + 业务自有代码；
   - config.db / 业务数据库 / Studio 配置均为各自独立实例。

### 2.2 依赖关系（推荐）

```text
CommonLibs  →  (仅依赖 RTL/第三方)
    ↑
    │
 UniBase    →  依赖 CommonLibs 中部分单元（可选）
    ↑
    │
 AppA/AppB  →  依赖 UniBase + CommonLibs + 业务代码
```

> 原则：
> - 公共库不依赖任何具体业务仓库；
> - UniBase 不依赖业务仓库；
> - 业务仓库可以视需要依赖 CommonLibs 和 UniBase。

## 3. 公共单元（UT/BT/DB/PG 等）的管理

### 3.1 命名与职责回顾

结合 `02_UniBase最佳实践指南.md` 中的约定：

- `UTxxx_*`：通用工具类（数学、字符串、文件等），与业务无关。
- `BTxxx_*`：基础工具类（异常处理、验证、线程/进程辅助等）。
- `DBxxx_*`：数据库访问与配置支持（Repository、连接池、缓存等）。
- `PGxxx_*`：PostgreSQL 深度功能（队列、搜索、时序数据等）。

### 3.2 收敛公共代码的流程

当在业务项目中发现一段具有复用价值的代码时：

1. **初始阶段**：在业务仓库中本地实现，前缀可使用 `UApp_*` 或 `AppX_*`；
2. **复用验证**：当至少两个业务项目有类似需求时，评估是否提升为公共库：
   - 代码是否与具体业务模型分离？
   - 是否依赖过多业务特定类型？
3. **抽象与迁移**：
   - 在 CommonLibs 仓库中新建合适的 `UTxxx_*` / `BTxxx_*` / `DBxxx_*` 单元；
   - 把与业务无关的部分迁移过去，保留少量可配置接口；
4. **替换业务实现**：
   - 更新各个业务仓库，改为引用 CommonLibs 中的新单元；
   - 删除原业务仓库内的重复实现。

### 3.3 版本控制与变更策略

- 公共库应有自己的版本号（例如 `CommonLibs 1.2.3`），与 UniBase 主版本解耦；
- **兼容性要求**：
  - 小版本（Minor）升级尽量保持 API 向后兼容；
  - 若必须删除/修改公共函数，应先标记为 `deprecated`，并在变更日志中提示；
- 建议每次变更公共库都：
  - 在至少一个示例项目中验证；
  - 更新对应的 `CHANGELOG` 或 Release Notes。

## 4. 多项目下的 config.db 与 Studio 使用规范（展望）

### 4.1 每个项目独立的 ConfigDB

- 每个业务应用有自己的 `ProjectRoot` 与 `config.db`（DB1x），不能共享；
- Studio 的 `StudioConfig.db`（DB1A）仅作为“**应用注册中心**”，保存：
  - `root_path` / `config_db_path`；
  - 备注、标签等元信息；
- 所有关于 **查询定义 / 连接配置 / i18n / Settings** 的权威来源都在各自项目的 ConfigDB 中。

### 4.2 Studio 对多项目的推荐工作流

> 该部分为未来 Studio 功能的规划方向，当前可看作愿景：

1. **统一入口列表**：
   - Studio 启动后从 `StudioConfig.db` 读取应用列表；
   - 显示项目名、版本、路径、最近编辑时间等信息。
2. **按项目切换上下文**：
   - 选中某应用后，Studio 连接该项目的 ConfigDB；
   - 所有 i18n/日志/查询/配置编辑操作都作用在该项目上。
3. **一键新建项目（脚手架）**：
   - Studio 提供“从模板创建新项目”（例如 `UniBaseRun` 模板）；
   - 自动复制标准目录结构、示例代码、Tests 和 TestGUI；
   - 初始化一个干净的 ConfigDB（Tier0+Tier1），并注册到 StudioConfig 中。

## 5. 多团队协作与代码所有权

### 5.1 所有权划分

- **UniBase 框架团队**：
  - 负责 `Core/`、`VCL/`、`FMX/`、`Tools/` 的设计与实现；
  - 负责定义 ConfigDB Schema 与 doQry 协议；
  - 对 `docs/00–18` 与 `12/13/14` 有最终解释权。
- **公共库团队（如有）**：
  - 负责 CommonLibs 仓库的治理与演进；
  - 建议由经验丰富的 Delphi 开发者维护；
  - 变更需提前通知所有业务团队。
- **业务团队**：
  - 负责自己仓库内的所有业务代码和配置；
  - 遵守 UniBase 与 CommonLibs 的约束，不在本地“Fork 一份公共库”长期使用。

### 5.2 Code Review 与变更流程建议

- 对 UniBase 与 CommonLibs 仓库的修改应：
  - 至少有一名非作者的 Reviewer 审核；
  - 在 PR 描述中列出“影响的业务项目”；
  - 必要时安排灰度升级和回滚方案。
- 对业务仓库的修改：
  - 重点检查是否遵守 `docs/01` / `docs/02` 中的分层约束；
  - 是否正确使用了 UniBase/公共库，而不是复制粘贴；
  - 是否更新了对应测试与文档。

---

## 6. 对当前 v0.3 阶段的建议

- 不强制要求立即重构所有现有项目到“三层仓库”结构；
- 建议在新增项目或重构时，**优先按本规范设计新的仓库划分**；
- 当 CommonLibs 成熟后，再逐步将老项目中散落的 UT/BT/DB 代码回收进去。
