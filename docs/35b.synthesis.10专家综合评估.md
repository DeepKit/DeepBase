## R2 五大发现（跨专家共识）

### 发现 1：SafeQuery 审计可绕过 — 架构级缺陷

**指出专家**：威胁建模 + 设计模式

`OpenReadOnly` 和 `OpenWithKeyCallback` 返回裸 `TFDConnection` 指针。调用方拿到后可直接 `TFDQuery.Create(conn)` 绕过 `SafeQuery` 的全部审计。`GetRawSQLiteHandle` 甚至暴露了 `sqlite3*` C 句柄。
**P0 验收条件 `GetBodyColumnsSeen = False` 可被静默满足，实际正文已泄露。**

### 发现 2：命令队列是过度工程化

**指出专家**：设计模式 + 容错 + 并发

`IUIACommandExecutor` + `TThreadedQueue<TUIACommand>` + `TUIAExecutionThread` 带来 ~150 LOC 和 4 个并发问题（PopItem 死锁、栈捕获悬空指针、队列无界 OOM、消费者死亡死锁），但粘贴操作本质是串行的。**替代方案：同步调用 + 可选 `TTask.Run`（5 LOC）**。功能无损，并发 bug 清零。

### 发现 3：MapRow 是性能杀手

**指出专家**：性能 + 设计模式

100 万行 × 每行 `TDictionary.Create` = **2.2GB 峰值内存** + 100 万次堆分配。`FForbiddenFields` 的 O(n×m) 线性扫描在执行每行时重复。v0.3 新增的 `MapRows` 仍是逐行转调，未做任何批量优化。

### 发现 4：并发设计有 4 个 P0 缺陷

**指出专家**：并发（独力发现全部 4 个）

| # | 缺陷 | 后果 |
|---|------|------|
| P0-1 | `FWatchTargets: TList<string>` 三线程无锁访问 | Add 触发 Grow → Contains 读野指针 → AV |
| P0-2 | `PopItem(Cmd)` 无超时 + 无 `DoShutDown` | 线程关闭时永久阻塞在 PopItem → 死锁 |
| P0-3 | `FActiveInstance` 缺失赋值 + 无 `MemoryBarrier` | 回调读 nil 或脏值 → hook 静默不工作 |
| P0-4 | `TUIACommand` record 在 while 循环中被 TThread.Queue 捕获 | 下一次循环覆盖 Cmd 或帧释放 → heisenbug |

### 发现 5：容错缺失导致级联故障

**指出专家**：容错 + 威胁建模

三个最大的级联故障链：
1. **静默剪贴板数据丢失**：UIPI 阻止粘贴 → 验证超时 → 恢复重试全失败 → `%TEMP%` 备份也失败 → 用户数据永久丢失
2. **SetWinEventHook 静默失效**：回调异常 → Windows 取消 hook → 无检测/恢复 → UIA 引擎致盲
3. **SafeQuery 审计阻断数据流**：`RecordColumnAccess` 抛异常 → 查询从未执行 → 业务层无数据

## v0.4 变更建议（按 ROI 排序）

### 变更 A：删除命令队列，改为同步调用（ROI ∞）

**当前**：`IUIACommandExecutor` + `TThreadedQueue` + `TUIAExecutionThread`（~150 LOC，4 个并发 bug）
**改为**：
```delphi
// 直接同步调用
UIA.SetValue(Locator, text, Guard);

// 需要异步时（可选）：
TTask.Run(procedure begin
  CoInitializeEx(nil, COINIT_APARTMENTTHREADED);
  try UIA.SetValue(Locator, text, Guard);
  finally CoUninitialize; end;
end);
```
**收益**：删除 1 个接口、1 个类、1 个线程、4 个并发 bug。功能不减。

### 变更 B：OpenReadOnly/OpenWithKeyCallback 返回 IExternalDBReader 而非 TFDConnection（ROI 最高）

**当前**：返回裸 `TFDConnection` 给调用方 → SafeQuery 审计可被绕过
**改为**：返回 `IExternalDBReader` 接口（仅暴露 `SafeQuery`/`GetSchema`/`GetSchemaFingerprint`/`Close`）
**收益**：消除架构级审计绕过路径。SafeQuery 成为强制唯一出口。

### 变更 C：MapRow 列式布局替代 TDictionary（ROI 最高）

**当前**：每行新建 `TDictionary<string, Variant>`（2.2KB/行，100万行=2.2GB）
**改为**：`TArray<Variant>` 列式布局（370B/行，100万行=370MB），列索引由 `FFieldMappings` 顺序定义
**收益**：内存降低 **83%**，消除 100 万次堆分配。

### 变更 D：并发缺陷修复（4 项）

| 缺陷 | 修复 |
|------|------|
| P0-1 `FWatchTargets` 无锁 | 改用 `TThreadList<string>` |
| P0-2 `PopItem` 死锁 | 若命令队列被裁撤则不再存在；若保留则加 `DoShutDown` + 超时 |
| P0-3 `FActiveInstance` 缺赋值/屏障 | `TInterlocked.Exchange(Pointer(FActiveInstance), Pointer(Self))` 在 `SetWinEventHook` 之前 |
| P0-4 record 栈捕获 | 若命令队列被裁撤则不再存在 |

### 变更 E：容错加固（5 项）

| 故障场景 | 修复 |
|---------|------|
| SafeQuery 审计抛异常阻断查询 | 审计包裹在 `try/except` 中，仅记录不抛出 |
| SetWinEventHook 回调异常静默取消 | `try/except` 包裹回调 + 每 60s 健康检查 + 自动重新注册 |
| SaveBackupToTemp 磁盘满 | 三级降级：Temp → AppData → 程序目录 → Logger.Critical |
| EmptyClipboard 后 GlobalAlloc 失败 | 剪贴板清空前预检内存可用性 |
| 粘贴验证超时状态不确定 | 超时后通知用户 + 记录完整日志 |

### 变更 F：UIA JSON 映射文件完整性校验 + FindElement 归属验证

| 威胁 | 修复 |
|------|------|
| JSON 映射文件篡改 | SHA256 哈希校验 + `.sig` 签名文件，不匹配则降级到内置映射 |
| UIA 元素欺骗 | FindElement 返回后验证元素所在进程名匹配目标进程；粘贴前二次确认前台窗口 |

### 变更 G：BodyZero 审计改为装饰器模式（可选，ROI 中等）

**当前**：审计逻辑硬编码在 `TExternalSQLiteReader.SafeQuery` 中
**改为**：`TAuditedExternalDBReader` 装饰器组合 `IExternalDBReader` + `IBodyZeroAuditor`
**收益**：Reader 回归单一职责；审计可独立测试；可复用于其他数据源。**若只有 SQLite 一个 reader 实现，可暂缓。**

### 变更 H：SchemaAdapter FieldMapping JSON 外置 + MapRows 批量优化（可选）

**当前**：FieldMapping 在 Pascal 代码中硬编码，与 UIA JSON 外置不一致
**改为**：统一 JSON 外置配置 + `MapRows` 批量预分配缓冲区
**收益**：微信版本适配无需重新编译 + 性能提升

## 是否是最优设计？

**结论：v0.3 已消除所有编译/运行时硬伤，方向正确。v0.4 建议的 8 项变更中，A+B+C+D 四项是"实现前必做"（否则会留下架构级安全隐患和并发崩溃），E+F 是"发布前必做"，G+H 是可选的工程优化。**

**做 A+B+C+D+E+F 后的最终设计评分为 8.0/10。扣分主要在于 SchemaAdapter 和 UIA 的 FieldMapping 尚未统一外置（一致性略带瑕疵），以及 10+ MB 大剪贴板的性能优化尚未完全解决。**

核心判断：**管道分层的方向是正确的，但可以更薄。** 四层中，Reader（32）和 ClipboardGuard（35）是最有价值的层——它们代表了独立的故障域。Adapter（33）是必要的兼容层。UIA 引擎（34）内部的命令队列是唯一需要裁撤的过度工程。
