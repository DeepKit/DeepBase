## 〇、这件事和你之前处理的「双重编码乱码」不是一回事

这点必须先讲清楚，否则会用错方法：

| | 双重编码乱码（S0/S1/S2） | **本单丁类** |
|---|---|---|
| 成因 | GBK 误读 UTF-8 后再编码 | 有损编码转换，**字符被替换成 U+FFFD** |
| 可逆性 | **可逆**（`encode('gbk').decode('utf-8')` 能还原） | **不可逆**（原字符已被 `EF BF BD` 覆盖） |
| 后果 | 注释/字符串看起来是乱码，**仍能编译** | **字符串右引号消失 ⇒ E2052 编译失败** |
| 处置 | 脚本还原 + 人工复核 | **只能人工按上下文补回** |

⇒ **不要试图写脚本批量还原本单这 4 处。** 它们只能人工补。

## 二、必做三件事

### 2.1 逐件确认损坏形态（不要跳过）

对 4 处逐一取**字节**（不是字符），确认：
- 引号究竟是被 `EF BF BD` 覆盖，还是被某个单字节 `?` 覆盖；
- 同一行还有没有其他字符一并丢失（**引号可能不是唯一的被害者**）。

### 2.2 按上下文补回，并写清依据

- 补回什么字符必须**有依据**（如：多语言 demo 的字符串应在语言表里有一致的原文；`TestLLMClient` 的字符串应与 LLM 配置键对应）；
- 每处在回执里写明：「补回的是 X，依据是 Y」；
- **禁止**：为了编译通过而随便加一个引号、或整段删掉、或改成空串——那会把损坏从「编译期可见」降级为「运行期不可见」，更糟。

这 4 件 **不在** 你先前的双重编码还原清单（50 文件 / 850 行）内 —— 说明**当初那次扫描的面漏了它们**。
