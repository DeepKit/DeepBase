## 一、背景

主控在复核甲 A-1 证据 `06-bypass-grep.txt` 时发现文件内嵌乱码 `'鏃ュ織瀵煎嚭 - '`，溯源得：

```
Tools/LogAnalyzer/LogAnalyzer.MainForm.pas:997
  实际字节： ... '\xe9\x8f\x83\xe3\x83\xa5\xe7\xb9\x94\xe7\x80\xb5\xe7\x85\x8e\xe5\x9a\xad - ' ...
  该文件：valid_utf8 = True, U+FFFD = 0, NUL = 0, BOM = True
```

`鏃ュ織瀵煎嚭` 即「日志导出」经 **GBK 误读 → 以 UTF-8 重编码** 的双重编码乱码。

**门禁缺口**：`check_pas_encoding.js` 现行检测面为 `非法UTF-8 / U+FFFD / BOM / NUL / 孤立CR`，**对合法 UTF-8 的双重编码乱码零感知** ⇒ 该文件在 `973 个 .pas 全部通过 / EXIT=0` 的绿单之内。这与乙 R7 的 S-1「内容级乱码（合法 UTF-8 双重编码，门禁抓不到）」是**同机制、同类缺陷**，且不是孤例。

## 三、本单交付面（两件，**只改门禁 + 只报清单**）

### 3.1 P2-1 门禁盲区收口（乙域，可改）

在 `09_工程脚本/encoding-gate/check_pas_encoding.js` 增检测类 **G6：双重编码乱码**：

- 判据（须同时满足，避免误报）：① 行内含中文；② 整行 `gbk → utf-8` 可逆；③ 行内含**双重编码高频标记字**（如 `鈥 锛 銆 鐨 涓 鍜 鏄 鍑 鐢 鏈 绠 鎴 缁 璇 鍔 鍏 鍥 鏂` 明确子集）≥1;
- 退出码沿用既有语义：**0 通过 / 1 违规 / 3 扫描自身失败**;
- **必须增负样本**：构造一个只含 G6 违规（无 U+FFFD / 无非法 UTF-8 / 无 NUL / 无孤立 CR）的 fixture，证明「修 G6 前该样本假绿、加 G6 后必红」;
- 与 P1 §〇 的 fail-closed 修复保持同源（计数 0 ⇒ EXIT≠0）。

### 3.1b 附带修正：命名冲突（主控代码审阅发现，1 行级）

`check_pas_encoding.js` 的单文件读取失败分支现打印 `G6 读取失败: <rel>`，但该类文件既有的检测类是 **G1–G5**，**没有 G6**。本单 §3.1 恰好要把 **G6 指派给「双重编码乱码」** ⇒ 若不动，同一门禁里 `G6` 会指向两件事（读取失败 / 双重编码），后续取证必踩坑。

**要求**：把读取失败分支的标签改为不冲突者（如 `G0 读取失败` / `READ-FAIL`），与 §3.1 的 `G6` 互斥。

### 3.3 门禁参数解析 fail-open 残留（同源，需一并收口）

`check_pas_encoding.js` / `check_eol.js` 的 `arg(name, dflt)` **静默丢弃未识别参数**（`process.argv.indexOf('--'+name)` 不命中即回落默认值）。后果：用户写错根参数（如 `--rot <path>`）时门禁**不报错**，而是回落到仓库根继续扫描并**用真实计数报「通过」** ⇒ 用户以为「我指定的根通过了」，实际根本没扫它。

P1 §〇 已堵住「扫到 0 个」这一路（EXIT=3），但**「根非空且不是用户想要的那个根」这一路仍开着**。属 甲回执 §六/11 登记项的实际归属。

**要求**：未知 `--xxx` 参数 ⇒ **EXIT≠0 并打印该参数**（fail-closed）；正向证据须含「传错参数名 → 拒绝」的实弹输出。

## 七、★ RE-OPEN：§3.3 补做（乙按本节直接开工）

> 打的不是「流程不完」，是**洞没堵上**：门禁仍然会在「你指定的目录」和「它实际扫的目录」不一致时报通过。

### 7.1 打回依据（主控实测，可复现）

```
编码门禁：--root D:/definitely-not-here  ⇒ EXIT=3  ✅（正确：读不到目录，fail-closed）
编码门禁：--ROOT D:/definitely-not-here  ⇒ EXIT=0  ❌「编码门禁通过：975 个 .pas …」
编码门禁：--Root D:/definitely-not-here  ⇒ EXIT=0  ❌ 同上
行尾门禁：--root D:/definitely-not-here  ⇒ EXIT=3  ✅
行尾门禁：--ROOT D:/definitely-not-here  ⇒ EXIT=0  ❌「行尾门禁通过：检查了 1451 个文件」
行尾门禁：--rot . / stray / --root（缺值）⇒ EXIT=0  ❌（该文件 参数校验命中数 = 0，本单零改动）
```

**两处根因**：

1. `check_eol.js` **本单零改动**（工单 §3.3 点名的是 `check_pas_encoding.js` **与** `check_eol.js` 两张门禁，实际只改了前者）;
2. 编码门禁校验侧 `raw.slice(2).toLowerCase()` 把 `--ROOT` 归一为「已知参数」**放行**，而取值侧 `arg()` 用**大小写敏感**的 `indexOf('--root')` ⇒ **落空 ⇒ 静默回落默认仓库根**。代码注释 `:34` 写「`--ROOT` …**应报错**」，实现却接受它 —— **注释与实现相反**。

### 7.2 补做要求

| # | 要求 |
|---|---|
| 1 | 两张门禁**共用同一份参数校验实现**（抽成单一函数 / 单一模块引入），**禁**两份等价物各自维护 |
| 2 | 大小写变体（`--ROOT` / `--Root=`）**二选一**：(a) 一律 `EXIT=3`；(b) 作为别名接受 —— 但**取值侧必须同步归一**。**绝对禁止**「验证器接受、取值器不认」 |
| 3 | 补做须覆盖 5 类：未知参数 / 缺值 / 裸位置参数 / 大小写不符 / 值形似参数 |
| 4 | `check_eol.js` 与 `check_pas_encoding.js` **各**留一份 5 类负样本输出 |

### 7.3 决定性验收判据（主控复验时逐条实跑）

1. `--ROOT <不存在目录>` ⇒ **EXIT=3**（不是 0）;
2. `--ROOT <存在目录>` 若被接受 ⇒ **必须真的按该目录扫描**（用「该目录 .pas 计数 ≠ 975」来反证，不得回落默认根）;
3. `--rot .` / `stray` / `--root`（缺值）在**两张门禁**上均 **EXIT=3**;
4. 两张门禁正向仍 EXIT=0，且扫描计数与仓规模同量级（975 / 1451 量级，非 0）。
