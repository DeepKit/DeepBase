## 一、背景（主控已安全复现，未触碰真实基线）

`check_eol.js --emit-baseline` 的实现是「**从空基线起算，只写本次扫到的违规**」。实测（用 `--baseline` 指到临时路径）：

```
--root ./docs --emit-baseline  ⇒ 写成 { pas_lf 0, mixed 0, md_crlf 116 }    ← 在库 902 项 → 116 项
--root .      --emit-baseline  ⇒ 写成 { pas_lf 658, mixed 25, md_crlf 203 } ← 比在库基线还少 9 项
```

后果：

1. **窄根 = 大规模丢数据**（902 → 116）;
2. **扫描集合与实仓不一致时 = 直接写空**（12:22 那次 225 B 的空基线正是这种形态，行尾门禁当场 886 项红）;
3. **即使全根也会静默减少**（−9 项）;
4. **无确认、无备份、无「不允许变小」的守卫**。

> 12:22 事故的**归属不从本单追查**（Git 无工作树写审计，无法从产物反推执行方，主控不接受无证据指认）。本单只做一件事：**让这种事不可能再发生**。

## 二、交付面（三件，同一文件族）

### 2.1 守卫一：**不得在"扫描集合不完整"时写基线**

`--emit-baseline` 必须**先自证扫描面完整**，否则拒绝写入并 `EXIT≠0`：

- 扫描到的 `.pas` 数量与**仓规模同量级**（与门禁正向跑的计数一致，允许小幅差异但**不得为 0 / 个位数**）;
- ROOT 必须是**仓库根**（或显式 `--allow-narrow-root` 才放开，且放开时打印告警）;
- 不满足 ⇒ `EXIT≠0`，**不写文件**。

### 2.2 守卫二：**不得让基线变小**（除非显式确认）

- 计算「旧基线各类条目数」与「新基线各类条目数」;
- 若**任一类变小** ⇒ 默认 **拒绝写入 + EXIT≠0**，并打印「从 X 项降到 Y 项，疑似扫描面不完整」;
- 仅在显式 `--force-shrink` 时才允许，且**必须先写备份**（见 2.3）。

### 2.3 守卫三：**写入前原子备份 + 可回滚**

- 写入前把旧基线备份为 `eol_baseline.json.bak`（或带时间戳），**先写备份再写新文件**;
- 打印备份路径，使「误写后一键还原」可操作。

### 2.4 附带：`--emit-baseline` 与门禁判定互斥（可选）

若实现成本低：同一次进程里 `--emit-baseline` 与「输出 PASS/FAIL 判定」不得同时发生（避免"边改基线边报绿"）。

## 三、验收判据（主控复验时逐条实跑，**用临时 `--baseline` 路径，不动真实基线**）

1. **窄根拒绝**：`--root ./docs --emit-baseline --baseline <临时路径>` ⇒ **EXIT≠0 且未写出文件**（或写出但被 2.2 拦下）;
2. **缩水拒绝**：构造一个会让条目数下降的场景 ⇒ **拒绝写入**，打印「从 X 降到 Y」;
3. **备份可用**：正常写入场景下，`.bak` 存在且内容为**写入前**的旧基线;
4. **不回归**：不带 `--emit-baseline` 时，两门禁正向仍 EXIT=0（977 / 1461 量级）;
5. **负样本**：上述 1/2 各加一条自动化负样本（防复发）;
6. **证据**：全部输出落盘，UTF-8 合规;**H15 原子提交**（`--only` / 显式 pathspec）。
