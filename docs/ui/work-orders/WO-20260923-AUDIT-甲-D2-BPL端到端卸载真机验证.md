## 一、目标（一句话）

用一个**真实可加载的最小 BPL**，端到端验证「插件卸载后该 BPL 不再被占用」，把 A18 从 `DEFERRED` 变成 `VERIFIED` 或 `VERIFIED WITH LIMITS`。

---

## 二、必做四件事

### 2.1 构建最小 BPL 夹具

- 新建一个**独立、最小**的 Delphi 包工程（`.dpk`），只导出一个空插件（实现本仓插件接口的最小实现），能编译出 `.bpl`；
- 夹具**必须是本仓构建链产物**（真实 `dcc64` 编译），**不得**用手写二进制或 mock 代替；
- 夹具代码单独目录（建议 `Tests/_fixtures/BPLUnloadMinimal/`），并在回执说明它为何是最小的。

### 2.2 端到端卸载测试（真跑）

- 用例：`Load` → 断言已加载 → `Unload` → **断言 BPL 文件不再被进程占用**；
- 判据必须是**文件层面的可观测事实**（如：卸载后能以独占方式打开/删除该 `.bpl` 文件；或 `GetModuleHandle` 返回 0），**不能只用内部计数器**；
- 至少 1 条**负向用例**：加载中（未卸载）时，独占打开/删除该 `.bpl` **必须失败**（证明检测方法本身有效，不是恒真断言）。

### 2.3 边界如实申报

若以下任一情形成立，**如实写「未覆盖」并说明原因，不得绕开**：
- Windows 上 BPL 卸载后仍被句柄占用（Delphi 包管理器行为）；
- 需要 IDE 进程内环境，独立 exe 跑不了；
- 夹具依赖第三方包无法在本仓构建。

### 2.4 永久限定的解除/收紧

- 若端到端验证**通过** ⇒ 回执中提出**解除**「不得声称插件卸载安全已解决」的申请，由主控裁定；
- 若**部分通过/有条件通过** ⇒ 提出**收紧后的限定表述**（如「单插件独立卸载已验证；依赖链存在时的卸载未验证」）；
- 若**不可行** ⇒ 维持永久限定，并把不可行的技术原因写进 `CodeReview` 供后续查阅。
