## 3. 按代码性质分布

| 性质 | 乱码行数 | 风险定级 |
|---|---:|---|
| 测试断言里的中文字面量（直接参与结果比对） | 主要部分 | **中**——乱码可能被当成「期望值」写死，掩盖真实失败 |
| 注释与文档头（不影响运行） | 主要部分 | 低——仅可读性损伤 |
| 运行时 UI 文案常量（`const`/字符串字面量） | 次要部分 | **中**——用户可见界面出现乱码 |
| 工具/CLI 输出文案 | 次要部分 | 低-中 |

关键风险点：测试文件里的乱码**若被当成期望值写死**，则该断言恒真或恒假，属于「假绿/假红」母题的变体。
门禁只负责拦住新乱码、并对存量登记防新增；存量值本身的真伪需各文件属主另行核对。

## 5. 机制与教训

乱码生成机制固定为：

```
原始中文 → UTF-8 编码（每字 3 字节）
         → 被按 GBK 逐 2 字节误读
         → 得到一串「看起来像中文的汉字」（实际是两字节拼出的码位）
         → 该乱码串再按 UTF-8 正常写入文件
```

结果文件是**完全合法的 UTF-8**：无 NUL、无 U+FFFD、有 BOM、行尾正常。
因此 G1（U+FFFD）、G2（非法 UTF-8）、G3（缺 BOM）、G4（NUL/UTF-16）、G5（孤立 CR）
五项判据对该损坏**零感知**——这正是门禁的盲区。

唯一可靠的判据是**可逆性**：行内汉字能整体 GBK 编码回原字节、并再按 UTF-8 解码出中文，
⇒ 该行本就是 GBK 误读的产物。该判据精确度经抽样验证（简述见请求审核报告 §3）：

- 命中样本还原后 100% 为通顺中文，无抽样假阳；
- 干净中文行的 UTF-8 字节**无法**通过 GBK 严格双字节解码 ⇒ 天然不命中（含 GBK→UTF-8 经典乱码
  「锟斤拷」的 fixture 实测命中 0 行，`Test.DeepBase.Encoding.Fix.PBT.pas` 三份副本同样命中 0）。
