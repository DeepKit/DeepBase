## 一、背景

全库 **50 个 `.pas` 文件、850 行**存在双重编码乱码（原 UTF-8 被当作 GBK 误读后再以 UTF-8 存盘）。典型：

```
鏃ュ織瀵煎嚭  →  日志导出        （Tools/LogAnalyzer/LogAnalyzer.MainForm.pas）
鏍稿績鎺т欢    →  核心控件        （Tests/GUI/Test.GUI.Core.pas）
```

其中 `Tools/Studio/Studio.Resources.pas`、`Examples/Templates/DocManager/**`、`FMX/DeepBase.FMX.*` 属**用户可见字符串**（界面文案/资源串），`Tests/**` 属**测试字面量**。

## 三、修复要求（三条硬约束）

1. **人工复核后落盘**：门禁 `--` 提供的「还原输出」只是**输入**，**不得自动批量回写**。每个文件改完须**肉眼确认还原后的中文通顺**再提交;
2. **改一个、从基线删一个**：每修复一个文件，就从 `09_工程脚本/encoding-gate/pas_encoding_baseline.json` 的 `mojibake` 段**删掉对应条目**，让 G6 立即对该文件重新生效（**基线是底线不是豁免单**）;
3. **不碰语义**：只还原乱码字符，**不改**代码逻辑、变量命名、注释含义；若某行还原后语义不明（原作者意图不可考），**保留原文并单列**到回执，不猜。

---

## 四、验收判据（分片独立验收）

1. **G6 归零**：`mojibake` 段中该分片的条目**全部删除**后，编码门禁对该分片文件**重新执行 G6 且 EXIT=0**（即"删了基线还绿"才算真修好，不是"留在基线里假装绿"）;
2. **S0 专项**：`BUG070_LogInjection.pas` / `Test.LogAnalyzer.pas` 须**明确回答**「乱码是否已被写死为期望值」—— 若已写死，说明该断言此前是否产生过假绿/假红，并修正;
3. **构建/测试**：分片改完后 `DeepBaseTests` 构建 EXIT=0，且**失败集合与改前一致**（不得因为改字符串而新增红项）;
4. **证据**：门禁原始输出 + 构建输出 + 测试失败集合对比，UTF-8 合规;
5. **提交**：**H15 原子提交**（`--only` / 显式 pathspec）。**分片可分批提交**（每批 5–8 个文件），但**禁止**与另一 owner 的文件混在同一笔。
