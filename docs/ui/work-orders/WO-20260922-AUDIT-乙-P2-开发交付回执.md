## 1. 工作内容（逐项）

### 1.1 §3.1b — G6 命名互斥修正（已完成）

**问题**：读取失败原本被标为「G6」，与 G6 的语义（双重编码乱码内容级判据）互斥——
读失败是**扫描自身失败**，乱码是**文件内容违规**，两者性质相反。混用标签会让
「门禁挂了但看不出是哪类故障」。

**修法**：读取失败改标 `G0`（`09_工程脚本/encoding-gate/check_pas_encoding.js:173`）。
G6 只表示内容级判据。已加注释说明理由，防止后人改回去。

> 注：本条在工单执行过程中已顺带完成，此处仅为留证。无回归——G0 与 G6 走同一 fail-closed 路径（退出码 3）。

### 1.2 P2-1 — G6 双重编码乱码检测（本工单核心）

**问题根因**：仓内的乱码**不是乱码版的 UTF-8**，而是「GBK 误读后以 UTF-8 正常写入」。
���物是**完全合法的 UTF-8 文件**：无 NUL、无 `U+FFFD`、有 BOM、行尾正常。

```
原始中文 → UTF-8 编码（每字 3 字节）
         → 被按 GBK 逐 2 字节误读
         → 得到一串「看起来像中文的汉字」（实际是字节拼出的错误码位）
         → 该乱码串再按 UTF-8 正常写入文件
```

因此 G1（`U+FFFD`）、G2（非法 UTF-8）、G3（缺 BOM）、G4（NUL/UTF-16）、G5（孤立 CR）
五项判据对该损坏**零感知**——这就是门禁盲区。

**修法**：新增 G6 判据，判据是**可逆性**——
行内汉字若能整体 GBK 编码回原字节、并再按 UTF-8 解码出中文，则该行本就是 GBK 误读的产物。

**实现位置**：`09_工程脚本/encoding-gate/check_pas_encoding.js:104`（G6 主逻辑）、
`:187`（装配点）。不依赖 ICU 可用性：Node 无 GBK 解码支持时**fail-closed 退出码 3**，
绝不静默跳过 G6（`:124-125`）。

**存量处置**：存量 50 文件 / 850 行登记为基线 `mojibake` 段
（`pas_encoding_baseline.json`）。**基线是底线不是豁免单**——修一个文件就从
`mojibake` 删掉对应条目，门禁立即对该文件重新执行 G6。本条已验证（见 §3 双向留证）。

**基线变更纯洁性**（已逐键核验，非猜测）：

| 基线键 | HEAD | 工作树 | 是否改动 |
|---|---:|---:|---|

### 1.3 §3.3 — 门禁参数解析 fail-open 收口（已完成）

**问题**：拼错/传错的 `--xxx` 被静默忽略 ⇒ 门禁按**缺省 root** 跑通并报 `EXIT=0`，
让「我按指定 root 扫过了」变成假象。典型事故：`--rot` 拼错 → 按缺省 root 跑 →
绿单覆盖了实际未被扫描的目录。

**排查中实测发现 4 条同源裂缝**（工单原文只点了 `--rot` 一处，实测是同源 4 例）：

| # | 输入 | 修前行为 | 修后 |
|---|---|---|---|
| 1 | `--rot` | 静默忽略，EXIT=0 | EXIT=3 未知参数 |
| 2 | `--Root:x` | 静默忽略，EXIT=0 | EXIT=3 未知参数 |
| 3 | `--root` / `--baseline`（**缺值**） | 回退缺省值，EXIT=0 | EXIT=3 缺值 |
| 4 | `--root=x --root` | 后一个被当 path 吞掉，EXIT=0 | EXIT=3 缺值 |

另收口 2 项：裸位置参数（`stray`）与大小写不符（`--ROOT`）。共 6 类一律 `EXIT=3`。
保留合法形式：`--root <dir>`、`--root=<dir>`、`--baseline <file>`、`--baseline=<file>`、`--help`。

**CI 安全性**：`delphi-ci.yml:50` 以**无参数**方式调用，不受本次收紧影响。
