## 〇、背景：这个门为什么必须有

S-3 事故的完整链条（见 `CodeReview\20260921-AUDIT-主控-乙-P0-HEAD编译断裂修复-请求审核报告.md`）：

1. 某笔提交让 **HEAD 全库不可编译**（E2003 / E2034 / E2250 / E2035）；
2. **没有任何机械门在拦它** ⇒ 不可编译的状态在仓库里躺了若干天，直到人工撞见；
3. 后果：全量测试套件**跑不起来**，甲乙两条线的验收全部卡死。

根因双源已查明：E2034/E2250/E2035 ← `9387222`（Top20#05）；**E2003 ← `1a85e92`**。而**让它们能躺几天不被发现的，就是缺这道编译门**。

⇒ 这不是「多一道检查」的锦上添花，是**验收证据链的底座**：没有编译门，「全量回归绿」这句话随时可能是假的。

---

## 一、目标（一句话）

把「全库 `.dpr` 必须能编译」做成**可机械执行、fail-closed、能进门禁族**的一道门，并且**判据是隔离工作树 @ 目标 commit**，不是共享工作树。

---

## 二、必做五件事

### 2.1 门禁脚本本体

新增 `09_工程脚本/build-gate/check_build.js`（或同族命名，与既有 `encoding-gate` / `eol-gate` / `evidence-encoding-gate` / `managed-copy-gate` 对齐）：

- 枚举仓内**全部 `.dpr`**（或按显式清单），逐个用 `dcc64` 编译；
- 输出：每个 `.dpr` 的 `BUILD_EXIT` + 编译计数；
- **复用 `09_工程脚本/gate-args.js` 的参数解析**（乙 P2b 已建的单一实现），**不得另写一套 `arg()`** —— 验证器与取值器必须同源（这是 P2 §3.3 打回的根因，不得重犯）。

### 2.2 fail-closed 三条（硬性，照抄既有门禁的成功修法）

| 情形 | 必须 |
|---|---|
| `readdir` 任一子树失败 | **EXIT≠0**，并打印失败路径 |
| 待编译 `.dpr` 计数为 **0** | **EXIT≠0**（空扫描不是通过） |
| 任一 `.dpr` `BUILD_EXIT≠0` | **EXIT≠0**，打印该 `.dpr` 与首个错误行 |

**禁止**任何形式的「跳过并继续报绿」。

### 2.3 输出必须自带可核数字

输出行须含：**被编译的 `.dpr` 总数 / 成功数 / 失败数 / 被跳过或失败的子路径数**。
⇒ 让「扫描计数 > 0 且与仓规模同量级」成为**一眼可核**的事实（P1 §〇 的教训：只看 EXIT 不算取证）。

### 2.4 负向样本（`test_negative_sample.js`，同族必备）

至少 3 例，全部**必须红**：

1. 指向不存在/写错的根 ⇒ **必须红**（防空绿）；
2. 空目录 ⇒ **必须红**；
3. **故意引入语法错误的 `.dpr`** ⇒ **必须红**（证明编译真在跑，不是只做文件枚举）。

### 2.5 隔离工作树口径写进说明

门禁说明里写死：**提交段的编译判定 = 隔离 `--detach` 工作树 @ 目标 commit 的 EXIT**；共享工作树结果只用于「有没有动别人的东西」的现场观察，**不作判定**。
（该口径已在 R8-P3 裁定 3 采纳，本单把它从口头口径变成门禁文档里的一行字。）

## 四、成本提示（如实告知，不要硬扛）

全库编译耗时约 **20 分钟量级**。本门**不建议**在每次小提交时全量跑；建议形态：

- 门禁说明里写清两种模式的**适用场景**，不要让它变成「没人愿意跑所以被绕过」的门。
