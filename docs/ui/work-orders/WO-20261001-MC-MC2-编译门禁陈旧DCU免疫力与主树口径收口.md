## 二、机制（主控 2026-10-01 坐实，五步链，每步可复算）

1. **符号曾在 `Security.pas`**：`git show 9387222~1:Core/DeepBase.Security.pas` 的 `:124-125` 原声明两个重载——
   `procedure SecureZeroMemory(var Data: TBytes); overload;` 与 `procedure SecureZeroMemory(var Data: string); overload;`。
2. **`9387222`（2026-09-20 19:24，Top20#05）把它们搬走**：新建 `Core/DeepBase.SecureMemory.pas`（SSOT，现源码恰为 `:19` TBytes / `:22` string 两个重载、无第三声明）并从 `Security.pas` 删除（当前源码对 `SecureZeroMemory` 0 命中）。⇒ **现行源码自洽，无源码侧歧义**。
3. **主树残留提交前的陈旧 dcu，且二进制内确含该符号**（原始 `grep -a`，非 `strings`——本环境 `strings` 提取无效，已用正对照证伪该方法：`TestResults/p1-dcu/DeepBase.SecureMemory.dcu` 用 `strings` 0 命中、原值 grep 6 命中）：
   - `TestResults/dcu32/DeepBase.Security.dcu`（mtime 2026-09-20 12:12，提交前 7 小时）——含；
   - `TestResults/dcu64/DeepBase.Security.dcu`（2026-09-14）——含；
   - `BuildOutput/dcu/Win64/DeepBase.Security.dcu`——含；
   - （`dcu/` 与 `TestResults/p1-dcu/` 下的同名件为提交后版本，不含 ⇒ 与时间线吻合。）
4. **搜索顺序把陈旧件排在源码前**：`09_工程脚本/build-gate/check_build.js` 的工程上下文中 `searchPaths: [...dproj 声明目录, env 目录]`（`:619`）——**dproj 声明目录在前**；而多个 dproj 的 config 联合（`DeepBaseCommerce.dproj:18/24` 等）声明了 `TestResults\dcu32;TestResults\dcp32` 与 `TestResults\dcu64;TestResults\dcp64`，**先于** UNIT_DIRS 的 `Core`。
5. **触发路径**：`DeepBase.Security` 由 `DeepBaseCore.dpk:90` contains（不是 `DeepBaseServices` 的 contains）⇒ 编译 `DeepBaseServices.dpk`（`:32` contains `Core\DeepBase.Security.DPAPI.pas`，`-B` 强制从源码重编该单元）时，其 `uses DeepBase.Security` 命中**陈旧 dcu** ⇒ DPAPI 作用域内同时有「陈旧 Security 的两个重载」与「现行 SecureMemory 的两个重载」⇒ `SecureZeroMemory(FData)`（`FData: TBytes`，`:136` 声明）匹配两个 TBytes 精确候选，无一更优 ⇒ **E2251**。

⇒ 结论：**E2251 是门禁被本机陈旧构建残留劫持的表现，与源码质量无关**；但门禁若无条件依赖机器状态，隔离树绿 = 主树红，验收口径就被迫永久绕行——这是本单要收的口子。
