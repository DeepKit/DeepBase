## 二、三案对照（每点给成本 / 可逆性 / 影响面）

### DP-1 路线批准

| 方案 | 成本 | 可逆性 | 影响面 |
|---|---|---|---|
| (a) 批准 | 触发 MOE-01/MOE-02/MOE-05 三张取证单（已可开）+ 后续 MOE-06 | 高（证物单本身零代码；实现单可停在探针） | 需先补 5 处表述缺口（G1–G5）与 3 处自相矛盾（C1–C3） |
| (b) 不批准 | 0 | — | 讨论包归档；三态标注与工单族留档作为后续复盘素材 |
| (c) 延后待证 | 仅 MOE-01 的 S 档 | 高 | 事实底盘先建，路线决策后置 |

**我方倾向 (c)，但倾向不构成建议采纳**：14 条待证项里 8 条是外部标杆数字，本仓零镜像零 vendored 源码，**在事实未核前给路线背书等于给未核数字背书**。

> **2026-10-02 更新（MOE-EV 取证后，(c) 的前置已完成）**：14 条待证项已全部裁定 —— **已核 2 条（E1 2.78T@8.24GB、E3 896/top-16）/ 不可核 12 条**，其中 E6（内存硬顶）、E13（与 PyTorch 字节级一致）、E14（8→64 GB 平滑过渡）被上游**自身数据**证伪。取证单见 `CodeReview/20261002-AUDIT-甲-MOE-EV-取证结论.md`。
>
> **DP-1 呈报必须附上的本方硬约束**（不依赖任何外推，只依赖「1,472 专家 × 17.5 MB」这一个架构常数）：本机（AMD Ryzen 7 3700X / 8 物理核 / 63.95 GB / 无独显）在**只做 MoE 专家 MLP 这一层**（不含 trunk、KDA/MLA、路由、采样、磁盘流式）就要 **24.12 s/token**（3 组中位），比上游 124 核机器「**全模型**」最好档 19.21 s/token **还慢 1.26 倍**；且 trunk 全量常驻需 108.81 GB，本机 63.95 GB **装不下 ⇒ 必须流式**。讨论包 §4.1「15~35 tok/s」经机器判定**缺 5 项基线**（硬件 / 量化格式 / 模型形状 / 重复次数 / 离散度）⇒ 不可复算，不可作本决策的依据。
>
> ⇒ **(c) 已无等待价值**（其唯一价值是「先建事实底盘」，而底盘已建完）。现在必须在 (a) 批准 / (b) 不批准 之间真选一个。

### DP-5 Phase 1 判据订正（新增决策点，讨论包未提）

> **2026-10-02 升级（MOE-EV 取证后）**：本决策点已从「我方建议改」升级为「**有上游原文支撑的必须改**」——上游自己与 torch 的比对就是 elementwise + 容差，且上游公开的 byte-identical 说的是 token id 层。下面三条原文见 `CodeReview/20261002-AUDIT-甲-MOE-EV-取证结论.md` E13。

**先决事实（三条原文 + 一条工程推论）**：

1. 上游 ARCHITECTURE.md 的 correctness 段：「**numeric level**: logits from the released 93-layer checkpoint compared **elementwise** against a **torch reference**」⇒ **与 torch 是逐元素 + 容差，不是字节级**。
2. 上游公开的 byte-identical 是**另一件事**（上游 PERFORMANCE.md）：「Every row produced byte-identical output: `17374, 20829, 10, …`」「byte-identical output at **all twelve budgets**」⇒ 指的是 **token id 序列跨 12 档预算一致**。
3. 上游 replication.tsv 三次运行 s/token 分别 14.7760 / 14.6655 / 20.1408（**离散 33.1%**），而 **ids 三次完全相同** ⇒ 确定性体现在 **token id 层**，与墙钟无关。
4. 工程推论：讨论包 §5 Phase 1 判据 3「验证与 PyTorch 参考输出字节级完全一致」与 §1.5/§6-G3「零依赖、不引入 Python」**自相矛盾**；且浮点 GEMM 的累加顺序/FMA 融合/编译优化都会改变末位，**「字节级完全一致」在工程上不可达**。

| 方案 | 成本 | 可逆性 | 影响面 |
|---|---|---|---|
| (a) **改为「与发起方一次性提供的固定 token id 序列逐位相同」**——这正是上游真正做到并公布的那件事；PyTorch 只作**离线数据来源**，不进构建与运行链；若另需数值精度判据，用 elementwise 相对误差 + 显式阈值 | S | 高 | **阈值需老板给**（例：`<= 1e-2` 相对误差 for fp32 accumulate）。注意 (a) 已不是「新造标准」，而是**采用上游已验证的标准** |
| (b) 保留原判据 | 0 | — | Phase 1 验收判据不成立 ⇒ 单子会卡在验收门上；且会在验收时才发现「判据本身没被执行过」，浪费一个 WP |
