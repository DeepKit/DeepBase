## 〇、缺陷陈述

**证据件可以在门禁全绿的状态下，自身带着门禁明令禁止的内容**——因为证据件是在跑门**之后**才写出来、
才入库的，门禁从没扫过它。

| 方 | 事件 |
|---|---|
| **主控** | CI 证据件 `CodeReview/20261002-AUDIT-主控-CI-证据/01-shell修复前后-五门读数.txt` 第一版为「展示根因」逐字抄录了 5.1 误读产生的乱码路径字形。该串合法 UTF-8、无 NUL、无 U+FFFD ⇒ E1/E2 零感知，但整行可逆回 GB18030 且还原出中文 ⇒ 正是 evidence-encoding 门的 **E3（双重编码乱码）**判据。**该件一入库，门禁立刻点名它判失败**。已修（改按码位转义记载），提交 `866fa42` |
| **甲** | `WO-20261002-MC-甲-MOE-EV` 回执 §六 记 evidence-encoding 扫 **1235** 件 `EXIT=0`；而其最终 HEAD 实为 **1243** 件 ⇒ **少 8 = 甲自己的 8 件 CodeReview 交付件**，门禁没扫它们 |

**根因同一个**：evidence-encoding 门（及其余四门）的默认口径只扫 **git 已跟踪**文件。
「先跑门 → 再写交付件 → 再提交」的顺序下，**跑门那一刻的绿，对交付件本身不构成任何保证**。

## 一、正确口径（本单要立成的规矩）

1. **跑门前先 `git add`**（交付件进 index 即被 `git ls-files` 覆盖），再跑门；或
2. evidence-encoding 门用 `--all-worktree` 走工作树枚举（主控亲测可用，该 flag 已存在）。

⇒ 两者取其一。**回执/结论件里的门禁读数必须能回答「这次扫到几个文件、其中是否包含本单自身交付件」**。

## 二、顺带立一条：退出码不许经管道读

同一轮里主控还踩到：`node <门> 2>&1 | tail -2; echo $?` 拿到的是 **`tail` 的退出码**，不是 node 的。
CI 工单第一版五门读数正是这样把红读成 0 的。
⇒ 门禁退出码一律**子进程 `returncode` 直取**（Python `subprocess.run(...).returncode`，或 pwsh `$LASTEXITCODE` **且不经管道**）。
