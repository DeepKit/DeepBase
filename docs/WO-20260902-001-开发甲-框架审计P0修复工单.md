## 三、修复项明细

### FIX-1 · DB.Pool Shutdown 超时后仍释放 csInUse 连接（P0 · UAF/堆损坏）

- **位置**：`D:\_Progs\02Business\DeepBase\Persistence\DeepBase.DB.Pool.pas:1067-1095`

- **现状**：Drain 循环最多等 `FConfig.AcquireTimeoutMs`；超时后无条件 `FPool.Clear`。`FPool` 是 `TObjectList<TPooledConnection>` 且 owns objects（`:929` Create(True)），Clear 会 Free 仍在 `csInUse` 的连接对象，而调用方仍持有该连接引用 → UAF/堆损坏。

- **修复要求**：

  - 超时后**跳过** **`csInUse`** **连接**（不释放、留在池记录中），仅释放非 in-use 连接。

  - 对被跳过的连接记录错误日志（含连接标识），明确报告"泄漏而非崩溃"的取舍：关闭路径上泄漏优于 UAF。

  - 保持既有 `FInitialized := False` 语义。

- **验收**：新增回归测试——构造 1 个 `csInUse` 连接 + 超短 AcquireTimeoutMs 触发超时路径，断言该连接对象未被 Free（用 weak 引用/标记对象验证），且 Shutdown 正常返回。

### FIX-2 · DB.Guardian 任意 Open 失败即 quarantine（P0 · 静默数据回滚）

- **位置**：`D:\_Progs\02Business\DeepBase\Persistence\DeepBase.DB.Guardian.pas:398-431`

- **现状**：`AConn.Open` 抛任何异常一律判 `isCorrupted` 并 `QuarantineAndRecover`。SQLite busy/locked 等瞬态错误会被误判为损坏，触发备份回滚 → 静默数据回滚。

- **修复要求**：

  - 对 Open 异常做错误分类：仅结构性损坏（如 `SQLITE_CORRUPT`、`database disk image is malformed`、`file is not a database`、`file is encrypted` 等）走 quarantine；busy/locked/网络类瞬态错误返回 `isUnknown`/降级状态并保留原库，不 quarantine。

  - 分类函数按数据库类型（SQLite/MySQL/PG）分支实现，错误关键字常量集中一处（SSOT），不要散落 if 链。

  - 瞬态失败路径要有明确日志。

- **验收**：新增回归测试——模拟 busy/locked 异常消息，断言不触发 quarantine、`RestoredFromBackup = False`、原 DB 文件未被移动。

### FIX-3 · Scheduler FRunningITask 提前置 nil（P0 · Cleanup 并发 UAF）

- **位置**：`D:\_Progs\02Business\DeepBase\Core\DeepBase.Scheduler.pas:1032,1087`

- **现状**：`:1036-1042` 注释明确要求 FRunningITask 保留到回调之后（Cleanup `:1217` 用它做存活守卫），但成功路径 `:1032` 与失败路径 `:1087` 都在锁内、回调调用**之前**置 nil。窗口期内 `Cleanup` 可 Remove+Free 任务，回调仍持有 TaskRef → UAF。

- **修复要求**：

  - 将 `FRunningITask := nil` 移到 `LOnCompleted`/`LOnFailed` 回调**返回之后**执行（回调在锁外调用，清 nil 需重新进锁）。

  - 成功/失败/重试三条路径都要核对：只要回调还在用 TaskRef，守卫就必须非 nil。

  - 同步修正与实际不符的注释。

- **验收**：新增回归测试（BUG326 扩展）——注册 OnCompleted 回调，回调内触发 `Cleanup` 并断言 TaskRef 仍可安全访问（如读取 FId），回调返回后 Cleanup 能正常清除任务。

### FIX-4 · FileWatcher Debounce 捕获裸 Guard（P0 · 析构后 UAF）

- **位置**：`D:\_Progs\02Business\DeepBase\Core\DeepBase.FileWatcher.pas:851,870-889`

- **现状**：`HandleDebounce` 中 `LGuard: TFileWatcherGuard` 为裸类引用，被匿名 TTask 捕获；Watcher 释放后任务执行 `LGuard.GetWatcher` → UAF。注释声称"keeps guard alive"但裸引用不保命。

- **修复要求**：同文件 `NotifyChange`（`:671` `LGuard: IInterface` + `:676` ref-count bump）是正确范本——照此将 `HandleDebounce` 的局部变量改为接口引用，捕获即增引用计数。

- **验收**：新增回归测试（BUG320 扩展）——注册带 debounce 的 watch，立即 Free watcher，等待超过 DebounceMs+10ms，断言无 AV（用进程存活/异常捕获断言）。

### FIX-5 · WorkerQueue Stop(False) 不 WaitFor 即 Clear（P0 · 工作线程 UAF）

- **位置**：`D:\_Progs\02Business\DeepBase\Core\DeepBase.WorkerQueue.pas:2149-2177`

- **现状**：`Stop(False)` 只 `Terminate` 不 `WaitFor`，随后 `FWorkers.Clear`（列表 owns 线程）→ 释放仍在运行的线程对象 → UAF。

- **修复要求**：

  - `AWaitForCompletion=False` 的语义应是"不等待**任务队列**排空"，而非"不等待**线程**退出"。两个分支都必须在 Terminate 后 WaitFor 再 Clear。

  - 排查同文件**缩容路径**及 `DrainAndStop` 是否存在同样 Terminate→不 WaitFor→释放的模式，一并对齐「Stop → Drain → Wait → Free」顺序。

  - 若担心 WaitFor 阻塞，可加带超时的 WaitFor + 泄漏并日志（对齐 FIX-1 取舍），禁止无等待释放。

- **验收**：新增回归测试——入队长任务后立即 `Stop(False)`，断言 Destroy 全程无 AV 且线程对象安全终止。

### FIX-6 · KeyManager GCM 边界 off-by-one（P0 · 功能错误）

- **位置**：`D:\_Progs\02Business\DeepBase\Core\DeepBase.KeyManager.pas:1075`

- **现状**：`(Length(AData) > 1 + 12 + 16)` 严格大于。空明文 GCM 包恰 29 字节（版本 1 + Nonce 12 + 密文 0 + Tag 16），会误走 legacy CBC 分支 → 解密失败。

- **修复要求**：改为 `>= 29`。同时确认 legacy CBC 分支的 `Length <= 16` 排除逻辑不与新边界产生交叠歧义。

- **验收**：新增回归测试——`Encrypt(空 TBytes)` → `Decrypt` 应返回空 TBytes 且走 GCM 分支（可断言密文长度 = 29 / 首字节 $02）；空字符串 `EncryptString('')` round-trip 同样覆盖。

### FIX-7 · WeChat4x 指纹前缀非 hex（P0 · 适配器永不命中）

- **位置**：`D:\_Progs\02Business\DeepBase\Core\DeepBase.SchemaAdapter.WeChat4x.pas:75-79`

- **现状**：`FSchemaFingerprintPrefixes := ['4x7f2a9b1c']` 含非 hex 字符 `x`；SHA256 hex 摘要不可能含 `x`，`TryMatchFingerprint`（`DeepBase.SchemaAdapter.pas:251`）永不匹配 → 4.x 适配器永不被 registry 选中。代码注释自认是占位符（待 DATA-P0-001 目标机 dump）。

- **修复要求**：

  1. 在 `Validate`（或构造）中加入指纹前缀 hex 合法性校验：非 \[0-9A-Fa-f] 直接 raise `ESchemaAdapterValidationError`，让此类占位符错误在加载期 fail-fast。
  2. 用 4.x `Msg_*` 表的真实 canonical column-signature 计算 SHA256 并替换占位符；计算口径必须与 registry 侧一致（同一函数派生，禁止两处各算各的）。若仓库内无真实 schema fixture 可依据，**在交付报告中标注 BLOCKED-DATA-P0-001**，保留 hex 校验交付，不得虚构指纹值。
  3. 扩展 `Tests\Regression\Test.Regression.BUG332_WeChatSchemaRegistryResolve.pas`：从 fixture 计算 SHA256 → registry resolve → 断言命中 4.x 适配器（当前测试只验长度，不验真实匹配）。

- **验收**：hex 校验生效（非法前缀构造即 raise）；BUG332 扩展测试真实走 SHA256 前缀匹配链路。若标注 BLOCKED，hex 校验 + 测试框架仍须交付。

### FIX-10 · DB.DoQry Sweep/Clear 不检查 InUseCount（P0 · UAF）

- **位置**：`D:\_Progs\02Business\DeepBase\Persistence\DeepBase.DB.DoQry.pas:1817-1829`

- **现状**：按 Connection 清理 GPreparedPool 时不检查 `Entry.InUseCount`（对比：LRU 淘汰 `:546` 与复用路径 `:614` 均已检查）。In-use 的 TFDQuery 被从池和索引摘除后，正在执行的线程仍持有它，后续 Release 归还路径找不到条目 → UAF/泄漏。

- **验收**：新增回归测试——取 In-use prepared query 后触发同连接 sweep，断言条目仍在池中、查询可正常归还。

### FIX-11 · PluginManager UnloadBPL 后接口悬垂（P0 · 插件卸载 UAF）

- **位置**：`D:\_Progs\02Business\DeepBase\Core\DeepBase.PluginManager.pas:788-810`

- **现状**：`PluginIntf := LoadedRec.Plugin`（`:791`）是本地接口引用，跨过 `UnloadBPL(PackageHandle)`（`:805`）存活到过程结束；且 `FPlugins.Remove(PluginID)`（`:808`）在 Unload **之后**才释放字典内引用。任何一次接口 `_Release` 都跳进已卸载 BPL 内存 → UAF/崩溃。

- **修复要求**：调整为——Finalize → 从 `FPlugins`/`FLoadOrder` 移除（释放字典侧引用）→ 本地 `PluginIntf := nil` → **最后** `UnloadBPL`。确保 UnloadBPL 调用时已无任何接口引用指向 BPL 内 vtable；`FirePluginUnloaded` 回调不得触碰 PluginIntf。

- **验收**：新增回归测试——加载真实测试 BPL → 卸载 → 断言卸载后接口引用计数归零、无 AV（可用进程存活 + 二次 load/unload 循环压测）。
