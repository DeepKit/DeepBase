# UniFlow：智能应用的操作系统

> 统一的 Workflow + Agent + Skill 协同层，为基于 UniBase 的应用提供"可控、可观测、可扩展"的智能流程能力。
>
> **核心使命：把 AI 从“玩具”变成“工具”。** 详见 `01.00.Product-UniFlow-核心定位-v1.0.md`

## 1. UniFlow 是什么？

### 1.1 一句话定义

**UniFlow 是一个让 AI 能力可控、可靠、可集成的运行时框架。**

从架构角度，它是"智能应用的操作系统"——为业务软件提供统一的协作、安全、记忆、扩展能力，让开发者只专注于业务逻辑。

### 1.2 核心能力

- **工作流（Workflow）**：定义与执行引擎，管理任务的完整生命周期
- **智能体（Agent）**：运行时支持 LLM + 工具循环，可控的 AI 能力接入
- **技能（Skill）**：注册与调度机制，统一调用外部能力（脚本、HTTP、LLM 等）
- **角色体系**：11 个标准化角色，覆盖智能应用的所有通用需求

### 1.3 类比理解

| 层次 | 操作系统 | UniFlow |
|------|----------|---------|
| 硬件抽象 | 驱动程序 | 适配器 / 通信官 |
| 进程管理 | 调度器 | 引擎 + 调度员 |
| 内存管理 | 内存分配器 | 后勤（资源管理） |
| 文件系统 | 文件 I/O | 记录员（持久化） |
| 安全机制 | 权限 / 沙箱 | 守卫 |
| 系统调用 | API | 军械官（Skill 注册） |
| 用户进程 | 应用程序 | 业务软件的领域代码 |

## 2. 设计原则

### 2.1 六大核心原则

1. **Workflow 优先，Agent 其次，LLM 再其次**
   - 能用确定性 Workflow 表达清楚的流程，不引入 Agent
   - 能用简单 Agent 完成的，不做复杂多层 Agent 链

2. **AI 归 AI，程序归程序**
   - Agent/LLM 负责"理解、生成、诊断、建议"
   - 程序模块负责"状态管理、权限控制、持久化、回滚"

3. **人始终在环（Human-in-the-loop）**
   - 对关键/不可逆操作，必须有 Guard + 验证链 + 可选人工确认
   - 支持 HumanTask 作为 Workflow 中的一等公民

4. **可观测、可审计**
   - 所有关键决策、Agent 行为、Skill 调用，都有统一日志和指标
   - 支持回放与审计：知道"为什么当时做了这个决定"

5. **Vendor 中立**
   - Skill / Agent 定义不依赖具体云厂商，可接入多种 LLM/工具实现

6. **简单可依赖**
   - 内核 API 和概念保持简洁，优先稳定性与可维护性

### 2.2 架构原则

| 原则 | 说明 |
|------|------|
| 角色单一职责 | 每个角色只做一类事 |
| 依赖层级清晰 | 高层依赖低层，不反向 |
| 信任边界明确 | 不信任区的输出必须校验 |
| 消息驱动协作 | 角色通过消息通信，不直接调用 |
| 状态可观测 | 所有状态可通过督察查看 |
| 故障可恢复 | 任何角色崩溃不影响整体 |
| 扩展点标准化 | 业务扩展通过定义的接口 |

## 3. 软件工程理念

### 3.1 关注点分离到极致

传统分层：UI / Business / Data
UniFlow 分层：11 个角色，每个只做一件事

```
传统：一个 Service 类里可能混合
  - 业务逻辑 + 日志记录 + 权限检查 + 缓存处理 + 错误处理 + 外部调用

UniFlow：各司其职
  - 业务逻辑 → 执行者
  - 日志记录 → 记录员
  - 权限检查 → 守卫
  - 缓存处理 → 后勤
  - 错误处理 → 调度员 + 守卫
  - 外部调用 → 通信官
```

### 3.2 契约优于实现

```
// 传统方式：调用具体类
var result = MyService.DoSomething(input);

// UniFlow 方式：通过角色接口
var result = await Executor.Execute(skillId, input);
```

好处：
- 实现可以随时替换
- 测试时可以 Mock
- 升级时不影响调用方

### 3.3 默认安全

传统方式：安全是"加上去的"——写完功能 → 想起来加个权限检查 → 可能漏掉

UniFlow 方式：安全是"内置的"
- 所有请求默认经过守卫
- 不过守卫的请求**无法执行**
- 安全是架构级保障，不是程序员记忆

### 3.4 可观测性是一等公民

- 记录员**自动记录**所有角色行为
- 督察提供**完整的运行时观测**
- 任何时候都可以查看系统内部状态

### 3.5 失败是正常的

传统方式：假设一切顺利，失败是"异常"
UniFlow 方式：假设随时可能失败，设计时就考虑恢复

- 每个 Workflow 有检查点
- 调度员知道如何重试
- 后勤可以回滚状态
- 守卫监控异常行为

## 4. UniFlow vs Vibe Coding（氛围编程）

### 4.1 什么是 Vibe Coding？

> Vibe Coding = 用自然语言描述意图，让 AI 直接生成代码/执行操作，人类主要做"感觉对不对"的判断。

### 4.2 核心区别

| 维度 | Vibe Coding | UniFlow |
|------|-------------|---------|
| **核心理念** | "说出来就能做" | "说出来，系统理解后，按规则做" |
| **人的角色** | 描述者 + 审核者 | 设计者 + 监督者 |
| **AI的角色** | 主力执行者 | 专项顾问（智囊） |
| **可控性** | 低（AI 自由发挥） | 高（流程约束 AI） |
| **可重复性** | 低（同样的话可能不同结果） | 高（同样的 Workflow 相同结果） |
| **适用场景** | 原型探索、一次性任务 | 生产系统、长期维护 |
| **失败成本** | 高（不知道哪里出错） | 低（可定位到具体角色/步骤） |

### 4.3 Vibe Coding 的问题

| 问题 | 说明 |
|------|------|
| 不确定性 | "帮我加个按钮"——加在哪？什么样式？什么行为？ |
| 难以维护 | 三个月后，谁记得当时"Vibe"了什么？ |
| 难以协作 | 我的 Vibe 和你的 Vibe 不一样 |
| 难以测试 | 怎么测试"感觉对不对"？ |
| 责任模糊 | 出了问题，是 AI 的错还是人的错？ |

### 4.4 UniFlow 如何解决这些问题

| Vibe Coding 的问题 | UniFlow 的解决 |
|--------------------|----------------|
| 不确定性 | 智囊必须输出**结构化意图**，守卫校验 |
| 难以维护 | 记录员存档**每一个决策**，可追溯 |
| 难以协作 | 角色体系是**共同语言**，减少歧义 |
| 难以测试 | 督察提供**回放、Mock、断点** |
| 责任模糊 | 每个角色有**明确职责**，问题可定位 |

### 4.5 UniFlow 对 Vibe Coding 的态度

> **不是"禁止"，而是"收编"。**

- Vibe Coding 的体验（说话就能做事）→ SoIs 层提供
- Vibe 之后的可靠执行 → UniFlow 保障

```
用户的 Vibe（自然语言）
        ↓
    SoIs 澄清
        ↓
    智囊 结构化理解
        ↓
    调度员 规划流程
        ↓
    执行者 + 守卫 可靠执行
        ↓
    记录员 全程存档
```

**Vibe 是入口，不是全部。**

## 5. 优势与劣势

### 5.1 核心优势

#### 优势 1：可控的智能

| 对比维度 | 纯 AI 驱动 | UniFlow |
|----------|------------|---------|
| 决策者 | AI 自主决策 | 程序主导，AI 辅助 |
| 可预测性 | 低 | 高 |
| 可审计性 | 难 | 易 |
| 可回滚 | 难 | 易 |

**核心理念：AI 是"顾问"，不是"老板"。**

#### 优势 2：工程化的扩展性

想换 AI 提供商？只改智囊的实现。
想换存储后端？只改后勤的实现。
想加新能力？在军械官注册新 Skill。

**业务代码永远不直接依赖具体实现。**

#### 优势 3：团队协作的语言统一

角色体系就是团队的"通用语言"：
- 开发者 A："这个 bug 是守卫没拦住。"
- 开发者 B："哦，那我去加个 Validator。"

#### 优势 4：渐进式采用

```
第一天：只用 总指挥 + 执行者 + 后勤（最小系统）
第一周：加入 守卫（质量保障）
第一月：加入 智囊 + 军械官（AI 能力）
第一季：加入 通信官 + 完整记忆（复杂集成）
```

### 5.2 核心劣势

#### 劣势 1：学习成本

- 11 个角色 + 5 层架构
- 新手需要 1-2 周理解全貌
- 文档和培训要求高

**应对：提供最小启动包 + 渐进式学习路径**

#### 劣势 2：性能开销

- 角色间通信有额外成本
- 每次请求经过多个角色

**应对：提供"快速路径"优化 + 本地直调选项**

#### 劣势 3：过度设计风险

- 简单项目可能"杀鸡用牛刀"

**应对：明确"什么时候不该用 UniFlow"**

#### 劣势 4：生态依赖

- 依赖 UniBase 基础设施
- 目前主要是 Delphi 生态

**应对：核心协议与语言无关，可逐步扩展**

## 6. 先进性总结

### 6.1 架构先进性

- 智能应用操作系统定位
- 角色化分层设计
- 消息驱动协作模式

### 6.2 安全先进性

- **零信任架构**：不信任任何角色，特别是 AI 和外部调用
- **最小权限**：架构级强制，不是程序员记忆
- **强制审计**：记录员独立，自动记录所有行为

### 6.3 质量先进性

- **设计可测**：每个角色都可独立测试
- **自动回归**：历史请求自动成为测试用例
- **故障注入**：开发时就能模拟生产故障

### 6.4 协作先进性

- **统一语言**：角色体系是团队共同词汇
- **清晰边界**：每个角色职责明确
- **渐进采用**：按需引入，不需要一次性全上

## 8. 底座必须解决的"元问题"

| 元问题 | 说明 | UniFlow 的回答 |
|--------|------|----------------|
| **谁来协调？** | 多个组件如何协作 | 引擎 + 调度员 |
| **谁来保护？** | 如何防止错误和恶意 | 守卫 |
| **谁来记住？** | 状态和历史如何管理 | 记录员 + 后勤 |
| **谁来扩展？** | 新能力如何接入 | 军械官 |
| **谁来沟通？** | 内外部如何通信 | 通信官 |
| **谁来思考？** | 智能能力如何引入 | 智囊 |
| **谁来执行？** | 具体动作如何完成 | 执行者 |
| **谁来决策？** | 全局方向谁定 | 总指挥 |
| **谁来观测？** | 运行状态如何可见 | 督察 |

**每一个元问题，都有一个明确的角色负责。没有灰色地带。**

## 9. 典型使用模式

### 9.1 纯 Workflow 模式

- 步骤可预知、流程稳定
- 每个步骤是 SystemTask 或 SkillTask
- 适合：链影工厂视频流水线、批处理任务、定时报表

### 9.2 Agent 增强模式

- 整体由 Workflow 驱动，部分步骤使用 AgentTask
- 例如：标题生成、脚本生成、错误诊断
- 好处：不改变整体控制流，易于回滚

### 9.3 交互式协作模式（Human-in-the-loop）

- Workflow 中显式包含 HumanTask
- 常见于 SoIs"澄清→确认→生成"循环
- DevDirector"自动方案→人工审阅"

---

## 10. 明确的非目标

UniFlow **不追求**：

- 完全自治的"强智能体系统"
- 取代业务层的所有决策逻辑
- 替代专门的调度系统（如大规模集群作业调度）

UniFlow 的目标是：

- 为日常应用提供**稳健、可控、可审计**的智能流程基础层
- 把"AI 能力"安全、可视化地嵌入到业务流程中
