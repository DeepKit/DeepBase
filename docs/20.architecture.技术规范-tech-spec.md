## 1. 概述与架构

### 1.1 设计目标

DeepBase 的目标是为 Delphi 应用提供一套**开箱即用的基础设施**，通过统一约定和组件封装，解决 Delphi 开发中的常见痛点：

1. 配置文件散乱（INI、Registry、XML 混用）
2. 国际化困难（硬编码中文、乱码问题）
3. 日志无统一规范
4. 各窗体重复实现状态保存、MRU 等功能
5. 异常处理不一致
6. 缺乏自动更新机制

### 1.2 内容分类（必需 / 推荐 / 可选）

| 分类 | 说明 | 包含内容 |
|------|------|----------|
| **DeepBase Core（必需）** | 所有项目必须引入的基础层 | root.txt、config.db Tier 0 表、TDeepBaseManager 核心接口 |
| **DeepBase UI & Tools（推荐）** | 大多数项目会用到的增强 | VCL/FMX 控件、Studio、CLI |
| **DeepBase Cloud（可选）** | 需要服务器支持的高级功能 | 自动更新服务、远程配置、反馈收集、License 验证 |

### 1.4 多应用 / 多数据库拓扑

为支持 DeepBase Studio 统一管理多个应用，同时保持各应用间隔离：

- **每个应用实例**拥有：
  - 唯一的 `ProjectRoot`（由 `root.txt` 指定）
  - `ProjectRoot` 下有 `config.db`（DB1x：该应用的 DeepBase ConfigDB）
  - 0..N 个业务数据库连接（本地 DB2x 或远程 DB3x）

- **DeepBase Studio** 本身：
  - 作为独立应用，拥有 `StudioRoot` 和 `StudioConfig.db`（DB1A）
  - 维护应用注册表，只存各应用 ConfigDB 的路径和元信息

**关键约束：**

1. 每个应用实例有唯一的 ProjectRoot 和唯一的 ConfigDB
2. Studio 只存"指针"，不复制配置
3. 命名空间隔离：Query 名和连接 Profile 名在单个 ConfigDB 内唯一
4. 稳定 AppId 校验：防止误连错库
5. 连接 Profile 只存在于某个应用的 ConfigDB 中
6. 并发：应用自身是 ConfigDB 的主要写入方，Studio 只在低频管理操作中写入

### 1.5 错误码约定

| 错误码 | 含义 | 说明 |
|--------|------|------|
| 0 | 成功 | 已初始化 |
| 1 | config.db 不存在 | 尝试自动创建失败 |
| 2 | config.db 损坏 | 表结构检查失败 |
| 3 | 权限错误 | 无法写入 root.txt 或 config.db |
| 4 | 路径无效 | root.txt 指向的目录不存在 |
| 5 | 资源目录缺失 | assets 目录结构不完整 |
| 99 | 未知错误 | 见错误消息详情 |

ErrorMsg 返回格式：`[code] 错误类型: 详细描述`，例如 `[1] ConfigDB Not Found: Cannot create at D:\config.db`

## 2. 目录与文件约定

### 2.1 root.txt 与目录结构

root.txt 文件位置（按优先级查找）：

1. EXE 所在目录
2. `%APPDATA%\{AppName}\`

内容：第一行为项目根目录的绝对路径。

```text
D:\Apps\MyTool
```

DeepBase 会使用：

```text
D:\Apps\MyTool\MyToolConfig.db
```

### 2.2 开发环境与用户环境行为差异

**开发期：**
- root.txt 在 EXE 目录
- config.db 在同一目录
- 日志输出到 `logs/` 子目录

**用户环境（交付后首次运行）：**
- 程序安装目录不可写
- EXE 目录可能没有 root.txt
- DeepBase 在用户数据目录查找/创建 root.txt
- config.db 创建在用户数据目录

**root.txt 冲突解决规则：**
- EXE 目录和 AppData 目录同时存在 root.txt 时，以 AppData 中的为准
- 首次运行自动从 EXE 目录复制 root.txt 到 AppData（如果 EXE 目录有而 AppData 没有）

## 3. 线程安全

以下方法保证线程安全：

- `Log()` 及所有日志方法
- `GetConfig()` / `SetConfig()` 及所有配置读写方法
- `T()` / `TN()` 及所有 i18n 方法
- `AddMRU()` / `GetMRUList()`

以下方法仅限主线程调用：

- `ApplyTheme()`
- `RestoreFormState()` / `SaveFormState()`
- 所有 UI 控件操作

### 3.1 SQLite WAL 与 Checkpoint 策略

DeepBase 默认对 config.db 启用 WAL 模式：

```sql
PRAGMA journal_mode = WAL;
PRAGMA synchronous = NORMAL;
PRAGMA wal_autocheckpoint = 1000;  -- 每 1000 页自动 checkpoint
```

注意事项：

- WAL 文件（`-wal`、`-shm`）会随应用运行自动增长；应用正常退出时 DeepBase 会执行 `PRAGMA wal_checkpoint(TRUNCATE)` 回收空间
- 若应用异常崩溃，下次启动时 SQLite 会自动完成恢复
- 多进程同时写入时依然是文件锁（一个写者），应避免 App + Studio 同时高频写入

### 3.2 内存缓存策略

| 模块 | 缓存范围 | 失效时机 | 备注 |
|------|----------|----------|------|
| **Settings** | 全量加载到 TDictionary | SetConfig* 写入时立即更新 | 默认不查库 |
| **i18n (I18nTexts)** | 按语言全量加载 | 切换语言时清空并重新加载 | 第一次 T() 调用后击中缓存 |
| **FormStates** | 按需读取，不主动缓存 | 每次 RestoreFormState 都查询 | 低频调用 |
| **Logs** | 无内存缓存，直写库/文件 | 不适用 | 异步队列写入 |
| **MRU** | 按 Category 延迟加载 | AddMRU 时刷新对应 Category | GetMRUList 返回内存快照 |
| **AnimationAssets** | 首次加载后缓存 | 手动调用 RefreshAssets 或重启 | SVG 渲染后缓存 Bitmap 序列帧 |

### 3.3 Schema 迁移策略

迁移元数据表：

```sql
CREATE TABLE IF NOT EXISTS SchemaMigrations (
  version INTEGER PRIMARY KEY,
  script_name TEXT NOT NULL,
  applied_at TEXT NOT NULL,
  checksum TEXT,
  execution_time_ms INTEGER
);
```

迁移脚本命名规范：

```
migrations/
├── V001__Initial_Schema.sql
├── V002__Add_Hotkeys_Table.sql
├── V003__Add_UsageStats_Index.sql
└── R001__Refresh_Views.sql           # R = Repeatable
```

迁移最佳实践：

| 原则 | 说明 |
|------|------|
| 向前兼容 | 新版本代码应能处理旧 Schema |
| 向后兼容 | 尽量不删除字段，先标记废弃 |
| 小步迁移 | 每个脚本只做一件事 |
| 幂等检查 | 脚本内部用 `IF NOT EXISTS` 保护 |
| 备份优先 | 生产环境迁移前自动备份 |

## 5. 数据访问：DeepBase.DB.DoQry 概览

### 关键角色

- **ConfigDB（DB1x）**：每个应用自己的 config.db
  - 含 `queries` 表：按 `proc_name + db_type` 定义 SQL 模板、参数 Schema、超时、默认 LIMIT 等
  - 含 `connection_profiles` 表：定义连接本地业务库和远程业务库的 Profile

- **业务数据库（DB2x/DB3x）**：真正存放业务数据的库

- **DeepBase.DB.DoQry（门面）**：
  - 从 ConfigDB 加载 queries 和 connection_profiles
  - 基于 JSON 参数 Schema 校验构造参数化 SQL
  - 通过 FireDAC 连接到 DB2x/DB3x 执行查询
  - 使用 DeepBase.Logging 输出结构化日志
  - 使用 EDeepBaseDbError 统一承载 DB 相关错误上下文

### 推荐使用方式

- 应用启动时调用 `UniDbInit(DeepBase.RootPath)` 完成 DoQry 绑定
- 连接管理：短期自行创建 TFDConnection，长期在 ConfigDB 维护 connection_profiles
- 执行查询：统一通过 `UniDbSelect/UniDbExec/UniDbInsertReturningId/UniDbScalar`

### 设计约束

- 所有查询定义只存放在当前应用的 ConfigDB 中
- Query 名和连接 Profile 名只在单个 ConfigDB 内唯一
- doQry 只依赖 DeepBase 的 RootPath/ConfigDB/Logging/Errors

## 6. 性能规范

### 6.1 API 响应时间基线

| API | 目标时间 | 测试条件 | 备注 |
|-----|----------|----------|------|
| `GetConfig` (缓存命中) | < 0.1ms | 内存字典查找 | 首次加载后缓存 |
| `GetConfig` (首次加载) | < 10ms | 单次 SQLite 查询 | 全量加载到内存 |
| `SetConfig` | < 20ms | 单次 SQLite 写入 | 同步写库+更新缓存 |
| `T()` 翻译 (缓存命中) | < 0.5ms | 内存查找 | 按语言全量加载 |
| `T()` 翻译 (未命中) | < 5ms | 含回落逻辑 | 返回原文并记录 |
| `SaveFormState` | < 50ms | 单次 SQLite 写入 | 单窗体状态 |
| `RestoreFormState` | < 30ms | 单次 SQLite 读取 | 单窗体状态 |
| `Log` (异步) | < 0.1ms | 仅入队时间 | 后台线程写库 |
| `AddMRU` | < 30ms | 含去重+截断+写入 | |
| `GetMRUList` | < 10ms | 单次 SQLite 查询 | 默认 10 条 |

### 6.2 资源限制

| 指标 | 警告阈值 | 拒绝阈值 | 说明 |
|------|----------|----------|------|
| config.db 文件大小 | 50MB | 100MB | 超过则日志警告/拒绝启动 |
| Settings 内存缓存 | 10MB | 20MB | 全量加载到 TDictionary |
| I18nTexts 单语言缓存 | 5MB | 10MB | 切换语言时重建 |
| 日志队列深度 | 5000 条 | 10000 条 | 超过则丢弃最旧条目 |
| MRU 单分类条目数 | 50 | 100 | 超过则自动截断 |
| FormStates 记录数 | 500 | 1000 | 窗体名去重 |

## 7. 异常处理规范

### 7.1 异常层级定义

```pascal
type
  EDeepBaseException = class(Exception)
  private
    FErrorCode: Integer;
    FContext: string;
  public
    constructor Create(ACode: Integer; const AMessage: string; const AContext: string = '');
    property ErrorCode: Integer read FErrorCode;
    property Context: string read FContext;
  end;

  EDeepBaseConfigError = class(EDeepBaseException);   // 100-199
  EDeepBaseDBError = class(EDeepBaseException);        // 200-299
  EDeepBaseI18nError = class(EDeepBaseException);      // 300-399
  EDeepBaseLLMError = class(EDeepBaseException);       // 400-499
  EDeepBaseLicenseError = class(EDeepBaseException);   // 500-599
```

### 7.2 错误码分配范围

| 范围 | 模块 | 说明 |
|------|------|------|
| 0 | 成功 | 无错误 |
| 1-99 | 初始化 | Manager 初始化错误 |
| 100-199 | Config | 配置读写错误 |
| 200-299 | Database | 数据库操作错误 |
| 300-399 | I18n | 国际化错误 |
| 400-499 | LLM | AI 调用错误 |
| 500-599 | License | 授权错误 |
| 600-699 | Update | 自动更新错误 |
| 700-799 | Network | 网络相关错误 |
| 800-899 | Security | 安全相关错误 |
| 900-999 | 保留 | 未来扩展 |

### 7.3 异常处理最佳实践

```pascal
// Controller 层捕获并转换异常
procedure TUserCtrl.LoadUser(UserId: Integer);
begin
  try
    FRepo.GetUser(UserId);
  except
    on E: EDeepBaseDBError do
    begin
      LogError('LoadUser failed: ' + E.Message, E.Context);
      raise EUserException.Create(GetUserFriendlyMessage(E));
    end;
  end;
end;

// View 层统一处理
procedure TMainForm.HandleException(Sender: TObject; E: Exception);
begin
  if E is EDeepBaseException then
    ShowMessage(GetUserFriendlyMessage(EDeepBaseException(E)))
  else
    ShowMessage(T('An unexpected error occurred.'));
end;

// 全局异常处理器
procedure GlobalExceptionHandler(Sender: TObject; E: Exception);
begin
  DeepBase.Exception.LogException(E);
  if E is EDeepBaseException then
    Application.MessageBox(
      PChar(GetUserFriendlyMessage(EDeepBaseException(E))),
      PChar(T('Error')), MB_ICONERROR);
end;
```
