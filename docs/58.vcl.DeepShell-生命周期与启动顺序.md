# DeepShell 生命周期与启动顺序

> audience: ai, developer
> status: design-contract

## 1. 目标

DeepMainForm 必须给下游一个稳定生命周期。下游不要直接抢 `FormCreate`、`FormShow`、`FormClose` 做核心初始化，而是覆盖 DeepShell 提供的虚方法。

## 2. 标准生命周期

```pascal
procedure InitializeShell; virtual;
procedure RegisterServices; virtual;
procedure RegisterCommands; virtual;
procedure RegisterProviders; virtual;
procedure BuildShellUI; virtual;
procedure LoadShellState; virtual;
procedure AfterShellShown; virtual;
procedure BeforeShellClose; virtual;
procedure SaveShellState; virtual;
procedure ShutdownShell; virtual;
```

推荐调用顺序：

```text
Create
  -> InitializeShell
  -> RegisterServices
  -> RegisterCommands
  -> RegisterProviders
  -> BuildShellUI
Show
  -> LoadShellState
  -> AfterShellShown
Close
  -> BeforeShellClose
  -> SaveShellState
Destroy
  -> ShutdownShell
```

## 2.1 BuildShellUI 与 DFM 的关系

DeepShell 基类第一版优先使用代码动态创建 Shell 骨架，不依赖 DFM：

```text
菜单 / 工具栏
Top Area
Middle Area / MainHost
Bottom Area
StatusBar
左右 ToolWindow
```

`BuildShellUI` 的职责是创建这些基础控件并建立 Command 绑定。下游继承类可以有自己的 DFM，但不要在 DFM 中重建 Shell 骨架。

推荐规则：

- `TDeepMainForm` 核心控件由基类在 `BuildShellUI` 中创建。
- 下游 DFM 只放业务专用控件，或完全不用 DFM。
- 下游不要直接删除或替换基类创建的 `MainHost`、Top/Bottom Panel、StatusBar。
- 下游需要自定义区域内容时，通过 Provider、SettingsPageProvider 或 protected hook 注入。
- 如果必须使用 DFM 继承窗体，应在 `inherited BuildShellUI` 后挂接业务控件，不要跳过 inherited。

这样做的目标是让 DeepShell 可被包复用、可测试、可被 AI scaffold，而不是依赖设计器状态。

## 3. DPR 启动顺序

最小程序：

```pascal
uses
  DeepBase.Manager,
  DeepBase.Persistence.Manager.FireDAC;

begin
  Application.Initialize;
  DeepBase.InitializeOrRaise;
  try
    Application.CreateForm(TMainForm, MainForm);
    Application.Run;
  finally
    DeepBase.Finalize;
  end;
end.
```

## 4. 带 DB1 的启动顺序

正式 DeepBase 应用推荐：

```text
Application.Initialize
DeepBase root 定位
DB1 / ConfigDB 初始化
DeepBase.InitializeOrRaise
Create TMainForm
  RegisterServices: 注册 SettingsStore / Recent / Layout
  RegisterCommands
  RegisterProviders
LoadShellState
Application.Run
SaveShellState
DeepBase.Finalize
```

Shell 核心不直接创建 Db1，但 SettingsStore 可以由下游注册为 DB1-backed 实现。

## 5. 带 Governance 的启动顺序

Governance 在 Command / Service / Context 基础设施存在之后接入：

```text
DeepBase.InitializeOrRaise
DB1 / ConfigDB ready
Create TMainForm
RegisterServices
RegisterCommands
RegisterProviders
RegisterGovernance(gmObserve, ConfigDB, SetupGovernance)
Bind CommandManager -> GovernanceService
Application.Run
ShutdownGovernance
DeepBase.Finalize
```

首次接入必须使用 `gmObserve`。`gmEnforce` 只在证据、门禁和高风险命令稳定后启用。

## 6. RegisterServices

下游在这里注册服务：

```text
项目服务
业务数据服务
Db1 adapter
doQry adapter
连接池 adapter
LLM facade
浏览器自动化 adapter
业务设置页 provider
```

不要在这里创建主视图控件。UI 内容由 Provider 创建或由 `OpenView` 挂载。

## 7. RegisterCommands

下游在这里注册业务命令。命令必须声明：

```text
Id
Caption
Category
Shortcut
Enabled / Visible
CapabilityId
GateKey
RiskLevel
Execute handler
```

所有按钮、菜单、快捷键都绑定这些命令。

## 8. RegisterProviders

下游在这里注册：

```text
IShellStructureProvider
IShellMainViewProvider
IShellInspectorProvider
ISettingsPageProvider
```

Provider 不应在注册阶段做重活。真实数据加载应延迟到打开项目或用户请求时。

## 9. LoadShellState

加载顺序：

```text
全局 Settings
Theme / i18n
全局 Layout
最近项目 MRU
项目级 Layout
工具窗状态
当前视图
```

如果项目路径不存在，不要报致命错误；应从 MRU 中标记失效或提示用户移除。

## 10. SaveShellState

关闭前保存：

```text
主窗体位置
三区折叠状态
左右工具窗状态
当前 Tab
当前视图
最近项目
最近文件
最近命令
```

敏感数据不要进入 Layout / MRU。连接密码、Token、私钥走 Security / Secret 服务。

## 11. ShutdownShell

关闭顺序：

```text
停止接受新 Command
取消后台任务
保存状态
取消 EventBus 订阅
释放工具窗
释放 Provider
关闭可选服务
```

不要让后台线程访问已释放控件。
