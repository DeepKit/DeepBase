## 1. 总体评价

**探针写得很好。** BCrypt 零外部依赖的方向是我们一直在找的——DeepBase 框架的 32 号文档之前假设必须加载 `sqlite3_sqlcipher_x64.dll`，你的方案证明了不依赖那个 DLL 也可以完整解密。几个具体值得肯定的点：

- 内存扫描 + 已知偏移的双路径回退设计得很合理
- 熵值过滤（>7.5 + 非零字节 < 24）这个启发式在微信场景下验证有效
- `DeriveSQLCipherKey` 的 HMAC 两步派生（aes_key + mac_key）写得很清晰
- `WeChat Files\` 路径发现逻辑覆盖了多个可能位置

## 2. DeepBase 侧准备怎么用你的探针

### 2.1 直接复用的部分

| 探针组件 | DeepBase 映射 | 方式 |
|---------|-------------|------|
| **PBKDF2 参数集的确认** (SHA1/64000/AES-256-CBC) | `TSQLCipherCompatibilityConfig.WeChat4xCipherConfig` | **直接替换**——之前文档推测 4.x 用 SHA512，实测 SHA1 才是对的 |
| **`GetProcessIdByName` + 内存扫描** | `GetWeChat41KeyCallback: TFunc<string, TBytes>` | 封装为回调函数，注入到 `TExternalSQLiteReader.OpenWithKeyCallback` |
| **`DeriveSQLCipherKey`** | 同上 KeyCallback 内部 | 密钥派生逻辑在回调中完成，Reader 只消费最终 `TBytes` 密钥 |
| **`TryDecryptDB` (BCrypt 完整解密)** | 备选方案（独立解密层）→ **提升为与 FireDAC 并列的等选项** | `TExternalSQLiteReader.Backend := beBCryptDirect` 时走你的 BCrypt 全链路 |

### 2.2 需要和你确认/协调的点

| # | 问题 | 建议 |
|---|------|------|
| 1 | **已知偏移列表中的 4.1.10.30 值** | 当前列表最高到 `$2100000`（v4.0.x）。需要在微信 4.1.10.30 运行时跑一次探针，将实测偏移加入列表。我们这边的账号路径是 `D:\Personal\Documents\WeChat Files\wxid_swkc1c57428i21`，有 16 个 DB 文件 |
| 2 | **`FindWeChatDataRoots` 路径硬编码** | `GetDocumentsPath + 'WeChat Files\'` 覆盖了标准安装。建议额外读取注册表 `HKCU\Software\Tencent\WeChat\FileSavePath`（如果有的话），作为第三回退 |
| 3 | **异常处理中的 `ReadLn`** (line 784) | 生产场景下（DeepBase 作为 DLL/库）不能阻塞等待用户输入。建议在库化时去掉 `ReadLn`，改用 `Logger.Error` 记录异常 |
| 4 | **`HMAC_SHA1_SIZE = 20` 的硬编码** | 当前写死 20 是对的（SHA1 输出 20 字节）。如果未来微信迁移到 SHA256（输出 32 字节），需要能自适应。建议将 HMAC 长度作为 config 参数 |
| 5 | **`DecryptPageWithBCrypt` 函数重复** | `DecryptPage` 和 `DecryptPageWithBCrypt` 是同一逻辑的两个副本（line 298-364 vs 441-488）。建议只保留一个 |

### 2.3 想请你补充的

1. **微信版本检测**：目前 `ScanForData` 没有获取微信的精确版本号（如 `4.1.10.30`）。建议通过 `WeChatWin.dll` 的 `GetFileVersionInfo` 获取，这样可以建立"版本号 → 偏移值"的精确映射表
2. **MicroMsg.db 以外的表的 Schema**：探针当前只解密不读结构。我们需要知道 `MSG` 表在 4.1 中的列名列表（特别是 `CreateTime` 是否还是 int，`StrContent` 列名是否变了）。如果你有空，解密后用 `sqlite3 .schema MicroMsg.db` 导出一份
3. **多账户场景**：`ScanWeChatData` 已经发现了多账户目录（你这边和我们的测试都验证了这一点）。DeepBase 侧需要知道"当前活跃账户"是哪个——你有没有找到判断活跃账户的方法？还是需要用户在 DeepBase 中手动选择？

## 5. 几点感谢

- 探针避免了 DeepBase 框架侧引入 sqlcipher.dll 的外部依赖——这是一个架构层面的贡献
- `ScanForKeyInProcess` 的熵值启发式 + 已知偏移双路径给了我们在未知微信版本上的鲁棒性——这正是之前审查中"VendorLib 动态选择"所缺的东西
- BCrypt 的 HMAC per-page 验证确保了即使密钥不对也不会产生无声的错误数据——这种"先验证再返回"的做法和 DeepBase 的 SafeQuery 审计哲学一致
