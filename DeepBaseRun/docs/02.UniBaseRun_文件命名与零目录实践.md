# 02. DeepBaseRun 文件命名与零目录实践

> 本文档基于 `02_开发指南.md` 的命名与分层约定，说明 DeepBaseRun 示例项目的文件命名规则，以及如何在本项目中落实“业务代码零目录结构”的要求。

## 1. 零目录结构的适用范围

在 DeepBaseRun 中：

- **业务代码单元（.pas/.fmx）全部平铺在项目根目录**，不创建 `Source/`、`Core/`、`UI/` 等子目录。
- 仅以下三类目录允许出现在根目录下：
  1. `tests/`：测试工程和测试代码；
  2. `scripts/`：构建、初始化等脚本；
  3. `docs/`：项目文档。

即：

```text
DeepBaseRun/
  [根目录下是主程序与所有业务相关 .pas/.fmx]
  tests/
  scripts/
  docs/
  assets/ (运行或部署时存在)
  logs/   (运行时生成)
  config.db (运行/初始化后生成)
```

**注意：**

- 零目录结构的约束只针对“业务代码单元”，测试/脚本/文档单独成目录是允许且推荐的。
- 如果未来项目庞大到必须拆分多个子工程或 Package，应通过多个工程/库划分，而不是在单工程内建立深层目录树。

## 2. 业务代码文件命名约定

参考 `01_项目开发规范与标准.md`，并结合 DeepBaseRun 的实际文件：

### 2.1 主程序与工程文件

- 主程序：`DeepBaseRun.dpr`
  - 职责：FMX 应用入口，负责 Application 初始化、DeepBase 初始化、创建主窗体并进入消息循环。
- 工程文件：`DeepBaseRun.dproj`
  - 职责：Delphi 工程配置（编译选项、输出路径等），不写业务逻辑。

> 新项目初始化后，脚本会将这两个文件重命名为新项目名（例如 `MyApp.dpr` / `MyApp.dproj`）。

### 2.2 视图层（View）

- 主窗体：`ViewMain.pas` / `ViewMain.fmx`
  - 前缀：`View` 表示视图层；
  - 职责：
    - 承载主菜单、五面板布局和状态栏；
    - 承载配置编辑 Frame、日志查看 Frame 等 UI 组件；
    - 通过接口持有控制层引用，不直接访问数据库。

如果后续扩展更多窗口，可以按以下模式命名：

- `ViewSettings.pas` / `ViewSettings.fmx`：设置/选项窗口；
- `ViewLogFilter.pas` / `ViewLogFilter.fmx`：复杂日志过滤窗口或对话框等。

### 2.3 控制层（Controller）

- 主控制器：`CtrlMain.pas`
  - 前缀：`Ctrl` 表示控制层；
  - 职责：
    - 对外暴露接口（例如 `ICtrlMain`），供 View 层调用；
    - 实现“日志列表获取、日志内容读取、配置项读写”等核心逻辑；
    - 调用 DeepBase 提供的 API（`DeepBase.GetConfig`, `LogInfo` 等）；
    - 不引用具体窗体类型或 FMX 控件单元（尽量保持 UI 无关）。

其他控制器示例命名：

- `CtrlConfig.pas`：配置相关业务控制器；
- `CtrlLog.pas`：日志相关业务控制器。

### 2.4 数据模块（uDM）

- 数据模块模板：`uDM.pas`
  - 前缀：`uDM`，对应 `TDM = class(TDataModule)`；
  - 职责：
    - 在真实业务项目中，负责连接 PostgreSQL 等业务数据库；
    - 从 DeepBase 配置中读取连接参数（`Db.Host`, `Db.Port` 等）；
    - 不包含任何 UI 代码，不引用 View 单元。
  - 在 DeepBaseRun 中，可以只保留最小实现作为模板，或演示如何从 DeepBase 读取业务库配置。

### 2.5 模型与辅助单元

- 业务实体：`Model*.pas`
  - 如：`ModelLogRecord.pas`、`ModelSetting.pas`。
  - 前缀：`Model`，仅存放纯数据结构（record/class），不包含 UI 和数据库访问代码。

- 辅助类/工具：`Helper*.pas`
  - 如：`HelperUI.pas`、`HelperLogView.pas`；
  - 用于封装通用逻辑，减少重复代码；
  - 不直接访问数据库，数据库访问由 uDM 或 Repository 封装处理。

## 3. 非业务目录中的文件命名

### 3.1 tests 目录

- 测试工程：
  - `tests\DeepBaseRun.Tests.dpr`：DUnitX 命令行测试工程；
  - `tests\DeepBaseRun.GuiTests.dpr`：FMX GUI 测试工程（集成所有测试）。

- 测试单元命名建议：
  - `Tests.Config.pas`：与配置相关的测试；
  - `Tests.LogView.pas`：与日志查看逻辑相关的测试；
  - `Tests.MainForm.pas`：对主窗体行为的测试（通常在 GUI 测试工程中使用）。

### 3.2 scripts 目录

- `scripts\init-project.bat`：新项目初始化脚本，负责重命名工程、更新占位符、重写 root.txt。
- `scripts\build.bat`：编译主程序的脚本。
- `scripts\test.bat`：编译并运行命令行测试工程。
- `scripts\test-gui.bat`：启动 GUI 测试工程。
- `scripts\run.bat`：运行主程序（可选）。

脚本文件名应简短明确，全部使用小写 + 连字符/驼峰均可，建议统一为小写加中划线或小写无分隔，不使用中文文件名，避免编码问题。

### 3.3 docs 目录

- DeepBaseRun 自有文档采用 `01.`, `02.` 开头排序，例如：
  - `01.DeepBaseRun_项目概览与架构映射.md`
  - `02.DeepBaseRun_文件命名与零目录实践.md`
  - `03.DeepBaseRun_日志查看与配置编辑设计.md`
  - `04.DeepBaseRun_测试与脚本使用说明.md`

与上位文档 `01_DeepBase规范.md`、`02_开发指南.md` 等共同构成完整的文档体系。

## 4. 常见错误与建议

1. **错误：在根目录下新增 `Source/` 或 `Core/` 目录放业务代码。**
   - 修正：业务代码一律平铺在根目录，按文件命名区分职责；只有 tests/scripts/docs 允许是子目录。

2. **错误：在 View 单元中直接新建 `DataModule` 或引用业务数据库控件。**
   - 修正：数据库访问统一放在 `uDM.pas` 或专门的数据访问单元，由 Controller 调用。

3. **错误：测试代码与业务代码混在一起，测试单元也平铺在根目录。**
   - 修正：所有测试单元与测试工程统一放在 `tests/` 下，避免干扰主程序工程。

4. **错误：脚本和工具程序（如小型数据迁移工具）直接放在根目录，与主程序混杂。**
   - 修正：脚本统一放在 `scripts/`；如有辅助小工具工程，可考虑单独子目录或单独仓库。

5. **错误：新增文件命名不符合 View/Ctrl/Model/uDM/Helper 约定。**
   - 修正：在创建新单元前，先确定其角色，选择合适的前缀，并在文档/注释中说明职责。

## 5. 对新项目的迁移建议

当你基于 DeepBaseRun 初始化一个新项目时：

1. 保持零目录结构，不要擅自添加 `Source/` 等中间目录；
2. 扩展 View/Ctrl/Model/uDM 时，按照本章约定命名文件；
3. 如果项目成长到需要多个工程：
   - 用多个 `.dpr` / `.dproj` 或 Package 来区分不同子系统；
   - 但在每个独立工程内部，仍然遵守本章的零目录 + 命名规范；
4. 把任何“想放到新目录里”的冲动先写进文档和设计说明，评估是否可以通过“新工程 + 公共库”方式解决，而不是破坏当前的零目录约定。
