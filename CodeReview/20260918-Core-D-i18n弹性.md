## 二、按单元分组发现

### I 组 — `DeepBase.i18n.pas`

#### CD-I-01 🔴 `FCurrentLanguage`（托管 string）在多个公共方法中不加锁读写，违反本类自述的"全线程安全"契约
`d:\_Progs\02Business\DeepBase\Core\DeepBase.i18n.pas:286-294`（`GetCurrentLanguage`/`SetCurrentLanguage`）、`:507`（`Translate` 读）、`:611`（`TranslatePlural` 读）
```pascal
function TDeepBaseI18n.GetCurrentLanguage: string;
begin
  Result := FCurrentLanguage;          // ← 无 FLock
end;
procedure TDeepBaseI18n.SetCurrentLanguage(const Value: string);
begin
  FCurrentLanguage := Value;           // ← 无 FLock；_LStrAsg 会 finalise(释放) 旧串
end;
function TDeepBaseI18n.Translate(const Text: string): string;
begin
  Result := TranslateTo(Text, FCurrentLanguage);   // ← 无 FLock 读，再按值传递
end;
```
文件头自述 `Thread Safety: All public methods are thread-safe.`，且 `FCache`/`FLanguageChangeListeners` 全部用 `FLock` 保护——唯独 `FCurrentLanguage`（`string`，托管类型）例外。
- **问题**：`FCurrentLanguage := Value` 由编译器展开为 `_LStrAsg`：**增新串引用 → 释放旧串（refcount 归零时 `Finalise` 归还内存）**。并发的 `Result := FCurrentLanguage` 会先取指针再对旧串加引用；若恰在"旧串已被释放"与"读到旧指针"之间，则对已释放内存做 `InterlockedIncrement` → 堆元数据损坏 / AV。Win64 上读 8 字节指针本身原子，但**生命周期**不受指针原子性保护。触发面在真实存在：`Examples\MultiLanguageDemo\MainForm.pas:202 UB.I18n.CurrentLanguage := LangCode`（UI 线程写），只要有任一后台线程在同时 `Translate`/`T()`（回调路径）即命中。
- **触发条件**：语言热切换（菜单选语言）与后台/工作线程翻译并发；重启不触发、单线程不触发。
- **建议修复**：`SetCurrentLanguage`/`GetCurrentLanguage`/`Translate`/`TranslatePlural` 对 `FCurrentLanguage` 的读写纳入 `FLock`；或在切换语言时用**局部快照**：`FLock.Enter; L := FCurrentLanguage; FLock.Leave;` 之后只用 `L`。也可考虑切换走"引用计数安全的写时复制"。

#### CD-I-02 🟡 `NotifyLanguageChanged` 锁外读并调用 `FOnLanguageChanged`（方法指针可撕裂）
`DeepBase.i18n.pas:363-388`
```pascal
  FLock.Enter;
  try
    Listeners := FLanguageChangeListeners.ToArray;   // ✓ 多播快照在锁内
  finally
    FLock.Leave;
  end;
  ...
  if Assigned(FOnLanguageChanged) then              // ← 锁外读
    FOnLanguageChanged(Self);                        // ← 锁外调用
```
- **问题**：多播列表的快照/复制是**正确**的（锁内 `ToArray`、锁外派发，避免死锁，值得肯定）。但为兼容保留的**单播 `FOnLanguageChanged`**（`property ... write FOnLanguageChanged`）在锁外读、且 `TNotifyEvent` 是 method pointer（Win64 上 `Code+Data` 共 16 字节），并发 `OnLanguageChanged := ...` 可读到"新 Code+旧 Data"的半更新对 → 用错误 `Self` 调用处理器 → AV。
- **触发条件**：订阅方与语言变更并发；注册即写属性的模式。
- **建议修复**：把 `FOnLanguageChanged` 也纳入快照：`FLock.Enter; LSingle := FOnLanguageChanged; FLock.Leave;` 后调用 `LSingle`；`write` 侧同样加锁。

#### CD-I-03 🟡 `RecordMissingTranslation` 在非 DEBUG 下吞掉全部异常，无任何日志/指标
`DeepBase.i18n.pas:486-503`
```pascal
  try
    FStorage.RecordMissingTranslation(SourceText, LangCode);
  except
    on E: Exception do
      {$IFDEF DEBUG}
      OutputDebugString(PChar('... failed: ' + E.Message));   // Release 下啥也不留
      {$ENDIF}
  end;
```
- **问题**："缺失翻译记录"落库失败（连接掉线、约束冲突、事务死锁）在 Release 完全静默。该数据本身用于后续补齐翻译；丢失即永久丢失"哪些词条没翻"的证据，且无计数暴露。与 Core-C 反复出现的"Release 下异常日志静默为零"同族。
- **触发条件**：`FStorage` 落库路径异常（DB 侧任何问题）。
- **建议修复**：至少 `Logger.Warn`/`LogException` 一条并计入 `missing_translation_record_failed` 指标；`OutputDebugString` 改为不受 `{$IFDEF DEBUG}` 限制的降级日志。

#### CD-I-04 🟡 架构（SSOT）：存在两套"当前语言"真源，同一 UI 用 `T()` 与 `I18n.Translate()` 可能解析到不同语言
`DeepBase.i18n.pas:159-169 / 213-282`（`T/TFmt/TN` 经 `GTranslateCallback`/`GLanguageCallback`→`GetCurrentLanguageCode`）对比 `:505-613`（类方法用实例 `FCurrentLanguage`）。
- **问题**：全局 `T('...')` 走 `GLanguageCallback`（由 Manager 注入），`TDeepBaseI18n.Translate` 走实例 `FCurrentLanguage`。若二者未被同一处同时更新（本单元内 `SetCurrentLanguage` 不触碰全局回调，全局回调也不回写实例），切语言后**一半词条按新语言、一半按旧语言**。这正是"当前语言"缺乏单一真源。
- **触发条件**：只更新了 `I18n.CurrentLanguage` 而 Manager 侧回调仍返回旧值（或反之）。
- **建议修复**：`SetCurrentLanguage` 内同步刷新/驱动 `GLanguageCallback` 的底层真源（或反过来让全局 `T()` 唯一代理到 `I18n`），二者收敛为一个入口；补一条"设语言后 `T()` 与 `Translate()` 结果一致"的回归。

### TO 组 — `DeepBase.Resilience.Timeout.pas`

#### CD-TO-01 🔴 超时 `finally` 释放 `ResultLock`，而被 `Task.Cancel` 停不掉的 worker 稍后仍 `TMonitor.Enter(已释放锁)` → UAF/AV
`d:\_Progs\02Business\DeepBase\Core\DeepBase.Resilience.Timeout.pas:82-134`（`Execute`）与 `:136-196`（`Execute<T>`）
```pascal

  try
    Task := TTask.Run(procedure
      begin
        try TaskProc();
        except on E: Exception do
          begin
            TMonitor.Enter(ResultLock);        // :104 ← worker 用捕获的 ResultLock
            try ErrorClass := ...; ErrorMsg := E.Message;
            finally TMonitor.Exit(ResultLock); end;
          end;
        end;
      end);

    begin
      Task.Cancel;                             // :118 ← 无法中断已在运行的委托体
      ...
      raise ETimeoutException.Create(FTimeoutMs);
    end;
    ...

    ResultLock.Free;                           // :132 ← 主线程超时即释放，worker 可能仍在跑

```
- **问题**：`Task.Cancel` 只设置取消标志，**不会抢占/中断已进入 `TaskProc` 的工作线程**。超时分支 `raise ETimeout` 后经 `finally` 执行 `ResultLock.Free`（:132/:194）。此刻 worker 仍在 `TaskProc` 内运行：当它最终在 :104/:165 `TMonitor.Enter(ResultLock)` 或写入 `ErrorClass`/`ErrorMsg`（捕获自被释放对象的托管 string 槽）时，`ResultLock` 已被 `Free`（其 `TMonitor` 同步块/对象头已回收）→ 对已释放内存做同步/加引用 → **AV 或堆元数据损坏**。`Execute<T>` 的 `TaskResult := LResult`（:158）同样可能在锁释放后触碰捕获变量。这是**内存与生命周期 + 线程安全**双料 🔴。
- **触发条件**：**任何真实超时**（下游慢于 `FTimeoutMs`）且 worker 尚未自行结束——超时越频繁越易命中；`Execute(Proc,TimeoutMs)`（CB :439-453）与 `Policy` 组合（CD-PC-01）进一步放大触发面。
- **建议修复**：让 `ResultLock` 的生命周期由 **worker 结束**决定而非主线程——用引用计数句柄（主线程与 worker 各持一次，双方 `finally` 减一，归零才 `Free`），或用 `IEvent`/信号量握手：超时路径也需等 worker 真正退出（或至少 worker 完成对其捕获变量的最后访问）后再释放。绝不 `Free` 仍可能被 worker 触碰的对象。

#### CD-TO-02 🟡 超时非"操作真实上界"：`TTask.Run` 依赖线程池，池饱和时 `Proc` 可能根本未开始，返回"超时"后副作用仍延后发生

#### CD-PC-03 🟡 `With*` 所有权与外部引用重叠，可致双释放/UAF
`DeepBase.Resilience.Policy.pas:75-118`（各 `With*` 先 `FreeAndNil` 旧再存新）、`:62-73`（`Destroy` 按 Owns 释放）
- **问题**：`WithRetry(p,True)` 使策略拥有 `p`；若同一 `p` 被传入两个 `TResiliencePolicy`（都 Owns=True）→ 两个析构都 `FreeAndNil(p)`→**双释放**；若调用方 `WithRetry` 后自己再 `Free p`→后续 `Execute` 触碰已释放→UAF。`WithCircuitBreaker(...,OwnsBreaker=False)`（:100-108，默认 False）与其余默认 True 不一致，易误用。
- **触发条件**：复用同一子策略对象于多个组合器，或所有权约定混淆。
- **建议修复**：用引用计数/接口管理子策略所有权，或文档明确"子策略单一所有者"；`With*` 覆盖旧值时若旧值**已被其他组合器引用**应拒绝或取共享语义。

#### CD-PC-04 🔵 每次 `Execute` 构造 4–5 个闭包对象（装箱 `TProc`/`TFunc`），热路径分配压力
`DeepBase.Resilience.Policy.pas:143-177 / 207-238`
- **问题/正面确认**：每层用**不同**中间局部（`TimeoutProc/BreakerProc/RetryProc/BulkheadProc` :127-131 / :193-196）分别装箱捕获——**正确**规避了"共享同一变量导致捕获同一装箱"的陷阱（当前无捕获错误）。代价是每次调用分配多个堆上闭包记录；建议缓存不可变包装链（策略不变时）。

> **PC 组未见问题维度声明**：③线程安全（除继承 CD-TO-01 外，组合器自身无可变共享状态；`TResiliencePolicy` 由调用方独占配置后执行）、④异常处理（`finally` 将闭包局部置 nil **正确**）、⑤安全——**未发现**。
