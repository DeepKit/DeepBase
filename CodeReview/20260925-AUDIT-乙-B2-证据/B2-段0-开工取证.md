### B2-01 Firebase 布尔读写类型错位 —— 「恒读成 False」经实测不成立；类型不对称成立

- `Features/DeepBase.Commerce.Adapter.Firebase.pas:333-337` 写：`AddPair('booleanValue', TJSONBool.Create(AValue))` ⇒ 落到 JSON 里是布尔字面量。
- `:301-313` 读：`Fld.TryGetValue<string>('booleanValue', S)` + `SameText(S,'true')`，取不到即 `Result := False`。
- `:362`/`:409` `Result.IsActive := BoolField(Fields,'is_active')` ⇒ 商户激活态完全依赖这条读路径；写侧 `:435` 用 `WrapValue(AUser.IsActive)`（Boolean 重载）。
- **实测（`B2-段0-探针原始输出.txt` P1）**：`{"is_active":{"booleanValue":true}}` 经 `TryGetValue<string>` 返回 **True / `'true'`**，
  `SameText(...,'true')` = True，运行时类 = `TJSONTrue`（RTL `System.JSON.pas:874/881` 是 `TJSONBool` 的 sealed 子类，
  `TJSONValue.TryGetValue<T>` `:1961` 经 `AsTValue` 对字符串目标回落到 `.Value` 字符串化）。
  ⇒ 「写入 true 读回 false、商户激活状态永远失效」这一后果**不成立**；本单不修一个不存在的故障。
- 成立的部分（也是工单「期望」那句）：读写**类型不对称**——写侧类型化布尔、读侧靠 RTL 的隐式字符串化副作用取得，
  正确性挂在实现细节上而非契约上；同文件其余字段（`stringValue`/`integerValue`）读写同为字符串，只有布尔一侧跨了类型。
  ⇒ 修法是读侧改为按布尔类型取（`TJSONBool`），并用工单判据点名的往返用例把行为钉住（回归网，不是故障修复）。
- 分级建议：按实测，本条应从 **[Critical]** 降为 **健壮性/一致性**；是否改判由主控定，本单不自行改判，只照实报。

### B2-11 工作流上下文自死锁 —— 结论不成立（锁原语可重入），但「隐式重入依赖」缺陷成立

- `DeepFlow/Source/Workflow/DeepFlow.Workflow.Context.pas:83` `FLock: TCriticalSection`，`:297` `TCriticalSection.Create`；
