## 1. 重入边的准确位置（修前 :544-570 原文）

```pascal
function TWorkflowContext.ResolveJSON(const ATemplate: TJSONObject): TJSONObject;
var
  Pair: TJSONPair;
  ResolvedValue: string;
begin
  FLock.Enter;                       { :549 取锁 }
  try
    Result := TJSONObject.Create;

    for Pair in ATemplate do
    begin
      if Pair.JsonValue is TJSONString then
      begin
        ResolvedValue := ResolveString(TJSONString(Pair.JsonValue).Value);   { :557 横向重入 }
        Result.AddPair(Pair.JsonString.Value, ResolvedValue);
      end
      else if Pair.JsonValue is TJSONObject then
      begin
        Result.AddPair(Pair.JsonString.Value, ResolveJSON(TJSONObject(Pair.JsonValue)));  { :562 自递归重入 }
      end
      else
      begin
        Result.AddPair(Pair.JsonString.Value, Pair.JsonValue.Clone as TJSONValue);
      end;
    end;
  finally
    FLock.Leave;
  end;
end;
```

`ResolveString`（修前 :516）自身也 `FLock.Enter`（:522），`ResolveJSON` 也在自身体内调自己——
两条边都落在同一把 `FLock` 上，与工单表述一致。

## 3. 前提实测修正（须报主控）

工单把现象写成「同一**非递归**临界区 ⇒ 自死锁」。实测：本件的 `FLock` 是
`System.SyncObjs.TCriticalSection`，Windows 下包的是 `CRITICAL_SECTION`，**同线程重入 Enter 直接放行**
（计数递增），因此修前形态在本平台不会自死锁——见 `B2-11-反事实与判别探针.txt` §1（P1：修前件 + 真件
临界区 + 本次新用例 8/8 全绿）。

真实缺陷是结构性的：正确性隐式依赖「锁原语恰好可重入」这一平台副作用。锁一换实现
（非重入原语、跨平台语义变化）或被调件被他人改成不加锁版本，两条边立刻变成死锁——
实测复现见同文件 §2（P2：修前件 + 不可重入替身 ⇒ 嵌套解析硬挂，RUN_EXIT=124）。

据此选定期望里的第二种路线（被调件不重复加锁），而不是「锁改递归语义」：
后者等于把平台副作用升格成契约，正是本次要消除的依赖。
