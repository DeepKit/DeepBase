## 1) 缺陷本体：VerifyBackup 以 zip 方式打开未解密的 .zip.enc

$ git show HEAD:Features/DeepBase.CloudBackup.pas | grep -n "LZip.Open"
1218:    LZip.Open(AArchivePath, zmWrite);     # TBackupCompressor.CreateArchive（写侧，无关）
1274:    LZip.Open(AArchivePath, zmRead);      # TBackupCompressor.ExtractArchive（收明文路径，见 §3）
2540:        LZip.Open(LArchivePath, zmRead);  # ★ TCloudBackupManager.VerifyBackup —— 直接开加密归档

而 GetBackupArchivePath 在启用加密时给出的就是密文文件：

$ sed -n '1814,1820p' Features/DeepBase.CloudBackup.pas
function TCloudBackupManager.GetBackupArchivePath(const ABackupId: string): string;
begin
  if FConfig.EnableEncryption then
    Result := BackupFileUnderRoot(FConfig.LocalBackupPath, ABackupId, 'zip.enc')
  else
    Result := BackupFileUnderRoot(FConfig.LocalBackupPath, ABackupId, 'zip');
end;

后果链条（同一文件内可核对，不需外部假设）：
- `TZipFile.Open(<密文>, zmRead)` 必抛（zip 魔数不存在），被 VerifyBackup 外层的
  `except Result := False` 吞成「校验不通过」；
- InternalRestore 在 2031 行把 VerifyBackup 作为恢复前置门禁（Top20 #15 接入），
  门禁必然拒放 ⇒ 启用加密的备份既不可验证也不可恢复；
- 恢复路径本身（2049-2059）早就有正确的「解密到 tmp.zip 再交给 ExtractArchive」写法，
  即同一文件内两套读法：恢复侧解密、校验侧不解密——这是分叉而不是缺能力。

## 3) 附带同族事实（本单一并收口，逐条给出处）

3.1 恢复侧临时明文只在成功路径回收：
$ git show HEAD:Features/DeepBase.CloudBackup.pas | grep -n "TFile.Delete(LTempPath)\|if LTempPath <> LArchivePath"
2064（取消分支）、2086（成功分支）两处删除，中间 2077 `FCompressor.ExtractArchive` 抛错
即从 2100 的 except 逃逸 ⇒ 解密后的明文 `tmp.zip` 留在备份根，无任何出口回收。
（备份写侧 1921/1935 同样只有成功/取消两个删除点。）

3.2 「请求加密但未配密钥」= 写出明文并挂 .zip.enc 后缀（伪密文）：
构造侧 `if FConfig.EnableEncryption and (FConfig.EncryptionKey <> '')` 才建 FEncryptor，
而命名侧只看 `FConfig.EnableEncryption` ⇒ 密钥缺失时 InternalBackup 走 1971-1978 的
「明文 tmp.zip 直接 Move 到 <id>.zip.enc」分支（HEAD 1939-1946）。归档名声称已加密、内容是明文。

3.3 第二处 LZip.Open（1274，TBackupCompressor.ExtractArchive）定性：非缺陷。
该函数是纯 zip 工具，契约要求调用方给明文路径；仓内唯一调用点是 InternalRestore
（HEAD 2077），其入参 LTempPath 在加密分支下就是解密产物。修复后调用方改为
统一的明文解析入口，1274 保持不动，不再新增第二条判断。
