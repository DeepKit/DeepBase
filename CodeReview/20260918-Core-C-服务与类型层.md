## 二、按单元分组发现

### A 组 — LLM

#### CC-A-01 🔴 `SaveConfig` 无条件把 `Description` 写成空串（静默数据丢失）
`d:\_Progs\02Business\DeepBase\Core\DeepBase.LLM.pas:474`（PG 分支）、`:495`（SQLite 分支）
```pascal
LLMParam('Name', AConfig.Name),
LLMParam('Description', ''),          // ← 从不取 AConfig.Description
LLMParam('ProviderCode', AConfig.ProviderToStr),
```
- **问题**：`TLLMConfig` 含 `Description` 字段，但 4 条 INSERT/UPSERT 语句全部把该列硬编码为 `''`；PG 分支还显式 `Description=EXCLUDED.Description`，即每次保存都以空串覆盖既有描述。
- **触发条件**：任何一次 `SaveConfig`（UI 改一个 MaxTokens 也会触发）→ 已存在的非空 Description 被永久清空。
- **建议修复**：改为 `LLMParam('Description', AConfig.Description)`；补一条 round-trip 单测（存→读→比对全字段）。

#### CC-A-02 🟡 `SaveConfig`/`DeleteConfig` 存储不可用时静默 `Exit`
`DeepBase.LLM.pas:450-452`、`:580-582`
```pascal
Storage := GetStorage;
if not Assigned(Storage) or not Storage.IsConnected then
  Exit;                       // 无返回值、无异常、无日志
```
- **问题**：调用方（多为"保存成功"路径）无法区分已写库与完全没写；同时缓存也不更新，出现"界面显示已保存、重启后丢失"的双真源分裂。
- **触发条件**：DB 未连接 / 存储工厂未注册（见 CC-D-09）/ 连接掉线。
- **建议修复**：返回 `Boolean` 或抛 `EDeepBaseDB`；至少 `Logger.Warn` 一条并计入指标。

#### CC-A-03 🟡 `UpdatedAt` 用本地时间且无毫秒/时区
`DeepBase.LLM.pas:454`
```pascal
NowStr := FormatDateTime('yyyy-mm-dd"T"hh:nn:ss', Now);
```
- **问题**：与库内 `DateToISO8601`（UTC + `Z` + 毫秒）格式冲突（主题 1）；秒级精度下同一秒内多次保存无法排序；跨时区部署后"最近修改"排序错乱。
- **触发条件**：多节点/多时区，或与 `RefreshConfigCache` 按字符串排序混用。
- **建议修复**：统一走一个 `DateToISO8601(Now)` 帮助函数；全库禁止 `FormatDateTime` 直写时间戳列。

#### CC-A-04 🟡 `GetConfig` 未命中即全表重载（无 negative cache）
`DeepBase.LLM.pas:401-420`
```pascal
RefreshConfigCache;             // 整表 SELECT
FCacheLock.Enter;
if not FConfigCache.TryGetValue(AConfigName, Result) then
  Result.Name := AConfigName;   // 返回默认值，不留"确知不存在"标记
```
- **问题**：查询一个不存在的配置名会触发**整张配置表**重读；批量/循环里用名字试探（例如按 provider 逐个找）时呈 O(N×M) I/O 放大。注释说明 BIZ2-002 已收窄 TOCTOU 窗口（该点修复正确），但未解决 miss 放大。
- **触发条件**：任何"按名尝试、失败则试下一个"的调用模式。
- **建议修复**：`RefreshConfigCache` 加最小刷新间隔/版本号（`MAX(UpdatedAt)`）判定；对确认不存在的名字做短期 negative cache。

#### CC-A-05 🔵 四份近乎相同的 SQL 字面量（架构 SSOT）
`DeepBase.LLM.pas:458-560`：`LLMConfig`/`LLMConfiguration` 两表 × PG/SQLite 两方言 = 4 段列清单与占位符各自硬写。
- **问题**：加一列需同步 4 处，CC-A-01 类错误（漏传字段）正是这种重复的产物。
- **建议修复**：抽 `BuildUpsertSQL(table, columns, dialect)`，列清单单一来源。

#### CC-A-06 🟡 `TBillingClient.ApiKey` 以明文 property 公开可读写
`d:\_Progs\02Business\DeepBase\Core\DeepBase.LLM.BillingClient.pas:228`、`:152`
```pascal
FApiKey: string;
property ApiKey: string read FApiKey write FApiKey;
```
- **问题**：任何持有 `TBillingClient` 引用的代码/模块都能读出计费 API key；`write` 允许中途替换且无同步（与 `:903-912` 的快照读模式并存，说明作者已意识到并发问题但只修了快照路径）。
- **触发条件**：组件化 UI/DI 容器把 client 暴露给插件、或日志/诊断遍历对象属性（本库 `Serialization` 可按 property 反射导出 → 若有人序列化该对象即泄漏 key）。
- **建议修复**：去掉 public `ApiKey` 写口，只留构造注入；若必须保留 getter，改为返回掩码并另设 `InternalGetKey`（私有）。

#### CC-A-07 🟡 未强制/校验 TLS，Bearer token 可走明文
`DeepBase.LLM.BillingClient.pas:17`（文档示例 `http://server:8090`）、`:461`
```pascal
FHttpClient.CustomHeaders['Authorization'] := 'Bearer ' + FApiKey;
```

- **建议修复**：每个 `case` 补 `else Result := ''`（或 `'unknown'`）；入口处复用 `ValidateEnumOrdinal`；写入前统一枚举→字符串→枚举的 round-trip 单测。

#### CC-H-31 🟡 `EhaiCheckContextDrift` 只比 4/6 字段 → 授权人替换不算漂移
`DeepBase.EHAI.Types.pas:686-690` → `IsEqual`（`:387-393`）
