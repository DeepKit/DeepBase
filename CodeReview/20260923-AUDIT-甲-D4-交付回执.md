## 二、取证更正（本单自查发现并已更正，不藏着）

1. **`T1-观测面.txt` 曾有一行非法内容**：派生基准 SHA 被写成独立非注释行（`69d5a86`），
   按清单语法它会被当成一个工程路径 ⇒ `--manifest T1` 会 EXIT=2。fail-closed 会拦，但这是缺陷不是设计。
   **已更正**为注释并重新机械派生；现三面对账 `T0 点名(1) + T1(63) + T2(3) = 67 = git ls-files` 逐位一致、
   跨层零重复、`comm -3` 空（`D4-05`）。
2. **`T2-待定面.txt` 的归面判据原表述过宽**：原文「被引单元在全库零命中」对 DataAnalyzer 不成立——
   `Main.Form.pas` 作为单元存在于别的 Example 目录，缺的是本工程 `in 'Main.Form.pas'` 指向的同目录路径件。
   **已更正**为 F2613 / F1026 两种口径分开表述（取证 `D4-07`）。
3. **README 耗时旧数字作废**：`1m37s / 4m03s` 是「只编 67 个 `.dpr`」的量级，不能沿用来描述含包面的门。
   重测数字见 §四-4。
4. **五道静态门禁复跑的第一版取证有假 EXIT**：脚本里 `echo EXIT=$?` 取的是管道尾 `tail` 的码，
   三门红会被写成 EXIT=0。那份已丢弃并重做（`D4-11`），现为逐门真实退出码：**编码 0 / 行尾 0 / 证据编码 0 /
   托管拷贝 1 / 构建归属 1**，两处红的原因见 §五。
5. **过程纪律缺陷（如实报，不属工单判据）**：为清理自己失控的取证进程，我写过一把 pattern 过宽的清理脚本
   （含 `check_build`），它会连**别人正在跑的同名门禁**一起杀——本单取证期间乙线确实在并发跑这道门，
   存在误伤其运行的实际风险。该脚本已删除，证据链改为「单实例目录锁 + 一次性前台运行」，
   此后不再对本仓做任何批量杀进程操作。**若乙线某轮编译门结果出现莫名中断，请优先怀疑我这一笔。**
