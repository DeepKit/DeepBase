### 2.2 测量口径（判据 2 要求「写死」）

| 口径项 | 取值 | 依据 |
|---|---|---|
| **模型尺寸** | 单个 routed expert 的权重矩阵 = **4608 × 7168 = 33,030,144 个权重** | 与上游「One expert is 33,030,144 parameters」**逐位相同**；7168 = 上游 hidden |
| **打包格式** | **MX 风格 4 bit**：每权重 1 个半字节（E2M1 码值）+ 每 **32** 个元素 1 个共享标度 ⇒ **4.25 bit = 0.53125 B/权重** | 与上游「one shared 8-bit exponent per 32 elements」「0.53125 bytes per weight」一致 |
| **打包流实占** | 33,030,144 × 17/32 = **17,547,264 B** | 与上游自述**零残差相同** |
| **计算形态** | **直接吃打包半字节，任何时刻都不 materialize 反量化缓冲** | 这正是被测的那条设计主张的可测形态（上游「never dequantised」） |
| **内存口径** | 报三栏：**① 模型侧字节（打包流 / 展开后 float[]）② 进程 RSS（`WorkingSet64`）③ 进程峰值工作集（`PeakWorkingSet64`）** | 判据要求口径三选一写死；本单选择**三个都报**，因为单报任一个都可被质疑 |
| **重复次数** | **3 组**（非 1 组），**报全部而非报最好**；另给组间离散度 | 上游 BENCHMARKING.md 的纪律 |
| **输入** | `x[k] = sin(k × 0.0001)`，确定性；权重用固定种子 xorshift 填（不用 `System.Random`——其序列实现相关，不可跨运行时复现） | 跨机器可逐位复现 |

### 2.3 读数（**本方实测**，非档 C）

### 2.4 判据 4 要求的两栏对照：**理论打包比** vs **实测驻留量**

**理论打包比（本方算术）**

| 基准 | 公式 | 值 |
|---|---|---|
| bf16（16 bit） | 1 − 4.25/16 | **73.4375%** |
| fp32（32 bit） | 1 − 4.25/32 | **86.7188%** |

**实测驻留量（本方实测）**

| 项 | 值 |
|---|---|
| 打包流 | **17,547,264 B**（16.73 MiB） |
| 展开成 `float[]` | **132,120,576 B**（126.0 MiB） |
| 实测比值 | **7.5294×** |
| 进程 RSS：分配打包流后 | 185,446,400 B |
| 进程 RSS：展开后 | 321,175,552 B |
| 进程峰值工作集 | 332,382,208 B |
| GC 托管堆：展开后 | 165,880,024 B |

**结论（这是判据 4 的核心，禁止把两栏混成一个「降 75%」）**：

- 讨论包 §2.3 的「**降低 75% 以上**」**只在拿 fp32 当基准时成立（86.72%）**；拿 **bf16** 当基准是 **73.44%，不到 75%**。
- 上游自己的口径用的是 **fp32**（17.5 MB → 132 MB，7.53×，与本方实测的 7.5294× **吻合到小数点后 3 位**）⇒ 所以「75%」这个数在**上游的口径里成立**，但它衡量的是「相对 fp32 展开缓冲的缩减」，**不是「相对训练/服务常用 bf16 的缩减」**。
- 而 DeepBase 的移植场景（端侧推理、DeepBaseLLM 现有链路）**用的是 bf16** ⇒ **移植到 DeepBase 语境下应当引用 73.44% 这个数**，不是 75%+。

### 2.5 本机读数与讨论包 / 上游的对比（**不可直接对标，逐条说清差别**）

| 对比对象 | 本方读数 | 对比合法性 |
|---|---|---|
| 上游「全模型」最好档 **19.21 s/token**（124 线程 EPYC / 224 GB） | **24.12 s/token**（本机 8 核、**只算专家 MLP 一层**，不含 trunk / KDA / MLA / 路由 / 采样 / 磁盘流式） | **⚠ 严格说不可对标**（本方是子集、机器差 7.75 倍核）。但作为**量级与方向**的判断有效：**本机在只做子集的情况下，已经比上游全模型最好档慢 1.26 倍**（最佳组 20.01 s/token 则为 1.04 倍） |
| 讨论包 §4.1「15~35 tok/s」 | 本机专家层下界 **0.0415 tok/s**（1/24.12） | **不可对标**（那边是 2B~16B 另一尺寸，无硬件基线，见 E8）。**本单不据此判定讨论包错，只判定该数字本身不可复算** |
| 上游 8 GB 档 **32.69 s/token**（全模型） | 本机 64 GB 机器、只算专家层 **24.12 s/token** | 本机内存是它的 8 倍、核数是 1/15.5，**内存优势被核数劣势吃掉后仍只剩子集打平** ⇒ 本机这一档不构成端侧实时 MoE 的候选平台 |

### 2.6 本机这一档的硬约束（**可复算，不含外推**）

| 约束 | 数值 | 出处 |
|---|---|---|
| 每 token 活跃权重下界 | 1,472 × 16.73 MiB = **24.06 GiB** | 本方算术 |
| trunk 全量常驻需要 | **108.81 GB** | 档 C（ARCHITECTURE.md） |
| 本机物理内存 | 63.95 GB ⇒ **装不下 trunk ⇒ 必须流式** | 本方实测 |
| 存储带宽乐观下界 | 25.83 GB ÷ 3.2 GB/s = **8.07 s/token**（假设活跃权重全命中缓存，即不可实现的上界） | 本方算术 + 档 C 带宽 |

⇒ **本机这一档的结论只回答一个问题**：「按讨论包设想的那条路，DeepBase 目标机型（普通办公终端 / 工控 PC / 弱显卡或无独显机器）能不能跑？」——**本机读数与硬约束共同给出否定答案，且这个答案不依赖任何外推，只依赖「1,472 个专家 × 17.5 MB」这一个上游架构常数。**
