## F1.1 DeepBase.AntiTamper.pas

**总体结论**：核心加密与完整性校验流程总体正确，但存在 KDF 迭代数配置与实际行为不一致、日志文件句柄泄漏、IsSecureImageEnabled fail-open、ReseedMinimal 写入无法解密的记录等多个功能与安全缺陷，且 class var 共享状态无线程同步。

### 🟡 功能缺陷

#### F1.1.1 KDF 迭代数配置与实际行为不一致
- **位置**：d:\_Progs\02Business\DeepBase\Features\DeepBase.AntiTamper.pas:107、196
- **原始代码**：
```pascal
// GetDefaultConfig (L107)
Result.KdfIterations := 5000;
// DeriveKeyBytes (L196)
Iterations := Max(FConfig.KdfIterations, 10000); // 最少10000次迭代
```
- **问题说明**：`GetDefaultConfig` 返回 5000，但 `DeriveKeyBytes` 用 `Max(..., 10000)` 强制提升至 10000。配置明示值与运行时实际值不一致；若维护者删除 `Max` 包装，迭代数会悄悄从 10000 降回 5000，导致已加密数据无法解密。
- **触发条件**：任何调用 `GetDefaultConfig` 后直接 `Initialize`，或维护者修改 `DeriveKeyBytes` 时。
- **建议修复**：`GetDefaultConfig` 中 `KdfIterations := 10000`；`DeriveKeyBytes` 改为 `if FConfig.KdfIterations < 10000 then raise EAntiTamperException.CreateFmt(...)`。

#### F1.1.2 WriteLog 异常时未 CloseFile 导致文件句柄泄漏
- **位置**：d:\_Progs\02Business\DeepBase\Features\DeepBase.AntiTamper.pas:159-168
- **原始代码**：
```pascal
try
  AssignFile(LogFile, FConfig.LogFileName);
  if FileExists(FConfig.LogFileName) then Append(LogFile)
  else Rewrite(LogFile);
  WriteLn(LogFile, Format('[%s] %s', [DateTimeToStr(Now), AMessage]));
  CloseFile(LogFile);
except
end;
```
- **问题说明**：若 `Append`/`Rewrite` 成功后 `WriteLn` 抛异常（磁盘满、网络断开），`CloseFile` 不执行，文件句柄泄漏。`except end` 还吞掉所有异常。
- **触发条件**：日志文件所在磁盘满、网络位置断开、写权限被撤销。
- **建议修复**：用 `try/finally` 确保 `CloseFile`，`except` 只吞非 `EAbort` 异常。

#### F1.1.3 IsSecureImageEnabled 在异常时 fail-open
- **位置**：d:\_Progs\02Business\DeepBase\Features\DeepBase.AntiTamper.pas:483-498
- **原始代码**：
```pascal
class function TAntiTamperPackage.IsSecureImageEnabled(...): Boolean;
begin
  Result := True;
  try
    Result := GetStorage(ADatabasePath).IsSecureImageEnabled(GetTableName, AImageKey);
  except
    on E: Exception do begin
      WriteLog(...);
      Result := True;  // fail-open
    end;
  end;
end;
```
- **问题说明**：异常时 `Result := True`，即"无法判定 = 启用"。安全模块应当 fail-closed。
- **触发条件**：数据库连接失败、表丢失、SQL 异常。
- **建议修复**：异常分支 `Result := False`（fail-closed）。

#### F1.1.4 ReseedMinimal 写入无法被 LoadSecureImageBytesFromDatabase 解密的记录
- **位置**：d:\_Progs\02Business\DeepBase\Features\DeepBase.AntiTamper.pas:542-563
- **原始代码**：
```pascal
Data.EncryptedImageData := EmptyData;     // 直接赋空明文，未走 EncryptImageData
```
- **问题说明**：`EncryptedImageData` 写入空明文（长度 0），未调用 `EncryptImageData`。加载 'seed' 时 `DecryptImageData([])` 在 `Length < AES_BLOCK_SIZE` 处抛异常。
- **触发条件**：调用 `LoadSecureImageBytesFromDatabase(ADatabasePath, 'seed', ...)`。
- **建议修复**：`Data.EncryptedImageData := EncryptImageData(EmptyData);`

### 🔵 优化建议

- **F1.1.5** ComputeHMACSHA256 把数据先转 hex 再 HMAC，是反模式（L221-228）。建议直接对原始 `TBytes` 做 HMAC。
- **F1.1.6** VerifyImageIntegrity 重复实现 constant-time 比较（L321-342），类内已有 `ConstantTimeCompare`。建议复用。
- **F1.1.7** HandleSecurityViolation 在工作线程调用 MessageBox + Halt 风险（L499-529）。建议工作线程仅记日志并 `TThread.Synchronize` 弹 UI。
- **F1.1.8** GetStorage 每次创建新 storage 实例可能重复打开数据库（L136-149）。建议缓存或使用连接池。

## F1.4 DeepBase.AutoUpdate.pas

**总体结论**：高层次的更新检查助手，整体设计清晰；存在 JSON 类型不匹配未保护、下载失败残留文件两个功能缺陷。

### 🟡 功能缺陷

#### F1.4.1 ParseInstallPolicy 中 JSON 类型不匹配会抛未捕获异常
- **位置**：d:\_Progs\02Business\DeepBase\Features\DeepBase.AutoUpdate.pas:336-363
- **原始代码**：
```pascal
Info.AllowSilentInstall := PolicyObj.GetValue<Boolean>('allowSilent',
  PolicyObj.GetValue<Boolean>('allow_silent', Info.AllowSilentInstall));
Info.IdleWindowMinutes := PolicyObj.GetValue<Integer>('idleWindowMinutes',
  PolicyObj.GetValue<Integer>('idle_window_minutes', Info.IdleWindowMinutes));
```
- **问题说明**：`TJSONObject.GetValue<T>` 当键存在但值类型不匹配（如 `"allowSilent": "true"` 字符串而非布尔）时抛 `EJSONException`/`EInvalidCast`。`ParseInstallPolicy` 自身没有 try-except。同时第二个参数（默认值表达式）总是被先评估，即使第一个键存在也会调用 `GetValue<Boolean>('allow_silent', ...)`，存在双倍解析开销。
- **触发条件**：version.json 中 `installPolicy` 块的某字段类型被错误地写成字符串/数字。
- **建议修复**：用 `TryFindValue` + `is TJSONBool`/`is TJSONNumber` 安全转换；整个函数包 `try/except` 容错。

#### F1.4.2 DownloadUpdate 中 CopyFrom 失败时残留部分写入的文件
- **位置**：d:\_Progs\02Business\DeepBase\Features\DeepBase.AutoUpdate.pas:829-834
- **原始代码**：
```pascal
ForceDirectories(ExtractFilePath(DestFile));
FS := TFileStream.Create(DestFile, fmCreate);
try
  FS.CopyFrom(Response.ContentStream, 0);
finally
  FreeAndNil(FS);
end;
```
- **问题说明**：`FS.CopyFrom` 在网络中断、磁盘满时抛异常，finally 仅释放 FS 但 `DestFile` 已部分写入。同时 `ForceDirectories` 失败抛异常会直接传播出函数（契约是返回 Boolean）。
- **触发条件**：下载中途中断、磁盘空间不足、目标目录无写权限。
- **建议修复**：CopyFrom 异常时 `DeleteFile(DestFile)`；`ForceDirectories` 失败时设 `FLastError` 并 `Exit`。

### 🔵 优化建议

- **F1.4.3** CheckForUpdateAsync 返回未启动的 Task，依赖调用方调用 .Start（L748-769）。建议返回前调用 `Result.Start`。
- **F1.4.4** DownloadUpdate 中 SHA256 验证失败仅 Exit，未删除已损坏的目标文件（L849-851），与签名失败路径不一致。建议失败时 `DeleteFile`。

## F1.5 DeepBase.Updater.pas

**总体结论**：功能完整的更新系统，但存在 manifest 签名验证输入不一致、`InstallDownloadedUpdate` 用 `'*.*'` 字面量作为备份清单导致回滚失效两个严重问题。

### 🔴 严重问题

#### F1.5.1 InstallDownloadedUpdate 用 `'*.*'` 作为备份文件清单，导致回滚完全失效
- **位置**：d:\_Progs\02Business\DeepBase\Features\DeepBase.Updater.pas:1963-1972
- **原始代码**：
```pascal
SetLength(FilesToBackup, 1);
FilesToBackup[0] := '*.*';
if not CreateBackup(FilesToBackup) then
  Exit;
Result := ApplyUpdate(PackagePath, FCurrentUpdate);
```
- **问题说明**：`CreateBackup` 内部对每个字符串执行 `TPath.Combine(FApplicationDir, Files[I])` 然后 `FileExists`。`FileExists(FApplicationDir + '\*.*')` 必然返回 False，不会复制任何文件到备份目录，但 `Result := True`。随后 `ApplyUpdate` 若中途失败，`RestoreBackup` 备份目录为空，没有任何源文件可恢复。如果 ApplyUpdate 已部分覆盖应用文件，则应用二进制损坏且无法回滚。
- **触发条件**：调用方使用 `InstallDownloadedUpdate`，且 ApplyUpdate 中途失败。
- **建议修复**：用 `TDirectory.GetFiles(FApplicationDir, '*.*', soAllDirectories)` 真实枚举备份清单。

#### F1.5.2 DownloadAndInstall 与 StageAndVerifyPackage 中 manifest 签名验证输入不一致
- **位置**：d:\_Progs\02Business\DeepBase\Features\DeepBase.Updater.pas:1841
- **原始代码**：
```pascal
// DownloadAndInstall 中：
if not VerifySignature(ComputedManifestHash, Info.ManifestSignature, SignatureAlg) then
// StageAndVerifyPackage 中（L1289）：
if not VerifySignature(ManifestPayload, Info.ManifestSignature, SignatureAlg) then
```
- **问题说明**：`StageAndVerifyPackage` 注释明确"manifest_signature 签的是 payload 的 UTF-8 字节（非 hash）"，传入 `ManifestPayload`。而 `DownloadAndInstall` 传入的是 `ComputedManifestHash`（SHA256 hash 字符串）。RSA-SHA256 验签内部会对输入做 SHA256 再比对，传入 hash 会变成"对 hash 再 hash"导致签名验证恒为 False。此外 DownloadAndInstall 路径的 ManifestHash 比较未剥离 `'sha256:'` 前缀，而 StageAndVerifyPackage 路径有剥离。
- **触发条件**：服务器返回非空 `manifest_signature` 字段，调用方走 `DownloadAndInstall` 路径。
- **建议修复**：与 StageAndVerifyPackage 路径对齐：`VerifySignature(ManifestPayload, ...)` 并剥离 `'sha256:'` 前缀。

### 🟡 功能缺陷

#### F1.5.3 DownloadFile 接受 ProgressCallback 但从不调用
- **位置**：d:\_Progs\02Business\DeepBase\Features\DeepBase.Updater.pas:1405-1436
- **原始代码**：
```pascal
function TUpdateManager.DownloadFile(const Url, DestPath: string;
  ProgressCallback: TProgressCallback): Boolean;
// ...ProgressCallback 从未被调用
```
- **问题说明**：`ProgressCallback` 参数声明存在但实现从未调用；同时 `Response.BodyBytes` 整体加载到内存再写入磁盘，对几百 MB 的更新包会消耗大量内存且无法反映下载进度。
- **触发条件**：调用 `DownloadFile` 或 `StageUpdatePackage`/`DownloadAndInstall` 时，UI 期望进度回调但拿不到。
- **建议修复**：用流式 transport 或分块写入，并在每块后调用 `ProgressCallback`。

#### F1.5.4 FSilentInstallTask 字段从未赋值，析构中的 Wait 是死代码
- **位置**：d:\_Progs\02Business\DeepBase\Features\DeepBase.Updater.pas:674-683 与 2095
- **原始代码**：
```pascal
// StartSilentInstallLoop 中：
TThread.CreateAnonymousThread(...).Start;  // 未保存到 FSilentInstallTask
// 析构中：
if FSilentInstallTask <> nil then ...  // 永远不执行
```
- **问题说明**：`StartSilentInstallLoop` 用 `TThread.CreateAnonymousThread(...).Start` 启动后台线程但未保存到 `FSilentInstallTask`。析构时若后台线程仍在运行，对象被释放，后台线程访问已释放的 `Self` 会 AV。
- **触发条件**：调用 `StartSilentInstallLoop` 后立即 Free 对象。
- **建议修复**：保存线程引用并 WaitFor 后释放。`FreeOnTerminate := False`，析构中 `FSilentInstallThread.WaitFor`。

#### F1.5.5 BuildManifestSignaturePayload 不包含 Files 列表
- **位置**：d:\_Progs\02Business\DeepBase\Features\DeepBase.Updater.pas:1151-1157
- **原始代码**：
```pascal
Result := Info.AppId + '|' + Info.Version.ToString + '|' +
  ChannelToString(Info.Channel) + '|' + Info.DownloadUrl + '|' +
  IntToStr(Info.DownloadSize) + '|' + Info.PackageHash + '|' + Info.Signature;
```
- **问题说明**：manifest 签名只覆盖元数据头部，不包含 `Files` 数组。攻击者若能修改 manifest 但保留头部签名，可替换 Files 中的 path/hash/url 字段。
- **触发条件**：攻击者篡改 manifest 的 Files 数组。
- **建议修复**：把 Files 列表按规范序列化（如按 path 排序、用 `|` 分隔）拼入 payload。

#### F1.5.6 TSemanticVersion.Parse 只 strip 小写 'v' 前缀
- **位置**：d:\_Progs\02Business\DeepBase\Features\DeepBase.Updater.pas:547-550
- **原始代码**：
```pascal
if (Length(Ver) > 0) and (Ver[1] = 'v') then
  Ver := Copy(Ver, 2, MaxInt);
```
- **问题说明**：与 `DeepBase.AutoUpdate.NormalizeVersion`（同时处理 'v' 和 'V'）不一致。`TSemanticVersion.Parse('V1.2.3')` 时版本号被解析为 0.0.0。
- **触发条件**：用户传入 `'V1.2.3'`，或服务器返回版本带大写 'V' 前缀。
- **建议修复**：`if (Ver[1] = 'v') or (Ver[1] = 'V') then`。

#### F1.5.7 CleanupTempFiles 中 TDirectory.GetFiles 在 FTempDir 不存在时抛异常
- **位置**：d:\_Progs\02Business\DeepBase\Features\DeepBase.Updater.pas:2262-2279
- **原始代码**：
```pascal
var Files := TDirectory.GetFiles(FTempDir, '*.zip');
```
- **问题说明**：`TDirectory.GetFiles` 在目录不存在时抛 `ENotFound`，函数没有 try-except。若 FTempDir 被外部清理或从未创建，会再抛异常覆盖原始错误。
- **触发条件**：FTempDir 不存在。
- **建议修复**：开头加 `if not TDirectory.Exists(FTempDir) then Exit;`。

### 🔵 优化建议

- **F1.5.8** 全局单例 `Updater()` 双重检查锁定无 memory barrier（L442-455）。建议用 `TInterlocked.CompareExchange`；finalization 中加锁。
- **F1.5.9** FCancelled/FLastError/FStatus 多线程访问无原子保护。建议用 `TInterlocked.Exchange` 写 FCancelled；所有读写进 FLock。

## F1.6 DeepBase.ClipboardGuard.pas

**总体结论**：RAII 剪贴板保护设计良好，但 GlobalAlloc/GlobalLock 失败未检查会导致 AV；引用计数非原子。

### 🔴 严重问题

#### F1.6.1 SetContent/SetContentBytes/RestoreInternal 中 GlobalAlloc 失败未检查导致 AV
- **位置**：d:\_Progs\02Business\DeepBase\Features\DeepBase.ClipboardGuard.pas:185-189, 201-205, 265-269
- **原始代码**：
```pascal
var hMem := GlobalAlloc(GMEM_MOVEABLE, CharSize);
var pMem := GlobalLock(hMem);
Move(PChar(Text)^, pMem^, CharSize);  // pMem 为 nil 时 AV
```
- **问题说明**：`GlobalAlloc` 在内存不足时返回 0。`GlobalLock(0)` 返回 NULL，`Move(..., pMem^, ...)` 在 pMem 为 nil 时直接 AV。`SetContentBytes` 还有 `Move(Data[0], pMem^, ...)`，如果 `Data` 为空数组，`Data[0]` 也会 AV。
- **触发条件**：内存压力下 GlobalAlloc 返回 0；或调用 `SetContentBytes` 传入空 TBytes。
- **建议修复**：检查 `hMem = 0` 和 `pMem = nil`，失败时 `GlobalFree(hMem)` 并抛异常。

### 🟡 功能缺陷

#### F1.6.2 SetClipboardData 失败时 hMem 内存泄漏
- **位置**：d:\_Progs\02Business\DeepBase\Features\DeepBase.ClipboardGuard.pas:189, 205, 269
- **原始代码**：
```pascal
SetClipboardData(CF_UNICODETEXT, hMem);  // 未检查返回值
```
- **问题说明**：Windows 剪贴板契约：成功时 hMem 所有权转移，失败时所有权仍归调用方必须 GlobalFree。当前未检查返回值，失败路径也未 GlobalFree。
- **触发条件**：剪贴板已关闭、格式不支持。
- **建议修复**：检查返回值，失败时 `GlobalFree(hMem)`。

#### F1.6.3 Save 中 GlobalLock 返回 nil 未显式检查
- **位置**：d:\_Progs\02Business\DeepBase\Features\DeepBase.ClipboardGuard.pas:154-163
- **原始代码**：

Move(pData^, Bytes[0], DataSize);  // pData 为 nil 时 AV

- **问题说明**：锁失败时 `pData` 为 nil，`Move(pData^, ...)` 直接 AV。

### 🔴 严重问题

#### F1.7.1 ParseRfc822Date 忽略 GMT 时区，与本地时间比较产生系统性偏差
- **位置**：d:\_Progs\02Business\DeepBase\Features\DeepBase.TimeGuard.pas:183-268 与 393-460
- **原始代码**：

- **触发条件**：构造后未调用 Verify 即调用 IsTimeTrusted。
- **建议修复**：新增 `tgNotVerified` 枚举值，构造时设为 `tgNotVerified`。

## F1.8 DeepBase.WindowMonitor.pas

**总体结论**：前台窗口与进程监控实现清晰，但 `QueryFullProcessImageNameA` + `PChar` 类型不匹配会导致进程名乱码；多个回调与状态字段是 dead code。

### 🔴 严重问题

#### F1.8.1 声明 `QueryFullProcessImageNameA` 但用 PChar (PWideChar) 导致进程名乱码
- **位置**：d:\_Progs\02Business\DeepBase\Features\DeepBase.WindowMonitor.pas:102-104 与 425-429
- **原始代码**：
```pascal
function QueryFullProcessImageName(hProcess: THandle; dwFlags: DWORD;
  lpExeName: PChar; var lpdwSize: DWORD): BOOL; stdcall;
  external 'kernel32.dll' name 'QueryFullProcessImageNameA';
```
- **问题说明**：dcc64 中 `PChar = PWideChar`，但 `name 'QueryFullProcessImageNameA'` 链接到 ANSI 版本。ANSI 函数向 WideChar 缓冲区写入：每个 ANSI 字符占 1 字节，而 WideChar 缓冲区每槽 2 字节。`PChar(Result)` 读出的字符串到第二个 WideChar 的 0x0000 就终止，`Result` 实际只截取到 "C"。前台变化检测基本失效。
- **触发条件**：任何调用 `GetProcessNameFromHWND` 的场景。
- **建议修复**：改用 `QueryFullProcessImageNameW`：`external 'kernel32.dll' name 'QueryFullProcessImageNameW'`。

#### F1.8.2 Stop 中 WaitFor 无超时，"did not exit in 5s" 注释错误
- **位置**：d:\_Progs\02Business\DeepBase\Features\DeepBase.WindowMonitor.pas:174-182

#### F2.A.5.1 Shutdown 锁内释放接口引用可能重入死锁
- **严重度**：🟡
- **位置**：d:\_Progs\02Business\DeepBase\Features\DeepBase.Browser.Service.pas:86-97
- **原始代码**：
```pascal
class procedure TBrowserService.Shutdown;
begin
  FLock.Enter;
  try
    FDefaultSession := nil;
    FRecovery := nil;
  finally
    FLock.Leave;
  end;
end;
```
- **问题说明**：`FDefaultSession := nil` 和 `FRecovery := nil` 会在锁内触发接口引用计数减 1。若引用计数归零，底层对象析构器执行。若析构器（例如 `TBrowserRecoveryManager.Destroy` → `StopHealthMonitor` → 健康监控线程回调 `TBrowserService.Session`）重入 `FLock`（TCriticalSection 不可重入），将死锁。
- **触发条件**：Shutdown 时 Recovery 析构链回调 TBrowserService。
- **建议修复**：锁内将接口引用复制到局部变量并置字段为 nil，锁外释放局部变量：
```pascal
class procedure TBrowserService.Shutdown;
var
  LSession: IBrowserSession;
  LRecovery: IBrowserRecovery;
begin
  FLock.Enter;

if (FMaxRequestBodySize > 0) and (ARequestInfo.ContentLength > FMaxRequestBodySize) then
begin
  AResponseInfo.ResponseNo := 413;
  Exit;
end;
// ... 随后 SS.CopyFrom(PostStream, 0) 全量读入内存
```
- **问题说明**：`ContentLength` 对 chunked transfer-encoding 为 -1，`-1 > 10MB` 为 False，限制被绕过；随后 `SS.CopyFrom(PostStream, 0)` 全量读入，恶意客户端可用 chunked 流式上传超大体耗尽内存（DoS）。
- **触发条件**：客户端使用 `Transfer-Encoding: chunked` 且不发送 `Content-Length`。
- **建议修复**：读取时按 `MaxRequestBodySize+1` 限量，超过即 413。

#### F1.14.3 CORS 中间件默认空 origin 仍对 OPTIONS 返回 204 中断链
- **位置**：d:\_Progs\02Business\DeepBase\Features\DeepBase.HttpServer.pas:831-887
- **原始代码**：
```pascal
if FAllowOrigin <> '' then
  Ctx.Response.Header('Access-Control-Allow-Origin', FAllowOrigin);
if Ctx.Request.Method = hmOptions then
begin
  Ctx.Response.Status(204);
  Exit;   // 不调用 Next，即使 AllowOrigin 为空
end;
```
- **问题说明**：`FAllowOrigin=''` 时不设置任何 CORS 头，但 `hmOptions` 仍返回 204 并 `Exit`——后续中间件与路由不执行。其他 OPTIONS 路由永远无法触达。
- **触发条件**：用户 `Server.Use(TCorsMiddleware.Create)`（不传 origin）并发起 OPTIONS 预检。
- **建议修复**：`FAllowOrigin=''` 时不拦截 OPTIONS，让 `Next` 处理。
