## 二、判据 2 · 三选一方案书

### 方案 (a) 接通 self-hosted `delphi-windows` runner

| 维度 | 内容 |
|---|---|
| 动作 | 在某台 Windows 机器注册 GitHub self-hosted runner，加 `delphi-windows` 标签；同步修 yml 的 `DELPHI_PATH`/`DELPHI_VERSION` 到 37.0；同步修 yml 头部的 runner requirements 注释 |
| 成本 | **老板的机器 + 老板的时间**：一台常开 Windows 机的注册与维护、Delphi 授权与 SDK 装在自托管机上（含 FireDAC SQLite、`sqlite3.dll`，yml 头注释已列全）；本仓库侧是 3 处 yml 改动 |
| 可逆性 | **高**：runner 可随时 `remove runner`；yml 改动是纯文本 |
| 对禁动区的影响 | `.github/workflows/**` **不在**本单禁动区（MC3 禁动区是 `Core/**`、`contracts/**`、`Features/DeepBase.Licensing.pas`、`Tests/**`、`Tests/Integration/**`、`Scripts/**`、`TestResults/**`、`noise-baseline.json`），但**工单明令：决策点上交、老板拍板前不得动** |
| 对门禁读数的影响 | 若接通，CI 将**首次**真正执行 `contract-gate`（当前 HEAD EXIT=1，含 CONTRACTGATE 待修的假阳性）⇒ **CI 会从「零信号」变成「稳定红」**。这不是坏事（红是真信号），但必须与 CONTRACTGATE 的时序对齐，否则接通即红会被误读成新回归 |
| 前置 | 老板批准机器；C2 的版本口径必须同时修 |

### 方案 (b) 改 `integration-tests` job 为 GitHub 托管 Windows runner

| 维度 | 内容 |
|---|---|
| 动作 | 把 `runs-on` 改成 `windows-latest`（或带 Delphi 的自建镜像），并解决 `DELPHI_PATH`（托管 runner 上没有 RAD Studio 许可 ⇒ 只能靠 `choco`/私有缓存/镜像，且**许可仍是硬约束**） |
| 成本 | **许可成本被搬到了 CI 上**：GitHub 托管 runner 无法合法持有 Embarcadero 编译许可，除非走私有镜像 + 组织级许可安排。同时 yml 的路径假设要全量重核（`tzutil` 固定非 UTC 时区、FireDAC SQLite、`sqlite3.dll` 来源） |
| 可逆性 | **中**：yml 可回滚，但镜像构建流水线的沉没成本高 |
| 对禁动区与门禁读数的影响 | 同 (a)：接通即红。另需评估 yml 里既有 `tzutil` 假设（MC1 项 3 只做了静态登记、运行期效果因 runner 未接通如实未验）在托管 runner 上是否仍成立 |
| 前置 | 老板批准托管 runner 上的编译许可路径 |

### 方案 (c) 正式 DEFERRED + 双处明示「集成跑录从未执行」（**本单推荐**）

| 维度 | 内容 |
|---|---|
| 动作 | ① 在 `.github/workflows/delphi-ci.yml` 的**文件头注释**与 **`name`/job 名**处把「流水线覆盖了什么」改成事实陈述——明确写「本流水线依赖 self-hosted `delphi-windows` runner，**自建库以来从未执行过任何 step**；所有『CI 绿』记录均属零信号，不得作为覆盖证据」；② 台账 §三 同处登记同一条事实；③ **不做**任何 `runs-on` 改动 |
| 成本 | **零机器、零许可、零 yml 行为改动**；只有文案与台账 |
| 可逆性 | **最高**（纯注释/文案，随时可改回） |
| 对禁动区与门禁读数的影响 | **零**（不动判定面）；但**它会摘掉一个正在误导人的暗示**，这是本方案的全部价值 |
| 前置 | 无。**本单可自行落地 §2 的 ①②③ 三步**（都在授权面内：yml 头注释属 `.github/workflows/**`——⚠️ 见下方边界说明） |

**⚠️ 边界自查**：工单项 2 明写「**老板拍板前不得动 `.github/workflows/**`**」。因此**本单连方案 (c) 的 yml 文案也不写**，只把该改什么、改在哪一行、原文是什么逐条列出（见 §三），交由老板拍板后由主控落笔。**这不是偷懒，是遵守工单的中止线**；台账那一半（§三 的 T2 行）同样由主控在验收时回填。

## 五、TimeGuard 非 Windows raise 分支：是否必须等 runner？

**工单项 2 任务 3 的问题，结论：不必须等 Windows self-hosted runner，但必须等「某个 Linux 执行环境」——两者不是一件事。**

| 判定项 | 结论 | 取证 |
|---|---|---|
| 目标面 | `Core/DeepBase.Security.SecretStore.pas:99` 的 `raise ESecretStoreUnavailable` 位于 `{$ELSE}`（非 Windows）分支，**Windows 进程内不可达**（已亲读确认：`:51-56` 的 uses 分支、`:91-103` 的工厂方法分支、`:105-128` 整段 `TWindowsSecretStore` 实现都在 `{$IF DEFINED(MSWINDOWS)}` 内） | 源码逐行 |
| 交叉编译能不能验？ | **能验「编译」，不能验「行为」**。本机 `...\37.0\bin\dcclinux64.exe` 存在 ⇒ 可交叉编译该单元证明 `{$ELSE}` 分支语法与链接成立；但「工厂抛异常 ⇒ 适配器返 nil」是**运行期**行为，交叉编译不产生可执行文件 | `Test-Path` 实测 |
| 本机 WSL 能不能替代？ | **不能在本轮判定**。`wsl --status` 在本机会话内挂起未返回（超时 120 s），既不能证明可用也不能证明不可用 ⇒ **如实登记为「未取证」，不假装有** | 命令超时留痕 |
| 与 CI runner 的关系 | Windows self-hosted runner **帮不上**：目标是 Linux 分支，Windows runner 上那段代码根本不编译。**真正需要的是 Linux 执行环境**（WSL2 + Linux 侧 Delphi，或一台 Linux runner，或 Linux 容器 + `dcclinux64` 产物运行） | 逻辑必然 |

⇒ **结论**：该项**不并入** CI runner 决策，另立「Linux 执行环境」前置；在此之前该项维持「未复证」登记，**不得表述为「已验证」或「不适用」**。
