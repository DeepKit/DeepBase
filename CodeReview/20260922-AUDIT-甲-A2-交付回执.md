## 一、交付面三件

### A2-1 建钥 DACL 收敛（默认收紧 + 声明式豁免）

缺陷根因确认：owner-only DACL 实施此前**只在导出路径被调用**，`LoadOrCreate` 走的是
POSIX-only 的 `ApplyOwnerOnlyMode`，Windows 建钥因此落在全继承的 ACL 上（主控实测的
9 条 `(I)` 条目、含 `FY3700\CodexSandboxUsers:(I)(M)`，本单复现见证据 02 的 RED 段）。

修法（不写第二份实施）：`ApplyOwnerOnlyToFile` 作为唯一分发器，Windows 走单条目 +
禁继承 DACL 并回读证明，POSIX 走 `0600`；建钥面与导出面同源调用它。`LoadOrCreate`
现在两处施加：临时文件写入后一次、`TFile.Move` 落地实名后再一次（改名是卷可能重新
评估继承权限的地方，也是后续所有运行信任的那个文件名）。第二处失败即删除该文件并重抛：
一把还没封存任何数据的密钥被删掉不损失任何数据，却不会在盘上留下一份可读的秘密。

豁免只有一种，且是声明式 + 可观测 + 默认关：`DEEPBASE_MASTER_KEY_FILE` 非空 **且**
`DEEPBASE_MASTER_KEY_EXTERNAL_ACL=YES`。默认路径不接受该声明（用户自己的 profile 目录
里"权限由别人管"不是一条值得接受的主张）；取值只认 `YES`，其它任何写法（含拼错）都算
未声明 ⇒ 收紧而不是放开。豁免生效时 `LoadOrCreate` 经宿主注入的 `TMasterKeyNotice`
打印"未收紧"的事实，`security status` 亦持续打印 `[WARN] Access policy`。旁路扫描见判据 2。

### A2-2 迁移建钥可观测（防静默）

`TUserMasterKey.RequireExistingKey(AOperation, AAllowProvisioning)`：密钥文件不存在且
本次未被显式放行 ⇒ 抛 `ESecurityException`，文案说明"现在新建的密钥封存的数据没有任何
早先的备份能打开，且会让旧密钥对应的备份全部对不上"，并指出恢复或放行的两条路。
`MigrateLegacyUBS2Secrets` 增 `AAllowProvisioning: Boolean = False`，门禁语句放在
`FStorage` 检查与取钥**之前**（`BuildUBS2Key` 是产品代码里唯一的 `LoadOrCreate` 调用点，
迁移经它取钥）。
`security status` 现在区分密钥来源两分支：`existing key file, read as it is` /
`no key file yet - the first use that seals data provisions one at the path above`，
后者同时给 `[WARN]` 并以退出码 1 结束；`status` 本身绝不建钥。

## 三、实现取舍（写在这里以免另立一套说法）

- 叶子密钥单元不引控制台：建钥事实通过宿主提供的 `TMasterKeyNotice` sink 出口。
  POSIX 侧 `BuildUBS2Key` 把 notice 送到 `DeepBase.Logger.Warn`；Windows CLI 侧由调用方
  决定是否注入。**manager 尚未初始化时没有日志可写**，所以这两条事实同时能从
  `security status` 读到，并在迁移路径由 `RequireExistingKey` 直接拒绝——不依赖"一定会打印"。
- `status` 只读：一次查询若把密钥创建出来，就会掩盖它本来要报告的那次丢失。
- 未追溯收紧既有文件：A2-1 的收紧作用于新建。一把更早建出来的密钥保持它建出来时的权限，
  直到属主自己用 `icacls`/`chmod` 改掉。这是本次交付的边界，不是遗漏（手册已同口径写明）。
