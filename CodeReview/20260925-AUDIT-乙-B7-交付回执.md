**fail-closed 的两种形态（选型理由，同步写进提交说明）**：查询型 API（`GetCorrectedNow`）抛异常——调用方拿到的是「时间」，无法用某个合法值表达「不可信」，返回哨兵值反而会伪装成可信读数；判定型 API（`GetTrialDaysRemaining`/`IsTrialActive`）返回不可用（`0`/`False`）——其语义本就是布尔/计数，且 `RefreshCachedTier` 等既有调用方在 `try/except` 外裸调，判不可用比抛异常更符合「拒绝放行」。两者都不回退到裸墙钟，符合 §〇-7。

**时间框架（为什么比较两侧都是 naive-local 裸值）**：试用到期存的是 Zulu（`DateToISO8601(...,True)`），`TryISO8601ToDate(..., False)` 对带 `Z` 的输入仍做 UTC→本地换算 ⇒ 解析结果是**本地裸值**；`TDeepBaseTimeSource` 的默认读数就是 `System.SysUtils.Now`（本地裸值）⇒ 同框架。修前把墙钟 `ToUniversalTime` 后再与本地裸值比较，正是乙 B9 §四.1 / 乙 B10 上报的那类混框架点位（本单把它在 Licensing 域内消掉）。框架选择由用例 `Test_TrialDays_FollowInjectedCoreClockNotWallClock` 的第二段断言钉住，换机器即红。

**为什么用 `SeedWatermark` 而不是 `SetNowFunc(GetCorrectedNow)` 全局注入**：`SetNowFunc` 的闭包若捕获 `Self`，会把「某个 `TDeepLicensing` 实例的守卫」写进 Core 的进程级单例——实例释放后是悬挂引用，多实例时互相覆盖，且全局时钟被单个产品的校钟结果劫持。改为把守卫的受信读数**只升不降地并进水位**（`:873` 仅 `tgOk`/`tgSkewMinor` 播种）：服务器侧提前或被篡改的读数最多缩短许可窗口，永不能续命；`tgSkewMajor`/`tgClockRewound` 的读数一律不入水位（用例 `Test_MajorSkewClock_RefusedAndNotSeededIntoCoreClock` 以 `LastSeen <= 0` 咬住）。

**`tgOffline` 仍判受信的取舍**：`TTimeGuard.IsTimeTrusted`（`Features/DeepBase.TimeGuard.pas:470`）的受信集合含 `tgOffline`，而 §〇-3 规定 TimeGuard 只读 ⇒ 离线启动仍是「可信」，试用照判。收紧它属**过紧回归**（判据③要求可信路径与修前一致），且会把「服务器不可达」误当成「时钟被改」——真正的回拨防线在 Core 单调水位（跨进程只升不降）＋在线时的 `tgSkewMajor`/`tgClockRewound` 拒绝。若主控认为离线也该拒绝，请另派一单连 TimeGuard 一起改。

## 四、`\bNow\b` 非判时用途逐条说明（工单 §一-静态自证要求）

- `:1011 var StartTime := Now;` 与 `:1017 if SecondsBetween(StartTime, Now) >= TimeoutSec then`：`ConfirmPurchase` 的**同一进程内耗时测量**，只决定「轮询是否超时」，不参与任何许可/试用有效性判定 ⇒ 不属判时点，保留裸墙钟。
- 登记风险（不在本单修）：同一次轮询期间发生时钟回拨会使 `SecondsBetween` 为负 ⇒ 该轮不触发超时（不会放大权限，只是少判一次超时；前跳则可能提前放弃）。正确形态是改用单调计时源（`TStopwatch`/`GetTickCount64`），与本单时间源语义无关，见 §六.5。
