## 六、`docs/data/trunk-quantisation.txt` 的 int4 误差实测（逐字节选）

```
method: 31 attention-projection tensors sampled from the released checkpoint
        by HTTP range read - real weights, no full download. 384 rows per tensor.
        Each tensor is round-tripped through int8 and int4 with one fp32 scale

L9.k_proj                            0.00914    0.16568    18.1x
L7.kv_b_proj                         0.00741    0.13427    18.1x
```

原文结论句：

```
K3's technical report section 4.1.4 states that the experts are MXFP4 with
quantisation-aware training "while all non-expert components remain in higher
precision" - that list IS the trunk, so it was never trained to tolerate 4-bit.
...
So the engine quantises NOTHING: routed experts are already MXFP4 in the
checkpoint and are multiplied in that form, and the trunk is copied byte for byte.
```

## 七、上游 docs/BENCHMARKING.md 的测量纪律（逐字节选）

```
**The measured run-to-run spread on an identical configuration is 33%.**

run | s/token
  1 | 14.78
  2 | 14.67
  3 | 20.14
mean 16.53, sd 3.13, spread 33.1%

If your A/B differs by less than that, you have measured nothing.
```

污染源清单（原文列）：后台自动更新（`unattended-upgrades` 占掉约 63% 一核）、两个引擎同时在跑、冷热页缓存、冷启动（token 0 付全部 trunk pinning 代价；8 token 的运行被它主导）、不同存储（**「This workload moves ~135 GB per token」**）。

建议改测的量（原文）：

```
- GB read/token, bytes actually pulled from disk
- requests / evictions, cache retention, derived as 1 - evictions/requests
- pinned N/93 layers, how much trunk is resident
- generated token ids, for correctness, exact
```
