## 二、三路评审意见

| 视角 | 选择 | 核心理由 |
|---|---|---|
| 架构 / 长期主义 | **新轨** | 旧轨是 Windows-BPL 专用、Delphi 单编译器锁定、进程内（插件崩即宿主崩），源码自承"非 Windows 需另写"⇒ 死路；新轨语言无关、Lease 门禁直击 BUG340 暴露的卸载脆弱性 |
| 工程可执行性（单人维护） | **冻结共存** | 旧轨维持现状成本 = 0；推新轨最高停摆点在"接入 dpk 并替换生产接线"，单人无真实需求驱动时极易停在"半套能编译但无生产调用"，比现状更糟 |
| 安全 / 治理 | **旧轨** | 旧轨验签走 `WinVerifyTrust` 且实测 fail-closed，三个回归钉是真实历史缺陷；新轨门禁从未被执行，结论上限只能是"代码存在、设计意图 fail-closed" |

## 四、终裁

### 裁定 1：生产唯一真相源 = **旧轨（BPL）**

判据 —— 本仓铁律 `Canonical Claim ≤ Git Evidence ≤ Runtime Evidence`：

- 旧轨：已编译（在 dpk 内）+ 已接线（`Manager.pas:429`）+ 有回归钉（3 个真实历史缺陷，全部入库）+ 验签实测 fail-closed ⇒ **具备完整运行时证据链**
- 新轨：不在构建、零调用、加载入口编译不过 ⇒ `SafeGuard` / `Verifier` / `TPluginLease` 三项门禁**无任何运行时证据**。其结论上限只能是「代码存在、设计意图 fail-closed」，**不得作为能力采信**，更不得作为选型理由

**质量优先 ≠ 追新。** 新轨的设计确实更先进（跨 ABI、Lease 计数门禁、热重载），但它当前**不是质量，是债务**。把未编译、未执行的代码当成"更好的架构"替换掉有运行时护城河的生产轨，是用纸面换实物。

### 裁定 2：新轨**冻结隔离**，不立即删除 —— 但附硬约束与复活门槛

不删除的理由：它有真实架构价值，删除不可逆；且其价值主张（跨 ABI / 卸载安全）对应旧轨的真实弱点（BUG340 卸载顺序缺陷、Windows 锁定）。

但"冻结"**不等于无限期搁置**，必须满足以下全部约束：

| # | 硬约束 | 落地动作 |
|---|---|---|
| C1 | **消解同名类（最高优先）** | 新轨 `TDeepBasePluginManager` 改名为 `TDllPluginManager`（或 `TPlugins.Manager` 命名空间化）。**这是活雷**：一旦被任何单元 `uses`，会静默遮蔽旧轨，且编译期未必报错 |
| C2 | **禁止进入生产构建** | 6 单元严禁加入任何 `.dpk`/`.dproj`；CI 增加扫描：生产包 `uses` 含 `DeepBase.Plugins.` 前缀 ⇒ **BLOCK** |
| C3 | **显式标记** | 6 单元文件头加 `[FROZEN — NOT IN BUILD — DO NOT USE IN PRODUCTION]`；乙单 B3 构建归属清单中登记为 `非构建资产（待复活评估）` |
| C4 | **不可信灰盒** | 新轨门禁在通过复活门槛前，**不得被任何路径默认信任**，不得写入任何"新轨已具备 X 能力"的结论 |
| C5 | **复活门槛（可证伪，四条全满足才允许评估启用）** | ① 修 `Manager.pas:431`、`CAbiLoader.pas:228`/`:236` 的 `PChar → PAnsiChar`，6 单元进入**独立测试包**并编译通过 ② `PluginLifecycleHarness.dpr` 在 CI 独立 job 跑通，产物留存可核 ③ 三个等价回归迁移并全绿：沙箱（BUG062）/ 配置绕过（BUG063）/ 卸载顺序（BUG340）+ 新增验签用例 ④ **存在真实生产调用需求**（跨语言插件、非 Windows 平台、或热重载需求）—— 不得为"架构更好看"而启用 |

### 裁定 3：旧轨**必须补的一课**

BUG340（插件卸载顺序）证明旧轨卸载域存在真实缺陷，而这正是新轨 `TPluginLease` 的设计动机。裁定：**旧轨不因本次选型获得豁免**，其卸载顺序安全问题由甲单另立条目跟踪（不依赖新轨复活）。
