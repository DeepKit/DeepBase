## §52 双重编码乱码的【确定式】逆解（2026-09-24 主控突破）

**结论先行**：UTF-8 字节被当 GB18030 解码造成的乱码，是**可逆的双射**，不用猜。
卡住所有人的是两个假象，逐个破除即可：

### 假象一：`str.encode('gb18030')` 会把 PUA 字符编错 ⇒ 看着不可逆

PUA（U+E000–U+F8FF，私有区）字符在 `encode('gb18030')` 时会被编成 **4 字节**（如 `\ue750` → `84 31 A4 37`），
而它原本来自 **2 字节** ⇒ 反向字节流错。教科书式的 `encode('gbk').decode('utf-8')` 因此漏检或还原错。

**破法**：穷举 GB18030 双字节表，建**反查表 char → 字节对**，一次建成永久可用：

```python
for b1 in range(0x81, 0xFF):
    for b2 in list(range(0x40, 0x7F)) + list(range(0x80, 0xFF)):
        bs = bytes([b1, b2])
        ch = bs.decode('gb18030', errors='replace')
        if ch != '\ufffd': REV.setdefault(ch, bytes([b1, b2]))
```

实测：**每个字符（含 2068 个 PUA）都只有唯一字节对**（多解字符数 = 0）⇒ 还原唯一确定。
对整段乱码：逐字符查表拼字节流 → `bytes.decode('utf-8')` ⇒ 原文到手。

### 假象二：「能 UTF-8 解码成功」就能判定是乱码 ⇒ 会把正常中文改坏

**致命坑**：GB18030 的汉字双字节**恰好常落在合法 UTF-8 双字节区间**
（`C2–DF` 后接 `80–BF`）⇒ 正常中文也能「解码成功」，只是变成 `'Ŀǰȱʧ'` 一类的怪拉丁字母。
主控的真实惨案：`目前缺失` 差点被改写成 `Ŀǰȱʧ`。

**破法**：叠加**可读性闸门**——还原结果的每个字符必须落在
`CJK(0x4e00–0x9fff) / ASCII / 中文标点` 内，出现任何其他字符即拒绝。
有了这道门，反而可以放心把段长下限放宽到 1 个字。

### 标准作业流程

1. 建 GB18030 反查表（一次，缓存成 json）
2. 对每段非 ASCII 连续段：查表拼字节 → UTF-8 解码
3. **可读性闸门**（挡假象二）
4. **正向强校验**：`damage(结果) == 现场乱码`（尾部残缺允许超长 ≤3）——这是硬证据
5. 尾部残缺（原 U+FFFD 或 `?` 占位）：枚举 1–2 个补全字节，得到约 64 个候选，
   按项目自身 **二元词频**排序取 top1；**要求 top1 分 ≥ 1.5× top2 分** 才采用，否则留待人工
   （实测抽样 top1 命中率 ~83%：正确字能组成 `完成/失败/原问` 这类常见 bigram，干扰项 `原问颀` 几乎不成词）
6. 占位符清理：`?` 是当年工具写的丢失字节占位，**修复后必须删掉**；
   但若占位符后紧跟 `/`（如 `?/summary>`）⇒ 被吞的其实是 XML 尖括号，还原成 `<`，**别删**

**反面教训**：任何改动源码的批量脚本，**必须先 dry-run 并逐条抽查**再做 `--apply`。
本次正是靠 dry-run 抓到了「把正常中文改成乱码」的误伤（见假象二）。

**效率坑**：不要对正常文本段跑搜索型 DFS（会指数爆炸、15 分钟跑不完）。
用反查表做 O(n) 直接映射；只在 64 候选排序时才有计算量。
