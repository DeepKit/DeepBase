
## §52 混合行乱码：genuine 段误反解 + join 丢字炸弹（2026-09-24 最终收口）

**场景**：双重编码文件的「混合行」——可读中文与乱码段共存于同一行；行尾/行中 `\uFFFD?` 占位。

**四条硬教训**：

1. **genuine 短路判据**：段本身可读且含 CJK ⇒ 是幸存原文，**不得**做 GB18030 反解
   （真实汉字的 GB 字节不是合法 UTF-8，反解必然 fail，v14 因此 65 行误判 undecodable）。

2. **rank_last 权重**：尾字补全打分必须 `BIGRAM×1000 + 字频`，否则 `的/不/用`
   等全局超频字压过强 bigram（`捷→键` 120 次 vs `的` 2.3 万次纯字频）。

3. **join-drop = 延迟炸弹**：字符串字面量里的 `?);` —— `?` 吞的不只是汉字还有收尾
   `'` 引号。join 后产生**未闭合字符串 = 编译错误**（`Assert.Fail('…执);`）。
   ⇒ join 类结果必须**逐条人工判读**，重点核「单引号配对 + 括号闭合 + 被吞的换行」。
   实测 114 条 join 里揪出 20+ 条代码破坏。

4. **2× 边距会拒真**：`完成`(1717) vs `完整`(1220) 都是真词，bigram 比 1.4× 过不了
   2× 边距 ⇒ 安全拒绝是对的，但兜底不能靠 join 留半句，必须转人工语义判读。

**占位符定量规则（实测校准）**：`FFFD+?` ≈ 1 个汉字/全角标点（3 字节）；
连续 N 个 FFFD ≈ N/2.5 个汉字。孤证不立——**优先用代码锚定**：
EventBus `超时设?000ms` 由下方 `WaitFor(2000)` 锚定 `置 2`；
WebAPI `成username` 由生产码 `GetStringClaim('username', Result.UserId)` 判为 `或`。

**CRLF 写回陷阱**：逐行写回时 `split('\n')` 会保留行尾 `\r`，若再做
`replace('\n','\r\n')` ⇒ **全文件 CR 加倍**（`\r\r\n`），diff 变整文件重写。
写回后必查：`bytes.count(b'\r') == bytes.count(b'\n')`（纯 CRLF 文件），
且 `git diff --numstat` 行数 ≈ 改动行数（整文件量级 = 加倍事故）。

**流程定式**：自动逆解（可读性闸门 + 正向强校验）→ 结构/历史对照 →
自动兜底 → **人工逐条判读（全量过目，重点：引号/括号/换行拆分）** →
独立复扫（PUA/FFFD=0）→ 三门 → 原子提交 → 隔离树编译。
