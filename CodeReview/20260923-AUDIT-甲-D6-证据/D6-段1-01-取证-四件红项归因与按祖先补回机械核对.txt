§二  PluginLifecycleHarness：为什么改 20 处标识符，而不是「补 uses」
--------------------------------------------------------------------------------------------------
工单前提：「你的修法不得把新轨解冻、不得把旧轨改掉，只补 `uses` 或在冻结边界内处理」。
实测结论：在该件上，「补 uses」与「不动轨」互斥，故选冻结边界内的第二条路。命令与输出：

```
$ git grep -n "TDeepBasePluginManager\b" -- Core/DeepBase.PluginManager.pas
Core/DeepBase.PluginManager.pas:91:  TDeepBasePluginManager = class      ← 旧轨类确有声明

$ sed -n '20,29p' Tests/Plugins/PluginLifecycleHarness.dpr               ← harness 的 uses 面
uses
  ShareMem,
  System.SysUtils, System.Classes, System.IOUtils, System.Hash,
  Winapi.Windows,
  DeepBase.Plugins.Contracts in '..\..\Core\DeepBase.Plugins.Contracts.pas',
  DeepBase.Plugins.SafeGuard in '..\..\Core\DeepBase.Plugins.SafeGuard.pas',
  DeepBase.Plugins.Verifier in '..\..\Core\DeepBase.Plugins.Verifier.pas',
  DeepBase.Plugins.Manager in '..\..\Core\DeepBase.Plugins.Manager.pas',
  DeepBase.Plugins.CAbi in '..\..\Core\DeepBase.Plugins.CAbi.pas',
  DeepBase.Plugins.CAbiLoader in '..\..\Core\DeepBase.Plugins.CAbiLoader.pas';
                                       ↑ uses 面只有新轨，旧轨单元 DeepBase.PluginManager 不在其中

$ git grep -n "TDllPluginManager = class" -- '*.pas'
Core/DeepBase.Plugins.Manager.pas:99:  TDllPluginManager = class          ← 新轨类（harness 已 uses 该单元）

$ git grep -n "procedure RegisterPluginKind\|procedure SetPluginDllPath\|property Verifier" \
      -- Core/DeepBase.Plugins.Manager.pas Core/DeepBase.PluginManager.pas
Core/DeepBase.Plugins.Manager.pas:141:    procedure RegisterPluginKind(const AKind, ACreateFuncPrefix: string;
Core/DeepBase.Plugins.Manager.pas:149:    procedure SetPluginDllPath(const AName, ADllPath: string);
Core/DeepBase.Plugins.Manager.pas:176:    property Verifier: IPluginVerifier read FVerifier write FVerifier;
                                       ↑ harness 调用的三个成员只存在于新轨，旧轨面一个都没有

$ git show 0d1fe7c:Tests/Plugins/PluginLifecycleHarness.dpr | grep -c "TDeepBasePluginManager"
20                                                                       ← 工单/回执口径「20 处标识符引用」的出处
```

归因：E2003 报的是「类名不在可见单元里」，不是「类被删了」。harness 从头到尾用的是新轨
（`DeepBase.Plugins.Manager` + 其成员），只是把类型名写成了旧轨的 `TDeepBasePluginManager`。
两条修法对比：
- 补 `uses DeepBase.PluginManager` ⇒ 旧轨类进消费方可见面，而旧轨面并没有 harness 需要的
  `RegisterPluginKind/SetPluginDllPath/Verifier`（上表第三组命令），补了 uses 仍然编译不过，
  除非再把成员调用改回旧轨 API —— 那正是工单禁止的「把旧轨改掉/把新轨绕过」。
- 把 20 处标识符指向 harness 本来就在用的新轨类 ⇒ 语义与 uses 面、成员调用三方一致，
  轨本体零改动。

轨零改动的机械证明（判据 3）：

```
$ git diff --name-only 0d1fe7c 78d7f9f -- Core/DeepBase.PluginManager.pas 'DeepBase.Plugins*' \
      'Core/*Plugin*' 'Features/*Plugin*'
（空输出 ⇒ 命中 0 件）
```

§四  「差异只来自编码」的骨架证明（ASCII 代码骨架 CRC，忽略空白/引号/? 者为宽松骨架）
--------------------------------------------------------------------------------------------------
```
$ python .tmp/d6_skel_proof.py        # 对每件取 git show <rev>:<path> 的 ASCII 代码骨架做 CRC32
```
脚本留在一维工作区 `.tmp/d6_skel_proof.py`，本单**未入库**：它是一次性核对工具，不是门禁。
骨架口径（供复算）：严格 = 去掉行首缩进后的整行文本；宽松 = 再忽略空白、引号内容与 `?` 字符，
即「只有编码损坏会碰到的那部分」允许不同。CRC 相同 ⇒ 结构相同；宽松相同而严格不同 ⇒ 差异纯来自编码。
