1、缺陷定位（为何原 R2 的守卫是假的）
--------------------------------------------------------------------------------
- 现象：TLLMChatFrame/TFMXLLMChatFrame 的 worker body 内 TThread.Synchronize 闭包
  直接解引用捕获的 Self（frame 字段 FRichEditChat/FMemoChat/FHistory/FChatItems…），
  守卫写成 `Assigned(Self) and not (csDestroying in ComponentState)` / `Fxx = nil`。
- 根因：宿主 frame 在 Destroy 里对超时 worker 走 Evacuate（移交隔离区、不再 Free），
  但 frame 对象本身随 Owner 释放；晚到的 Synchronize 执行时 Self 裸指针仍非 nil
  （Delphi 释放对象不清空指针），Assigned/ComponentState 检查全部失效 → 读已释放内存 = UAF。
- 与 B4 不一致：B4（MVVM TContext）用引用计数回信上下文规避同类问题；原 R2 frame 未采用。

8、H13 提交 blocker：E9 .gitattributes 触发全库行尾再归一化（结构性，待主控排期）
--------------------------------------------------------------------------------
- 实测：Core/DeepBase.ManagedWorker.pas 暂存后 diff --numstat HEAD = 306/292（默认），
  --ignore-cr-at-eol = 14/0。即真实内容仅 +14 行，其余全是 CRLF↔LF 逐行 EOL 差异。
- 根因：HEAD 各 .pas blob 以 CRLF 存；E9 引入的 .gitattributes 声明 `*.pas text eol=crlf`，
  其 clean 过滤器会在下次 git add 时把 blob 归一化为 LF。由于该再归一化从未以一次专门的
  `git add --renormalize .` 落地，任意单个 .pas 一旦提交即背上"整文件 EOL 重写"的巨差。
- 后果：乙若现在提交 E8 文件，会把 306/292 级的行尾再归一化噪声一并写入，违反 H11（禁批量改行尾）；
  若改为做全库 renormalize，则会一次性波及甲并行改动的文件，违反 H13（不得携带甲活跃改动）。
  两种都是特例绕过/短期主义，乙不做。
- 建议（交主控裁定排期）：待甲 R2/R3 工作树落定后，由主控统一发起一次全库
  `git add --renormalize .` 专项提交激活 E9 立法；此后乙的 E8 代码（内容 delta 已验证干净：
  ManagedWorker +14、frame/LLMResilience 上下文守护、测试）再以精确 pathspec 落一个纯内容提交。
- 在此之前，乙已完成并通过验证的代码/测试/证据全部留在工作树，不动 index、不 sweep、不携带甲文件。
