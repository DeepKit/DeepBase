二、能力取证（逐条可复算）
------------------------------------------------------------------------------
E1  RTL 的析构登记只挂在 TComponent 上
    grep -rn "FreeNotification" <RTL>/source/rtl/{sys,common} 命中（全量）：
      common/System.Classes.pas:2650  procedure FreeNotification(AComponent: TComponent);   ← 声明在 TComponent
      common/System.Classes.pas:2651  procedure RemoveFreeNotification(AComponent: TComponent);
      common/System.Classes.pas:17666 实现（内部再调 AComponent.FreeNotification(Self)，对称登记）
      common/System.Classes.pas:17589 TComponent.Destroy → RemoveFreeNotifications
      common/System.Actions.pas:962/1098 使用方
    sys/System.pas（TObject 本体）：**零命中**。即 TObject 层没有任何
    「A 死了通知 B」的登记 API；FreeNotification 的参数类型就是 TComponent，
    传不进裸 TObject。

E2  工单预设的「仓内既有等价的弱通知机制」在 Core 不存在
    grep -rln "FreeNotification" --include=*.pas .（排除 .tmp 脚手架）命中仅三件：
      VCL/DeepBase.VCL.MVVMControls.pas、VCL/DeepBase.VCL.TrayIcon.pas
    Core 目录零命中。
    乙 B2-14 已确立的范式（VCL/DeepBase.VCL.MVVMControls.pas:282 起
    TCommandButtonBinding = class(TComponent) + FButton.FreeNotification(Self) +
    override Notification）之所以成立，正是因为被跟踪的按钮是 TComponent；
    该范式无法直接搬到「任意 TObject 的绑定目标」。

E3  唯一的弱引用件是假实现，不能当登记机制
    Core/DeepBase.Memory.pas:339  TWeakRef<T: class> = record
    :1208 GetIsAlive 只做 FRef <> nil；源码注释自证：
      「无法检测目标对象是否已被释放（悬空指针风险）」
    ⇒ 它给不了析构通知，也不能把 S3/S4 的悬垂读转变为安全读。它自身是另案缺陷面，
      不属于本单项范围（本单纪律：不得改 A5 范围外文件）。

E4  接口路线（延长寿命 / 借 _Release 感知析构）在本仓不成立
    TObservableObject = class(TInterfacedPersistent, INotifyPropertyChanged)
    （Core/DeepBase.DataBinding.pas:107）
    TInterfacedPersistent 的引用计数不参与生命周期：
      common/System.Classes.pas:471   TInterfacedPersistent = class(TPersistent, IInterface)
      common/System.Classes.pas:6203-6208
        function TInterfacedPersistent._Release: Integer;
        begin if FOwnerInterface <> nil then Result := FOwnerInterface._Release
              else Result := -1; end;   ← 计数归零既不 Free 也不回调
    ⇒ 绑定条目就算持住接口引用，也拿不到「对象正在析构」这一事件；
      对裸 TObject 目标（不实现接口）更是无从取引用。

四、三条候选路线及其代价（请主控裁定，甲不自行选路）
------------------------------------------------------------------------------
(a-1) 分层登记 + 不可登记面 fail-closed【甲的建议】
   形态：source 必须是 TObservableObject 后代 → 在自有基类 TObservableObject.Destroy
         （:259，现为 FreeAndNil(FPropertyChangedHandlers)）加一条「正在析构」通知，
         由 TBindingManager 订阅并摘除条目；
         target 必须是 TComponent → Bind 里 FreeNotification(Self)，
         manager 以 Notification() 回调摘除该对象全部条目并同步 R01 的按源计数；
         两者皆非 → Bind 抛类型化异常（Core/DeepBase.Exceptions.pas 现有类优先，
         无则新增 EBindingTargetNotTraceable），不静默降级。
   得到：S3/S4 在生产面根治，判据可复刻为真单测；符合 fail-closed 总原则与
         「质量优先于兼容，允许 breaking change」。
   代价：① `Bind` 契约从「任意 TObject」收窄为「可追踪对象」= 公共 API 语义变更，
            需登记 breaking change（CHANGELOG / consumer-contract.json 由谁落需明示）；
         ② 两处裸 TObject 测试替身必须改成 TComponent / TObservableObject 后代
            （Tests/Test.DeepBase.DataBinding.pas 的 TTestTarget、本单 R01 新单元的
            TUnbindProbeTarget）⇒ 需主控确认「改测试替身基类」不算违反「不得回归」；
         ③ TObservableObject 加析构通知 = 该基类全部后代（含 VCL/MVVM 侧）行为面扩大，
            属高频公共路径，按纪律 7 须先留既有 fixture 基线。
(a-2) 绑定持强引用延长对象寿命
   已在 E4 证伪：TInterfacedPersistent._Release 不参与生命周期，裸 TObject 无法取引用；
   且「绑定改变所有权/寿命」与 VCL Owner 树释放顺序冲突。甲不建议，列此说明已排查。
(a-3) 只覆盖可登记面，其余维持裸指针不报错
   = 主控已否决的「保留裸指针契约 + 文档化」弱路线的变体（差别只在多一层静默分支）。
   列此仅作对照，不推荐：违背 fail-closed（同一 API 有的安全有的不安全，且不可区分）。
