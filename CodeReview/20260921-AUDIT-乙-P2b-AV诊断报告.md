## 二、线性定位到具体行

**故障行：`Tests/Test.DeepBase.Resilience.Timeout.PBT.pas:240`**

```pascal
for var I := 1 to 500 do
begin
  Sleep(10);
  TTask.CurrentTask.CheckCanceled;   // ← line 240：TTask.CurrentTask = nil ⇒ AV
end;
```

**根因链：**

1. 被测入口 `TTimeoutPolicy.Execute(Proc: TProc)`（`Core/DeepBase.Resilience.Timeout.pas:88`）内部把 `Proc` 包进 `TManagedWorker.Create(...)` 的线程体，由 `TManagedWorker.TCoreThread` 驱动。
2. `TManagedWorker.TCoreThread` 的声明是 **`class(TThread)`**（`Core/DeepBase.ManagedWorker.pas:37`），`FreeOnTerminate := False`，经 `FThread.Start` 直接启动 —— 这是**裸操作系统线程，不属于任何 `TTask` 池任务**。
3. `System.Threading.TTask.CurrentTask` 的语义是「当前正在执行的 TTask」，在裸 `TThread` 上下文中调用返回 **nil**（RTL 用线程局部槽存放，未由 TTask 设置即 nil）。
4. 于是 `TTask.CurrentTask.CheckCanceled` 构成 nil 实例方法调用 ⇒ 读 `Self = 0x0` 的字段 ⇒ AV。

代码证据（`Core/DeepBase.ManagedWorker.pas`）：

```pascal
TCoreThread = class(TThread)                    // line 37 —— 裸 TThread，非 TTask
...
constructor TManagedWorker.TCoreThread.Create(...);
begin
  inherited Create(True);                       // suspended
  FreeOnTerminate := False;
  FProc := AProc;
  FOwner := AOwner;
  FDoneEvent := ADoneEvent;
end;

procedure TManagedWorker.TCoreThread.Execute;
begin
  try
    if Assigned(FProc) then
      FProc();                                  // 测试闭包在此裸线程上执行
  finally
    FOwner.FFinished := True;                    // line 283
    FDoneEvent.SetEvent;
  end;
end;
```

## 三、判断：测试自身缺陷，非生产缺陷

**判为测试缺陷。** 理由：

1. **契约不匹配在测试侧。** `TTimeoutPolicy.Execute` 从未承诺工作体运行在 `TTask` 上；它承诺的是「超时后 `Cancel` + `Evacuate` 隔离，线程结束后由看护线程回收」。测试却按「工作体可调 `TTask.CurrentTask.CheckCanceled` 协作取消」来写，这个前提在生产实现里不成立。
2. **生产取消机制本就存在且已正确工作。** `TManagedWorker.Cancel`（`Core/DeepBase.ManagedWorker.pas:224`）做的是 `FCancelEvent.SetEvent; FThread.Terminate;`，并对外暴露 `property CancelEvent: TEvent read FCancelEvent;`（line 89）。测试若要做「协作取消」观测，**正确写法是 WaitFor 这个 `CancelEvent`**（或轮询 `Terminated`），而不是 `TTask.CurrentTask`。
3. **无生产代码路径调用 `TTask.CurrentTask`。** 全仓 `CheckCanceled` 在该 fixture 之外无其它消费者，属测试孤立误用，不影响任何生产调用方。
4. **`TTimeoutPolicy` 的超时语义本身已被其它用例覆盖**：Property5（同 fixture，PASS）已断言「超时抛 `ETimeoutException`、未超时不抛、结果一致」，压测 `Test.DeepBase.Resilience.pas:1649` 的 `Test_ConcurrentFiringTimeouts_NoAV_NoQuarantineLeak` 覆盖 Cancel→Evacuate→SweepQuarantine 全路径。故修正测试的协作取消观测方式**不会削弱既有覆盖**。

## 四、修复方向（报主控，待授权后落改）

本单红线「不为绿灯删测试 / 降断言 / 加 `{$IFDEF}`」不禁止**按同语义修正测试的取消观测机制**，但工单 P2-b 授权范围是「独立诊断根因 + 给出判断」，未授权改测试逻辑。故此处只给方案，不改代码。

候选方案（按推荐度排序）：

| 方案 | 做法 | 评价 |
|---|---|---|
| A（推荐） | 工作体改为 `LPolicy` 不可达的取消信号：把 `Sleep(10)` 循环改为轮询 `TTask.CurrentTask` 之外的可观测取消源。由于测试无法从 `Execute` 内部拿到 `Worker.CancelEvent`，需让被测面暴露一个可注入的取消谓词（例如 `TTimeoutPolicy.OnCancelProbe`）或让测试改用 `TManagedWorker` 直连（绕开 `Execute`）来单独验「超时 ⇒ Cancel 事件被置位」。 | 保持「超时会取消后台任务」的断言强度，不降级。需轻微扩生产面（新增只读探针/公开既有 CancelEvent），属增强非改语义。 |
| B | 把工作体改为不依赖取消的纯长跑（去掉 `CheckCanceled`），断言收敛为「`Execute` 抛 `ETimeoutException` + 后台最终退出（`LExited` 在 `CMaxWaitMs` 内 Signal）」。 | 完全不碰生产面，最小改动；但「取消是否真的被协作感知」这层断言消失，仅保留「后台不永久挂住」。 |

**建议主控选 A**：它把「超时 ⇒ 取消信号真的送达后台」这条被测语义保住，与 WO 中「不为绿灯降断言」的红线一致；代价是扩一个只读探针面。
