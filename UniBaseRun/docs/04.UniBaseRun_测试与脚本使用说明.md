# 04. UniBaseRun 测试与脚本使用说明

> 本文档介绍 UniBaseRun 示例项目中的测试工程结构（含 GUI 测试）以及脚本（.bat）的职责与使用方法，便于在命令行或 CI 环境中统一构建与运行。

## 1. 测试体系概览（DUnitX）

UniBaseRun 使用 **DUnitX** 作为单元测试框架，并提供两种运行方式：

1. 命令行测试工程：`tests\UniBaseRun.Tests.dpr`
   - 适用于本地快速测试与持续集成（CI）环境；
   - 运行结束时以进程返回码表示成功/失败，便于脚本与 CI 检测。

2. GUI 测试工程：`tests\UniBaseRun.GuiTests.dpr`
   - 使用 FMX 实现的图形界面测试运行器；
   - 集成并可视化展示所有 DUnitX 测试结果；
   - 方便开发阶段交互式调试和观察测试行为。

所有测试用例单元（`Tests.*.pas`）尽量与业务代码解耦，优先通过接口（Controller 接口等）访问业务逻辑，而非直接操作窗体控件。

## 2. 测试目录结构与命名

在 `tests/` 目录下建议结构如下：

```text
tests/
  UniBaseRun.Tests.dpr       <-- 命令行测试工程
  UniBaseRun.GuiTests.dpr    <-- GUI 测试工程
  Tests.Config.pas           <-- 配置相关测试
  Tests.LogView.pas          <-- 日志查看相关测试
  Tests.MainForm.pas         <-- 主窗体相关测试（多为 GUI/集成测试）
  Tests.*.pas                <-- 其他测试单元
```

命名约定：

- 所有测试单元以 `Tests.` 开头，后接被测试模块名称或功能，如 `Tests.CtrlMain.pas`；
- 测试类和测试方法采用 DUnitX 推荐的命名方式，如：
  - `TConfigTests` / `TLogViewTests`；
  - 方法名使用 `Test_功能描述` 形式。

## 3. 测试中的 UniBase 初始化

为了保证测试可重复、可预测：

1. **不要直接依赖真实部署目录的 root.txt 与 config.db**。
2. 在测试工程或测试初始化代码中：
   - 使用测试专用的 root 路径（例如指向 `tests\TestRoot` 目录）；
   - 或使用 UniBase 提供的“内存数据库”/临时数据库初始化方式（如 `InitializeWithDB(':memory:')`）。

典型模式：

- 在 `Tests.Config.pas` 的初始化部分：
  - 构造一个 `TUniBaseManager` 实例；
  - 调用测试专用的初始化逻辑；
  - 在测试完成后释放实例，避免污染全局状态。

> 具体初始化细节请参考 `04_安全与测试.md` 与 `02_开发指南.md` 的“测试友好初始化”章节，并结合实际 UniBase.Core 的实现。

## 4. 脚本概览

所有脚本位于 `scripts/` 目录下，使用 **.bat** 格式（对中文环境友好）。建议的脚本清单：

```text
scripts/
  init-project.bat    <-- 初始化新项目（在复制模板后运行）
  build.bat           <-- 构建主程序
  test.bat            <-- 构建并运行命令行测试
  test-gui.bat        <-- 运行 GUI 测试工程
  run.bat             <-- 运行主程序（可选）
```

脚本中尽量使用相对路径，以 UniBaseRun 目录作为工作目录，避免对绝对路径的硬编码。

## 5. init-project.bat：新项目初始化脚本

### 5.1 使用场景

当你需要基于 UniBaseRun 创建一个新项目时：

1. 将 UniBaseRun 整个目录复制到新位置，例如：`D:\Work\MyApp`；
2. 在新目录中运行：

```bat
scripts\init-project.bat
```

3. 按提示输入：
   - 新项目名称（例如 `MyApp`）；
   - （可选）公司/组织名、命名空间前缀等。

### 5.2 预期行为

- 将以下内容从 `UniBaseRun` 重命名/替换为新项目名：
  - `UniBaseRun.dpr` → `MyApp.dpr`；
  - `UniBaseRun.dproj` → `MyApp.dproj`；
  - tests 目录中的工程文件名（如需要）。
- 在代码和配置中执行占位符替换：
  - 工程文件中的输出名；
  - 代码中出现的 `UniBaseRun` 字样（作为项目名，而非文档标题）；
- 重写 root.txt：
  - 将其中内容更新为新项目根目录的绝对路径；
- 清理或重置：
  - 可选地清理示例生成的临时文件（如旧日志、临时配置等）。

> 具体替换规则应在脚本实现时统一整理，确保不会误改文档中的示例内容（例如保留某些教学用途的 "UniBaseRun" 字样）。

## 6. build.bat：构建脚本

### 6.1 作用

- 负责编译 UniBaseRun（或新项目）的主程序 EXE；
- 可根据参数选择 Debug / Release 配置；
- 编译成功后在指定输出目录（如 `bin/` 或根目录）生成可执行文件。

### 6.2 建议行为

- 检查 Delphi 编译器是否可用；
- 默认编译当前目录下的 `.dproj` 主工程；
- 支持参数：
  - 无参数：编译 Debug；
  - `release`：编译 Release；
- 编译结束后：
  - 显示简要结果（成功/失败、输出路径）；
  - 返回码为 0 表示成功，非 0 表示失败。

## 7. test.bat：命令行测试脚本

### 7.1 作用

- 编译并运行 `tests\UniBaseRun.Tests.dpr`；
- 供本地和 CI 快速验证代码是否通过所有单元测试。

### 7.2 建议行为

1. 如有需要，先调用 `build.bat` 编译主工程（可选）。
2. 编译测试工程生成 `UniBaseRun.Tests.exe`；
3. 运行 `UniBaseRun.Tests.exe`，将输出直接打印到控制台；
4. 根据测试框架返回结果设置进程返回码：
   - 所有测试通过 → 返回 0；
   - 存在失败/错误 → 返回非 0。

这有利于：

- 在命令行中通过 `if errorlevel 1` 检查是否存在测试失败；
- 在 CI 系统中通过构建步骤的返回码判断构建是否成功。

## 8. test-gui.bat：GUI 测试脚本

### 8.1 作用

- 启动 `tests\UniBaseRun.GuiTests.exe`（FMX GUI 测试工程）；
- 方便开发者在图形界面中查看测试列表、执行测试并观察结果。

### 8.2 建议行为

1. 如有必要，先编译 GUI 测试工程；
2. 直接运行生成的 EXE；
3. 不对返回码做严格约束（GUI 关闭即结束），主要面向人工使用场景。

## 9. run.bat：运行主程序

### 9.1 作用

- 简化本地调试启动流程：
  - 自动查找并运行主程序 EXE（如 `UniBaseRun.exe` 或初始化后新的项目名）。

### 9.2 建议行为

1. 检查主程序是否存在：
   - 若不存在，可提示先运行 `scripts\build.bat`；
2. 直接启动 EXE；
3. 可选择在控制台中输出少量提示（如"正在启动 UniBaseRun...")。

## 10. 在新项目中的复用方式

当你基于 UniBaseRun 创建新项目时，推荐：

1. 保留 `tests/` 与 `scripts/` 目录结构和脚本；
2. 按照本说明调整 `init-project.bat` 中的项目名与占位符规则；
3. 在扩展业务逻辑时：
   - 为新模块编写对应的 `Tests.*.pas`；
   - 确保测试工程也引用新模块；
4. 在 CI 中：
   - 将 `scripts\build.bat` 和 `scripts\test.bat` 作为标准构建/测试步骤调用；
   - 根据返回码决定构建是否通过。

通过统一的测试与脚本体系，可以显著降低新项目启动成本，并保证所有 UniBase 项目在构建与测试流程上的一致性。
